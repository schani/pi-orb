# Embedded Pi 0.99.1 characterization

Run: `node --experimental-strip-types --test scripts/native-mcp-exploration/embedded-history.test.mjs` (five passing, no provider credentials or external network). The model is `fauxProvider`; a loopback JSON-RPC MCP server supplies one tool. Pi's public SDK factories and `AgentSessionRuntime.dispose()` are exercised.

First red: missing `embedded-fixture.mjs` (`ERR_MODULE_NOT_FOUND`, `evidence/embedded-first-red.tap`); subsequent sanitized failures retained in `evidence/first-script-failure.json`, `evidence/failure-runtime-refactor.json`, `evidence/failure-cancel.json`, `evidence/failure-startup.json`. The initial script forgot to await `searchTools`; the runtime refactor asserted activation before startup finished; plain `AgentSession.dispose()` did not run `session_shutdown`, leaving an initialized connection. A pending-startup failure initially counted an HTTP response as an established MCP connection; only `notifications/initialized` proves that connection. Later failure traces use unique paths under `/tmp/embedded-pi-*.json` and print them on failure. During the review, the first revised assertion failed because `codemode-store` uses `data.set.evidence.matches`, not `data.value.matches` (`evidence/embedded-review-red.tap`); it was corrected after inspecting that result. Each test has a five-second watchdog; cleanup releases blocked server requests before awaiting shutdown.

Codemode `searchTools("echo")` stored `matches: 1` in `codemode-store`, then executes the callable MCP tool under a parent tool call; the MCP declaration is not directly active. Pi stores `codemode-store` entries and the parent result's bounded `nestedCalls` summary; both survive JSONL reload. `apps/orb-runtime/src/pi/mapping.ts` preserves the summary under `overflow.native.message.nestedCalls`, but its typed projection has no nested-call hierarchy. Live nested events include `parentToolCallId`; these are not separate session entries. This does **not** demonstrate browser permission approval, UI rendering, or fidelity of nested results (Pi only stores call summaries).

The public SDK does not expose a shared native MCP connection handle. Two independently bound sessions using the same approved extension registration establish two distinct session IDs (`fixture-1`, `fixture-2`): child shutdown DELETE retires only its ID; the root's third tool call uses its original ID without a new initialize (two initializations, three tool calls). The fixture rejects unknown/retired IDs. This is a viable simpler per-session ownership option, not a proof of sharing or host-level approval policy. One accepted call is held without a server reply; `session.abort()` yields a nested `tool_execution_end` with `isError: true` and a persisted failed codemode result before the response gate opens. Awaited runtime shutdown closes its connection. Shutdown during blocked initialization prevents a late initialized connection; the fixture does not model every network race.

Startup HTTP failure is visible at the transport; `manager.getEntries()` has no durable failure diagnostic. Pi's released MCP extension routes failed-connection status through `ctx.ui.notify` (`dist/extensions/mcp/index.js`, `reportProblems`), **source-reviewed, not UI-captured by this fixture**. A host requiring user-visible persistent failure needs its own bridge. The released package lacks the local custom-message preflight/cancellation patch and Codex diagnostics hooks; these tests do not imply otherwise.
