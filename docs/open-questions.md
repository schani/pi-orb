## Orb boot hooks

41. Define a per-project boot setup hook — the analogue of Amp's `.agents/setup` (2026-08-25; the general form of question 13, which asked only whether to adopt one). Decide **what** runs (a single well-known repository script, an Orbfile stanza, or a list of commands), **when** it runs (first boot only, every start, after compute replacement, after a checkout update), what it may assume (network, brokered credentials, a durable `$HOME` that may already carry the previous run's state), and how failure is reported (a `lifecycle:` event and a user-visible orb state, not silent stdout). The trust implication is smaller than it looks: repository code already runs as the agent in an orb, so a boot hook grants no new authority — it only moves the moment of execution earlier than the human's first prompt, which is precisely what makes an unattended orb useful and what makes a malicious commit take effect without anyone reading it. Motivating case: `apps/orb-runtime/skills/cloud-identity/SKILL.md` ends its Google Cloud flow by committing a non-secret external-account configuration plus a setup script, because the *trust* side of workload identity is per GCP project and permanent while the *in-orb* side — write the credential file, export three variables, run the `--cred-file` login — has to be redone in every new orb. With a boot hook that is zero steps; without one the next orb's agent or human has to run the script deliberately, and the skill must say so rather than imply it happens by itself. See `docs/workload-identity.md`. **Resolved (2026-08-25):** requirements in `docs/orb-setup-hook.md` — setup runs on the first boot of every compute incarnation with identity removed from its environment, resume runs on every start with identity, failure is user-visible and the orb still starts; implementation tracked in `TODO.md`.
