# Remote MCP

Status: **static headers implemented** (2026-09-08); **OAuth implemented locally, not deployed or live-provider-qualified** (2026-09-10). The implemented OAuth contract below supersedes the earlier planning details where stated. Historical investigation and rejected alternatives are retained below. Provider-account qualification remains tracked in `TODO.md`; public documentation is not an authenticated provider smoke test.

## Requirements

- The user wants an orb to be able to initiate adding a remote MCP server, the human to authorize it, and both server configuration and authorization to be available automatically in new orbs **of that project**. User clarification (2026-09-08): MCP connections must belong to projects. The earlier account-wide interpretation was incorrect; there is no global inherited catalog or implicit cross-project credential sharing.
- User clarification (2026-09-08): API keys may be ordinary project secrets readable by the orb. Refresh tokens still remain control-plane-owned; accepting static API key exposure does not require distributing OAuth refresh ownership.
- Initial target services: PostHog, Cloudflare, Datadog. Architecture must prioritize simplicity and robustness, with deterministic simulation boundaries designed before implementation.
- User decision (2026-09-08): **no OAuth in the initial implementation**. Ship static secret-backed headers. OAuth design below is future context, not first-release machinery: no callback routes, client registration, login-attempt persistence or refresh broker is needed for this slice.
- Dashboard-only addition is an acceptable first cut if in-orb initiation is disproportionately complex. A control-plane setup link returned by an orb avoids needing a terminal UI bridge and appears small enough to retain the preferred workflow.
- Pi SDK upgrades are routine and may be made whenever needed (user clarification 2026-09-08). The current SDK pin is a reproducible validation target, not a constraint on the design.
- Existing credential rules in `docs/credentials.md` remain: durable credentials belong to the control plane, never repository files, orb volumes, history, or logs. New orbs reuse a grant, not an MCP transport session.

## Implemented first slice (decision, 2026-09-08)

- The project-name **gear** on the dashboard and orb view opens one Config dialog with **General**, **MCPs** and **Secrets** tabs (2026-09-09). The selected MCP workbench/compact ledger is implemented 2026-09-11: chat-style native disclosures, a closed-by-default Add flow, Name before Endpoint, and OAuth or a bearer-token secret reference. Key values stay in Secrets; partial names/endpoints/authentication choices survive collapse and tab switches. Presets are optional shortcuts for PostHog, Cloudflare and Datadog US5. Description is exposed directly when editing, not under Advanced. Arbitrary headers remain in the catalog/transport contract, but nonrepresentable connections are explicitly blocked from editing instead of silently dropping their headers. Server names remain project-local identities; catalog membership means enabled. The token picker is a real dropdown of existing secrets. Catalog publication and secret deletion share the project row lock: missing references cannot be published and referenced names cannot be removed (HTTP 409); replacing a secret is allowed. Every secret-bound header participates, not only bearer Authorization. See `docs/web-ui.md` and `docs/credentials.md`.
- `GET /api/v1/projects/:projectId/mcp` returns `{revision, servers}`. `PUT` replaces the catalog using its expected revision, returning the incremented revision or 409. PostgreSQL locks the project row before checking the deletion fence and catalog revision; project deletion cascades the catalog. Maximum 20 servers, 16 headers/server, 240-character descriptions. Configuration contains no resolved credentials.
- `POST /api/v1/projects/:projectId/mcp/describe` uses project secrets for authenticated MCP metadata inspection. The browser can fetch/edit a description or automatically use it when saving an empty description. Missing metadata requires a human description. Unreachable/private endpoints can be saved with an explicit confirmation and manual description; inspection is not a requirement for ordinary coding. No model-generated summaries or automatic use of server `instructions`.
- Control-plane inspection is **public HTTPS only**: reject private/reserved IPs, validate DNS at socket lookup (no preflight/rebinding gap), forbid redirects, userinfo and fragments. An orb already has arbitrary project code/network access; its configured direct HTTPS endpoint may be private. This distinction permits private MCPs without granting the control plane private-network fetch authority. No insecure TLS bypass or HTTP endpoint setting ships.
- Incarnation-authenticated `GET /runtime/v1/mcp` derives project ownership from the orb, not request parameters. Boot fetches this catalog and resolves bindings against the existing project-secret snapshot. There is no runtime mutation route, OAuth, CLI proposal state, gateway, live update, or background connection manager. Changes/rotation/removal apply on **next process start**. Revoking an already-delivered key still requires provider-side revocation.
- The official `@modelcontextprotocol/client@2.0.0` owns protocol negotiation and Streamable HTTP. One connection owner serializes work for each server, while search connects different servers concurrently. Cleanup aborts pending work, fences late completion, and waits for ownership to release. A failed call is never automatically replayed; the next explicit operation may reconnect. SDK calls have 30-second deadlines and background transport reconnection is disabled.
- Three fixed Pi tools: `mcp_search({query?, server?, kind?, offset?, limit?})`, `mcp_call({server, tool, args?})`, and `mcp_read({server, kind, name?, uri?, args?})`. Search defaults to all four kinds, five entries/page (maximum 20), with per-server failures. Prompt arguments are strings. Templates return definitions; resource URIs go only to the selected MCP server. Tool arguments are checked against discovered schemas using Ajv's JSON Schema 2020-12 validator, matching MCP's schema dialect; nonstandard async validation is rejected. Failed schema compilation cannot leave a partially cached validator usable by a later call.
- Catalogs are cached per connection, limited to 5,000 entries/4MB and 50 pages per kind, rejecting repeated cursors. Partial catalogs are not published. An explicit method-not-found on the first resource/template-list page means that optional method is unsupported; it must not disable otherwise working tools. Recognize both SDK protocol errors and bounded JSON-RPC method-not-found envelopes carried by HTTP 404, as PostHog actually returns; ordinary 404/authentication/5xx failures are not silently skipped. Other HTTP errors retain their numeric status in sanitized tool output. Evidence: `docs/postmortems/2026-09-09-posthog-template-discovery.md`. Mid-pagination errors and other failures still reject the catalog. Tool output is JSON, bounded to 50KB/2,000 lines; oversized full JSON is saved in a private temporary directory. Binary/image payloads remain encoded JSON, not an Apps or image-rendering integration. Prompts retain message-role metadata inside labeled external tool output; they never become trusted messages or trigger a turn.
- The resource loader appends only configured server names/descriptions, without connecting or loading catalog contents. **Do not use only `before_agent_start` for this inventory:** Pi's inbox `sendCustomMessage(..., {triggerTurn:true})` bypasses that hook. The additive loader covers both queued and live first turns. Tool semantics live in tool definitions, not repeated prompt instructions. User clarification (2026-09-09): the shared runtime prompt also includes one short setup sentence directing the model to ask the human to open the project config gear and use its MCPs and Secrets tabs, with next-start adoption. This sentence is present even with an empty catalog and applies to the process host provider as well.
- Durable observability: adoption changes append `pi-orb:mcp-config` session records with catalog/secret revisions and server names, never header values. Tool failures use ordinary replicated tool output (search retains failed-server entries). Extension load/collision/bind failures fail readiness visibly; handler failures append visible `pi-orb:extension-error` messages. Healthy reads produce no extra records.

Tests start at domain boundaries: connection ownership/cancellation/late completion/lost-write DST, PostgreSQL revision/deletion contracts, runtime project-scope authorization, real SDK HTTP negotiation/pagination/read/call/redirect/no-replay contracts, and additive Pi-loader contracts. `e2e/mcp.e2e.test.ts` exercises real Pi and authenticated HTTPS with the browser, same-project reuse, and isolation. Independent automatic naming must have its own fake-model session; the ordered main scenario cannot be shared by concurrent consumers. Wait for a replicated completion marker before asserting control-plane history, not merely for streamed browser text. After a hash-route orb switch, wait for the selected navigation entry and `aria-busy=false` before typing: the retained old composer is inert during loading, so typing before route adoption is not a delivered message.

### Client-library choice and own-extension decision (2026-09-08)

The user approved implementing our own Pi extension, prioritizing the smallest reliable architecture with no speculative features. This resolves the extension-versus-owned-bridge choice; implementation is tracked in `TODO.md`. First-party extension composition uses Pi's own facilities rather than a new plugin system (`docs/pi-adapter.md`).

Recommended client library: **the official TypeScript SDK v2, `@modelcontextprotocol/client@2.0.0`**, with `@modelcontextprotocol/core@2.0.0` as a direct dependency only where our code imports its shared types/schemas. Registry metadata and the published client README were checked on 2026-09-08: v2 is the stable line, Node >=20, and replaces the monolithic v1 package. Pin the selected release in the lockfile; do not implement JSON-RPC, Streamable HTTP, protocol negotiation or OAuth primitives ourselves. Cross-version protocol behavior, cancellation and hidden retry behavior still require contract tests against the selected servers/fakes; an npm version is not a promise of compatibility with every deployed MCP revision.

### Executed smoke test

Repository dependencies were installed with `npm ci`. An isolated temporary npm project installed `pi-mcp-adapter@2.32.1`, Pi SDK/AI/TUI `0.85.1`, and `tsx`, with install scripts disabled. A loopback HTTP fake accepted MCP initialize/list/call, asserted a synthetic bearer header on every POST, and exposed an `echo` tool. No real account login, upstream MCP service, or inference request was used.

Findings, including initial failures:

1. The adapter declares optional `pi-ai ^0.84.1`; npm rejects explicitly pairing it with `0.85.1`. The isolated experiment used `--legacy-peer-deps` to test actual behavior. This is packaging evidence, **not** a proposed production install policy. Resolve the declared range with the upstream package or a reviewed package change; a Pi upgrade alone does not fix a peer range capped below our already-newer version.
2. With the runtime's current `createAgentSession` shape and no `bindExtensions`, `mcp` registers but a lazy connect returns `not_initialized`. At investigation time, `apps/orb-runtime/src/pi/agent.ts` did not bind extensions (the implementation now does); Pi's `bindExtensions` emits `session_start`. The adapter has a load-time fallback only for eager/keep-alive configs.
3. Adding `await session.bindExtensions({ mode: "print", onError })` before invoking tools makes the test pass: authenticated HTTP initialization, paginated-tool entry point, discovery, and `smoke_echo({ text: "orb-compatible" })` return `echo:orb-compatible`. This test used a single page; pagination itself was not qualified.
4. Therefore the transport/tool path works in a headless embedded Pi session after correct lifecycle binding. This is **not** evidence that an unmodified install works in the existing pi-orb runtime, nor an end-to-end production OAuth qualification. Shutdown, abort, reconnection, and lifecycle-error publication also need explicit host integration.

The fixture used in-memory Pi credentials/settings/session, a temporary `agentDir`, `DefaultResourceLoader.extensionFactories: [createMcpAdapter({ config })]`, `settings.scriptMode/sampling/elicitation: false`, one lazy URL server with a synthetic Authorization header, and direct calls to the registered `mcp` tool's `execute` method. The server used an OS-assigned port and was closed after the test. Temporary logs preserved the unbound failure separately from the bound success.

### Environment implications

- Pi TUI panels, footer notices, and custom renderers do not become web UI automatically. Our normal tool result/history mapping can display text/images, but `/mcp setup`, interactive auth, approval prompts, elicitation, and MCP Apps require separate host support. Ordinary orb messages use `sendUserMessage`/`sendCustomMessage`, not a terminal slash-command dispatcher.
- Explicit lifecycle binding is necessary, not a TUI requirement. The platform bridge should be baked/loaded by the runtime, with an explicit config/agent directory; `pi install` into a guest default home does not establish shared project configuration.
- Current main-adapter `headers: { Authorization: "!command" }` and `bearerToken: "!command"` are evaluated at connect time, **not** for every request. They cannot alone refresh an already-open connection. `requestHeadersCommand` does run per request, but gives the helper the exact body; if used, it must be a platform-owned helper and only credentials/connection identity, never request bodies, go to the credential broker. A native per-request credential callback is preferable for an owned adapter.
- Keep sampling, form/URL elicitation and Apps out of the initial supported surface rather than pretending headless defaults offer the human interaction they require. MCP authorization and MCP URL elicitation are distinct features.

## Earlier in-orb setup proposal (not implemented)

The initial implementation chooses browser-owned configuration to avoid pending-proposal storage and CLI machinery. Originally dashboard-only, the same project config dialog is also reachable from the orb view's gear (2026-09-09). The earlier alternative below remains design context, not a shipped route or command contract:

```text
pi-orb mcp add <name> <https-url>
# returns a pi-orb setup page URL, not an upstream token or OAuth callback
```

1. The incarnation-authenticated orb creates a bounded, durable **pending proposal** containing a name and URL. The control plane derives the project from the caller; the orb cannot choose another project. Proposed human confirmation owns persistent project configuration changes, including replacing a URL or selecting a secret reference. This is configuration-integrity policy, not protection against an orb already authorized to read that project's secrets.
2. The human opens the ordinary authenticated pi-orb browser page. It shows the project, actual server origin and relevant auth settings. Static auth uses a write-only project secret field/reference; OAuth shows the provider and scopes. Confirmation enables the connection for that project's orbs.
3. Initially, setup selects or writes project secrets and saves header bindings. There is no OAuth ceremony. In a future OAuth implementation, authorization would redirect to one stable HTTPS control-plane callback, with state/PKCE never passing through the agent and credential commit independent of the originating orb's lifetime.
4. The control plane persists project-owned connection metadata and secret references. Every new/started orb fetches its project's enabled catalog and secret snapshot automatically. Proposed first cut: additions, URL changes and static-key rotations apply on process boot, like existing project secrets. The originating orb can restart to use a new connection. Explicit idle-boundary sync is a later option, not a first-cut requirement or a promise of hot updates.
5. Dashboard Add creates the same proposal and follows the same flow. Reconnect, disable and remove are browser actions too. A broken MCP connection must not block unrelated coding work or every new orb's boot.

In-orb addition is therefore principally a small CLI/API entry point to the same browser-owned flow, not a full Pi UI/RPC protocol implementation. The browser page link is non-secret and can safely live in history; possession of it is not authority to complete setup. Protect mutation endpoints against CSRF and cap pending proposals per caller/project. Missing/deleted project or connection pages preserve the requested URL and show the resource-specific missing message.

## OAuth implementation (2026-09-10; deployment and live qualification pending)

The user approved implementation, specified **Datadog US5**, and will configure its OAuth redirect allowlist. Cloudflare account identity is selected during provider consent, not an input required to start implementation.

### Implemented contract

- The MCP form now offers **OAuth** or **Bearer token** (UI redesign implemented 2026-09-11). Cloudflare defaults to `https://mcp.cloudflare.com/mcp`; Datadog defaults to `https://mcp.us5.datadoghq.com/v1/mcp`. Both optional presets select OAuth; PostHog selects a bearer reference to `POSTHOG_KEY`. The narrow UI does not replace the underlying static-header catalog/transport contract. OAuth saves require no unauthenticated description probe; a supplied description or bounded name-based description is used. Add & connect persists the catalog before initiating authorization, reporting a saved-but-authorization-failed outcome explicitly. Non-Authorization header bindings remain supported through the API; combining OAuth with an explicit Authorization binding is rejected.
- OAuth catalog entries add `oauth: { id: "<uuid>" }`. Static entries retain their existing shape. The immutable OAuth ID is project-owned and URL-bound, not the mutable tool-facing name; editing the URL allocates a new ID. Catalog removal/auth-mode replacement atomically clears the old grant and fences its callbacks/refresh commits. Re-adding an old ID cannot revive its grant. No compatibility staging, new MCP tools, guest callback or token files.
- Browser routes: `GET /api/v1/projects/:projectId/mcp/:id/oauth` → `{status: "connected" | "pending" | "auth_required"}`; `POST .../oauth/connect` with `{}` → `{url}`; `POST .../oauth/disconnect` with `{}` → `{status: "auth_required"}`. Mutations require same-origin JSON. The stable callback is **`${PI_ORB_APP_ORIGIN}/api/v1/mcp/oauth/callback`**. It exchanges the code in the control plane and returns to `/#/projects/:projectId/mcp`, which opens the existing Config dialog on MCPs. This is also the safe setup link in broker failures. Ordinary gear entry still defaults to General. Failed/expired callback validation redirects to a clean failure URL; missing connection callbacks show a resource-specific error with a dashboard link.
- Random state contains non-secret project/connection routing plus 256-bit entropy; only its hash is persisted. An independent browser nonce is hashed in the attempt and delivered in a host-only HttpOnly SameSite=Lax cookie (`__Host-`/Secure on HTTPS). PKCE verifiers, discovered issuer/resource/client context, any client secret and tokens live exclusively in immutable secret-store versions under **`mcp-oauth`**, never PostgreSQL, project secrets, browser reads or history. Pending attempts have a ten-minute lifetime and one fenced exchange owner; duplicate/stale callbacks cannot exchange or publish twice. Initiating a new ceremony invalidates the old one and pauses new broker grants until consent completes; an unsuccessful Reconnect does not silently restore the previous grant. After process restart another instance can finish a pending ceremony; a crash after claiming/exchanging may require new consent rather than guessing whether a code was consumed.
- `POST /runtime/v1/mcp/:id/token` accepts `{url, rejectedGeneration?}` and returns only `{accessToken, expiresAt, generation}`. The route derives the project from the incarnation bearer, verifies the current catalog ID/URL, and reauthenticates after broker work. The broker's secret reader also checks payload project/connection identity. Caller-supplied project parameters grant no authority. This connection-scoped route deliberately does **not** expand the global `model | github` token-name enum.
- The domain adapts the existing `getToken` broker's leased refresh, exact-version readback and generation-CAS machinery instead of implementing another refresh state machine. The runtime resolves credentials before HTTP requests, caching until 30 seconds before expiry. A 401 marks only the rejected generation; the next explicit operation can request a newer token. Two consecutive rejected generations stop automatic refresh attempts until a newer browser grant appears. No SDK OAuth provider is installed in the guest, so the SDK cannot launch consent or silently replay tool calls. HTTP errors and lost writes remain ordinary replicated tool failures. Configuration adoption remains restart-only, while repairing authorization for an already-configured server does not require restart. Already-delivered tokens cannot be erased by Disconnect; provider revocation/expiry determines their remaining validity.
- **Registration decision (2026-09-10): initial OAuth uses advertised dynamic client registration.** Both required providers advertise it, so pre-registered-client UI and public Client ID Metadata Document hosting are not implemented. The SDK marks DCR deprecated for newer protocol revisions but still supports it; this is an explicit narrow implementation choice, not a claim that CIMD is unnecessary forever. Authorization code + S256 PKCE, issuer-echo validation, callback issuer validation when advertised, and resource binding use the official SDK primitives. Bearer tokens without a finite positive `expires_in` are rejected rather than inventing a lifetime. A missing refresh token is preserved as absent and eventually requires reauthorization; no implicit static-key fallback.
- Every control-plane discovery/registration/token fetch uses public HTTPS, socket-time DNS validation, disabled redirects, a ten-second fetch deadline and a 1 MiB response cap. Authorization endpoints are validated too. The test-only entry injects an exact-fixture-origin SDK network adapter; production has **no environment switch** to disable this policy or TLS verification. Browser callback headers are no-store/no-referrer with restrictive CSP. `infra/mcp-oauth.tf` creates the Secret Manager parent/IAM and excludes callback request URLs from Cloud Logging's default sink; deployed IAP continuation and any additional logging sinks still require qualification. The browser revision depends on that exclusion and secret IAM. The 2026-09-11 partial apply exposed missing deployer exclusion authority; the foundation-owned CRUD grant is now applied and federation-verified, and the release preflight correction is locally tested. Application recovery is still pending. Do not exercise production OAuth callbacks before verifying the exclusion exists (`docs/postmortems/2026-09-11-release-logging-exclusion-iam.md`).
- Migration `018_mcp_oauth.sql` stores fenced grant/attempt state and durable **`mcp_oauth_events`**. Connect/pending/exchange/connected/denied/expired/invalidation/refresh failure/removal edges contain connection identity and generation; ceremony failures include a safe error code, never credentials or remote error bodies. Consecutive refresh failures are coalesced. Pointer retirement transactionally queues exact immutable versions in **`mcp_oauth_garbage`** (including removal/replacement). A browser-role five-minute collector retries destruction idempotently; failed cleanup stays queryable and emits only failure/recovery edges. This is credential garbage collection, not a connection supervisor or proactive refresh daemon. In-flight secret writes recheck project/catalog authority; project deletion's existing quarantine precedes full namespace enumeration, which also removes unpublished crash residue. Unpublished writes whose outcome is uncertain remain for project cleanup, never guessed into a usable grant.

### Executed evidence and boundaries

Public discovery performed 2026-09-10 (no registration or account consent against the live providers): Cloudflare advertises issuer `https://mcp.cloudflare.com`, resource `https://mcp.cloudflare.com/mcp`, `/register`, S256, refresh grants and callback `iss` support. Datadog US5 advertises issuer `https://mcp.us5.datadoghq.com/v1/mcp`, resource `https://mcp.us5.datadoghq.com`, authorization/token/registration endpoints on `https://us5.datadoghq.com`, `mcp_all`, S256, public-client auth (`none`) and refresh grants. SDK URL serialization adds a trailing slash to an origin-only resource such as Datadog's; synthetic contracts assert that actual wire behavior rather than a raw-string metadata echo.

DST was implemented before routing/UI: production coordinator/broker/resolver with injected stores and protocol effects; duplicate callbacks, lost commit acknowledgement, wrong browser, expired consent, code-response loss, failed credential persistence, independent disconnect-versus-exchange actors, and a late invalid-grant response racing a newer login. Existing broker DST retains refresh-storm/lease-expiry/rotation-loss coverage; new garbage-collection DST proves retained cleanup ownership and exact-version isolation. PostgreSQL-shaped PGlite contracts exercise CAS, catalog/project fences and the retirement trigger. The same store/retirement-trigger suite also passed against a disposable **network PostgreSQL 18.4** cluster (2026-09-10), using a test-owned schema selected by `PI_ORB_TEST_DATABASE_URL`; the cluster was stopped and removed afterwards.

Pinned-SDK contracts cover both provider metadata shapes, PKCE/resource/issuer exchange, omitted replacement refresh tokens and rejected private endpoints. Runtime HTTP contracts count accepted calls to prove request-time token injection and no 401-triggered replay. Browser route tests complete a durable attempt with a newly constructed instance, reject CSRF/wrong-browser/duplicate callbacks, and verify redaction. `e2e/mcp-oauth.e2e.test.ts` uses real browser consent, real control-plane routes/storage, HTTPS OAuth/MCP and two real Pi runtimes: shared grant reuse, explicit rejection/retry refresh, revoked-grant reauthorization without restarting, foreign-project rejection, disconnect stopping new grants and transcript redaction. Naming and per-turn summaries have independent ownership/explicit completion barriers.

Two development failures were preserved and understood before proceeding: (1) the first DST trace (`test-failures/mcp-oauth-refresh-1789056888883-0.json`) exposed an incorrectly nested `ResultAsync` that treated a failed lease CAS as success; flattening the adapter result fixed the product error; (2) the first browser OAuth E2E hit the existing hosting cross-site API guard before callback handling. The guard now exempts **only the exact callback GET**, never POST, WebSocket, other API paths or the hosted-files origin; single-use state/browser binding/PKCE still authorize completion. Merely passing unit tests would not have found the browser navigation rejection.

Validation: `npm ci`, workspace/E2E typecheck, `npm run lint` (only pre-existing warnings), the full unit/infra suite (1,617 tests passed at the final full run, 5 opt-in skips), and `PI_ORB_E2E_BACKEND=process npm run test:e2e` (26 passed, 2 opt-in skips). Subsequent focused tests cover the final cleanup/callback changes and monotonic token-cache adoption under out-of-order SDK background-request responses; the complete OAuth browser/Pi E2E also passed again after cleanup changes. **No deployment, Datadog organization consent, Cloudflare account consent or authenticated live-provider call has been performed.** Those required release gates remain in `TODO.md`; synthetic metadata and OAuth fixture success do not clear them.

### Cloudflare process-host preflight (2026-09-10)

The user chose Cloudflare first and requested a process-host test instead of a production rollout. A separate `all`-role control plane is running on port **7180**, with PGlite, file-backed credentials and process hosts under `~/.pi-orb/cloudflare-qualification/`; its PID and non-secret project/connection identifiers are recorded there. It uses a dedicated `Cloudflare OAuth test` project with the public `octocat/Hello-World` repository, not a production project. Process hosts are unsandboxed; this validates the protocol on a trusted host, not production credential isolation. No production deployment or Tailscale Serve/Funnel configuration was changed.

**New live evidence:** Cloudflare accepted dynamic registration and authorization preparation using the private **HTTP tailnet callback**; the authorization destination was `https://mcp.cloudflare.com/authorize`. This qualifies registration only, not authorization-time redirect acceptance, human consent, token exchange, refresh or an authenticated MCP call. The operator's preflight attempt was explicitly disconnected afterwards so the human starts a fresh ceremony with their own browser nonce. User entry is the service's configured tailnet origin at `/#/projects/<test-project-id>/mcp`; using localhost in the human browser would reach the wrong machine. The guest browser could not resolve its own MagicDNS hostname, so UI rendering/authorization-required state was checked through localhost; the user must use the configured tailnet URL for same-origin mutations.

Preparing this HTTP test exposed a frontend bug: the new OAuth form called secure-context-only `crypto.randomUUID` directly. It now uses the existing `generateUuid` helper, which falls back to `crypto.getRandomValues` on trusted-network HTTP. Web typecheck, UUID/form tests and the served frontend build passed. Live account consent remains pending with the human; no account identifier or API key is required in chat.

**Authorization-time rejection (2026-09-10):** the human reached Cloudflare's authorization page, which rejected the callback with `invalid_request`: “Redirect URI must use HTTPS or a local loopback address”. Accepted DCR and the public Cloudflare server-library source were insufficient evidence for the deployed authorization endpoint's policy. Our implementation uses the official `@modelcontextprotocol/client` OAuth client primitives, not Cloudflare's server-side OAuth library. The private non-loopback HTTP callback cannot qualify this flow. The test needs a browser-reachable HTTPS origin or a browser-local loopback forward; changing the origin requires a fresh Connect ceremony. Prefer private HTTPS if supported. ### Testing-first architecture (revised proposal, 2026-09-10)

Define the observable invariants and executable simulation model before implementing the HTTP routes or UI. Run the **production** authorization coordinator, connection-scoped broker and runtime credential resolver against simulated effects; do not test a parallel toy implementation of the coordinator. Keep the existing MCP connection owner. Reuse `apps/control-plane/src/domain/broker.dst.test.ts` and `apps/orb-runtime/src/mcp/service.dst.test.ts` infrastructure, but add composed coverage: existing global-provider refresh tests and independent transport tests do not prove the project-connection contract.

**Small simulation boundary:** a transactional connection/attempt/pointer store, immutable versioned secret store, OAuth exchange/refresh port, runtime broker/HTTP ports, and injected clock/scheduler/entropy. Durable auth-edge writes participate in the state transaction where possible; secret/provider effects remain explicitly non-atomic. All first-party fallible methods return typed `Result`/`ResultAsync`. SDK discovery, crypto, HTTP, browser navigation and real timers stay at adapters. The SDK may implement protocol primitives, but must not secretly own the domain's refresh/retry lifecycle.

One composed harness has two control-plane instances with separate memory, two same-project orb resolvers, a foreign-project orb, an OAuth provider model and an MCP acceptance ledger. Restart drops an actor's memory but preserves stores and provider effects. The provider enforces single-use authorization codes, PKCE and resource/client binding; models rotating and retained refresh tokens; and records **acceptance separately from response delivery**. This makes response loss, cancellation and crashes after an upstream effect real schedules rather than generic pre-operation errors. The ledger counts accepted tool invocations by explicit operation ID, independently of client outcomes. Model/adapter contracts pin these semantics so an overly helpful fake cannot make broken production code pass.

| DST scenario | Required invariant / outcome |
| --- | --- |
| Concurrent near-expiry requests from two orbs and two control-plane instances | Healthy refresh coalesces once per stale generation; grants are published only after durable secret/pointer commit. Different connections and projects do not share tokens or serialize behind a global login lock. |
| Refresh pauses past lease expiry; another actor proceeds; old response arrives late | Only the current fenced owner can publish or invalidate a grant. A lease/CAS cannot fence an already-accepted remote rotation: model the possible lost credential and surface bounded reconnect-required, not an impossible exactly-once upstream guarantee. |
| Duplicate callbacks, denied/expired consent, two Connect attempts, callback after process restart | One code exchange owner per attempt; duplicate callbacks cannot exchange or publish twice. A newly initiated ceremony supersedes the previous pending ceremony. Expired/denied attempts terminate visibly. Successful completion on a different instance uses durable state, not the initiating process's memory. |
| Code exchange/refresh accepted, response lost; secret written, pointer not committed; pointer committed, acknowledgement lost | Read back authoritative state before treating a committed result as failure. Retry persistence of a still-held credential without repeating exchange/rotation. An irretrievably lost credential ends in a visible reconnect outcome; unreferenced secret versions remain enumerable for cleanup. |
| Callback or refresh races reconnect, auth-binding edit, Disconnect, connection/project deletion, or orb-incarnation retirement | No stale grant publication, no old failure clearing a newer grant, no resurrection, no cross-project vending. A token read authorized before the disconnect fence may finish; reads authorized after it fail. Previously cached access tokens are explicitly outside immediate revocation guarantees. |
| Access expiry/401 while MCP stays open; simultaneous stale rejections; insufficient scope; cancellation and lost tool response | Next explicit request uses a usable generation or returns a typed failure. No unbounded refresh loop, silent broader consent, leaked session, or automatic replay of an accepted tool operation. Reconnect authorization repairs the next explicit use without restarting the orb. |
| Provider/store outages, attempt expiry and deletion cleanup | Bounded completion, retryable outage distinct from invalid grant, no healthy-status spam. Required auth edges persist with state; failure/reconnect is visible through status/tool results. After failures cease and cleanup is driven, attempt/grant secrets are removed without deleting another connection's material. |

Place named scheduling checkpoints before/after attempt claim, upstream code consumption/refresh acceptance, secret write, pointer/status commit, token authorization/grant delivery, MCP acceptance, disconnect fence and cleanup. Failpoints distinguish failure-before-effect, effect-with-lost-response, and process death. Assert safety after every relevant mutation and bounded recovery only under explicit eventual-success assumptions. Use forced causal schedules for the critical races plus entropy exploration; timeouts are tested separately from ordinary success. No real sleeps, arbitrary stagger as a happens-before relation, or “retry until green.” Retain failure traces and replay with `DST_REPLAY` before changing product or model.

**Other test layers have separate jobs:**

- **Shared store contracts:** run identical attempt-claim, generation-CAS, project/deletion-fence, status-edge and cleanup ownership semantics against the simulation store, PGlite and PostgreSQL. ### Ownership and minimal contract

```text
Browser → control plane → provider consent → control-plane callback
Orb → control-plane token broker → access token only
Orb → MCP server directly (tools, streams, sessions)
```

- Add an immutable connection ID and an explicit static/OAuth auth discriminator to the catalog. Keep names for the tools' user-facing lookup. Non-Authorization header bindings can remain useful for provider project/site pinning; reject an explicit Authorization binding in OAuth mode.
- PostgreSQL owns connection identity, auth-relevant revision, approved resource/issuer/client/scopes, grant pointer/generation, and bounded login-attempt metadata. Secret storage owns tokens, client secrets and PKCE verifiers. Never put secrets in catalog responses, orb snapshots, history, or logs. A description/name edit need not invalidate consent; endpoint, issuer, client or auth-mode changes invalidate the old binding.
- Add one incarnation-authenticated token operation keyed by connection ID and expected auth revision. Derive project authority from the calling orb and recheck current connection/project ownership and deletion fences; never trust a caller-supplied project or token destination. Return only access token, expiry and generation. Do not extend the global `model | github` capability enum with arbitrary server names.
- Reuse the existing broker's secret-version pointers, leased refresh and generation fencing, adapting credential identity to project connections rather than copying its state machine. All orbs share one refresh owner per grant. Preserve an old refresh token when a successful refresh omits its replacement. No proactive fleet refresh daemon.
- Resolve credentials before each outbound MCP HTTP request, with an in-memory cache until shortly before expiry, not just at connection creation. Keep the SDK's protocol transport, but qualify its credential hook/fetch seam and hidden retries. The runtime cannot register clients, launch consent or hold refresh tokens. No credentials cross redirects or leave the approved resource boundary.
- A 401 invalidates the cached generation and permits one coalesced broker refresh for the next explicit operation; it does **not** replay the failed tool call. Timeouts and lost responses likewise never replay writes. Repeated rejection becomes visible reconnect-required rather than a refresh loop; insufficient scope requires human consent, not silent expansion.
- Disconnect/removal stops new broker grants and fences pending callbacks/refresh commits. Already-delivered access tokens remain usable until expiry or provider revocation: without a gateway, immediate revocation of every call is not a promise. Reconnecting the same binding replaces the grant generation without a catalog push.

Use the official MCP SDK's discovery/OAuth primitives behind narrow typed adapters, not a homegrown OAuth stack. Start with authorization code + PKCE S256, protected-resource/authorization-server discovery, and explicit resource binding. ### Protocol and storage rationale retained from the earlier proposal

Follow the [MCP authorization specification](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization), not a generic hard-coded OAuth endpoint:

- Discover protected-resource metadata from the challenge/well-known locations, then authorization-server/OIDC metadata. Validate issuer, resource identity, and scopes; bind grants to immutable connection ID, approved URL/resource, issuer and client identity, not a mutable display name.
- Browser authorization code + PKCE is the normal path. Device authorization is useful only for providers that actually offer it; existing Codex/GitHub device flows are not universal MCP login machinery.
- Client registration varies: pre-registered client where available, Client ID Metadata Document where supported, Dynamic Client Registration fallback where supported. Some providers require manually creating an OAuth application; arbitrary URL → one-click login cannot be promised universally.
- A metadata-document client needs a deliberately public, read-only HTTPS JSON endpoint reachable by authorization servers. The ordinary IAP-protected UI cannot serve that function. A browser redirect callback can be behind IAP because the human browser visits it, subject to validation that IAP preserves callback parameters/login continuation. Never put auth codes into application/access logs or third-party page resources; callback responses should be no-store with a restrictive referrer policy and redirect to a clean URL.
- Store non-secret catalog/connection revision/status/pointers in PostgreSQL. Refresh tokens, access tokens, static API keys, client secrets, and sensitive transient PKCE data use control-plane secret storage. Use the existing exact-version, generation-CAS and refresh-lease ideas, but generalize credential identity to arbitrary connections; today's `model | github` schema is not already an MCP broker.
- Persist bounded login-attempt state so a callback can land on another instance. Single-use state, expiry, browser/project binding, connection revision fences, duplicate callback handling, and reconnect/delete races are necessary. A stale login/refresh result must never resurrect a disabled/deleted connection or overwrite a newer grant.
- Multiple orbs must share **one refresh owner**, not each rotate the same refresh token. Preserve rotated refresh tokens and handle providers that omit a new refresh token. The existing upstream-rotation-before-durable-commit loss window remains: surface a reconnect request rather than claiming atomic OAuth refresh.
- `invalid_grant` becomes connection-level `auth_required`. Show a reconnect link without bouncing the orb. Scope escalation or a new issuer/endpoint requires human authorization, not an automatic broader grant.
- Workload identity (`docs/workload-identity.md`) is an alternative for a private MCP that explicitly trusts our issuer or federated cloud identity. It is not a substitute for user-delegated SaaS OAuth, and existing model/GitHub tokens must not be sent to arbitrary MCP endpoints.

## Revised recommendation: direct MCP, no gateway

User acceptance of orb-readable API keys removes the main motivation for a gateway. Selected architecture: **orb-side MCP client, project configuration and secret storage in the control plane**. The connection-scoped OAuth broker is implemented above (2026-09-10), pending deployment/live-provider qualification. Tool traffic, streams and session IDs stay in each orb. No cross-orb MCP session sharing, fleet connection reconciler, heartbeat supervisor, or live-config push system.

The gateway alternative would keep even static keys out of repository code and centrally deny new tool calls, but adds streaming, session routing, cancellation, multi-instance recovery and an extra network hop. It is no longer recommended given the clarified trust model. Disabling a configured static-key connection takes effect in a running orb on restart under the proposed snapshot contract; it cannot erase a previously delivered key. Immediate credential revocation requires revoking the key at the provider. OAuth disablement stops new broker grants, not already-issued tokens or in-flight side effects.

Reuse the existing project-secret bundle for static values. A project-owned revisioned catalog contains server name, short description, HTTPS URL and typed header bindings (the earlier separate connection ID/transport/enabled fields were unnecessary for this slice): a non-secret literal or a secret reference with an optional fixed `Bearer ` prefix. Do not store a credential copy in the catalog or implement arbitrary shell/templating evaluation. This supports Datadog's two headers as naturally as a single Authorization header. Resolve values into request headers in memory; do not generate secret-bearing `.mcp.json` files. Secret input happens in the write-only browser UI, not command arguments or chat.

Each connection belongs directly to a project, including any OAuth credential pointer and login attempts. There is no reusable account-wide credential object in the first design. Connecting the same service in two projects is two explicit connections, even if the human chooses to enter the same API key. Deletion follows project ownership and must clean OAuth credentials/attempts as well as the existing project's static-secret bundle.

**Static headers without OAuth is now the approved initial auth scope (2026-09-08).** Streamable HTTP remains the proposed transport: all three target services document static authentication. No OAuth client registration, callbacks or refresh state ships in this slice. The 2026-09-10 OAuth implementation adds a credential source for the same orb-side transport, not a separate data-plane architecture.

### Search, call and read

User decision (2026-09-08): discovery spans all kinds, execution belongs to `mcp_call`, and retrieval belongs to an additional `mcp_read`. The implemented parameter shapes are listed above; the interface rules are:

- `mcp_search` searches/lists typed entries: tools, prompts, resources and resource templates. **`kind` is optional; omitting it searches everything**, not just tools. Results carry `kind`, server identity, name or URI, description, and the relevant tool schema/prompt arguments/template. Support optional server filtering, bounded pagination, and exact lookup. Do not silently synthesize a universal JSON Schema for MCP prompt arguments; their metadata only specifies names, descriptions and requiredness, and `prompts/get` arguments are strings.
- `mcp_call` invokes `tools/call` only, using server/tool identity and schema-validated arguments. It does not retrieve prompts or resources.
- `mcp_read` retrieves prompts via `prompts/get`, resources via `resources/read`, and resource-template definitions via the discovered template catalog (`resources/templates/list` when discovery is needed). Reading a template returns its URI template and metadata; the agent can then supply an expanded concrete URI to read its resource. URI expansion follows standard URI-template semantics; a template is not itself a separate MCP read endpoint or a guessed filesystem path. Prompt arguments are optional where the selected prompt permits them. Retrieved prompts remain data, not automatically executed instructions.
- **Initial-prompt inventory (user requirement, 2026-09-08):** the extension lists each enabled MCP configured for the project with its name and short description. Pi already supplies the model with the three registered tools' descriptions and argument schemas; explain search/call/read semantics there, not in a redundant system-prompt legend. Beyond the one setup sentence in the shared runtime prompt, only the per-project server inventory needs additional prompt content. Store the short description with project connection metadata so the initial prompt does not depend on connecting to upstream servers or fetching their full instructions. Revised proposal (2026-09-08): during authenticated add/connection validation, fetch server metadata and prefill its optional description; let the human edit it before saving. If absent or unsuitable, accept a short setup-supplied description. MCP does not guarantee a concise description, and its optional `instructions` field can be lengthy executable guidance rather than a description; do not automatically inject that field or add a summarization model call. Save one bounded description with the connection, without background refresh machinery. Any setup-time remote fetch uses the same credential redaction and SSRF protections described below. Render a bounded, stable-order section additively to the existing system prompt without duplication on subsequent turns; omit the section when there are no configured MCPs. The inventory means configured availability, not a live health assertion. Do not inject credentials, URLs containing secrets, entire tool-name catalogs, or prompt/resource bodies.
- Teach the agent that search covers tools **and** prompt/resource metadata. The first slice returns matching entries and explicit per-server failures, not a separate server-health/status surface. A configured server in the initial prompt is not a live health claim, and an empty search is not proof that no dynamically addressable resource exists. A dedicated capability/count summary was rejected as unnecessary for this first slice; optional unsupported resource-list methods do not poison tool discovery.
- Retrieve content only when requested. A prompt comes back as a labeled tool result preserving its source and message-role metadata, **not** automatically injected as trusted system/user messages or executed as a new turn. This deliberately differs from the typical user-invoked slash-command UX; it makes prompts inspectable/adaptable by the agent without inventing a composer feature. Tool results and resource contents are external data, not higher-priority instructions.
- `resources/read` always goes through the selected MCP server with its normal credentials. An arbitrary resource URI is not authority for our client to fetch HTTP or read a local file directly. Follow-up linked resources require explicit retrieval, not recursive prefetching.
- Bound list pages, schemas, prompt bodies and resource contents using the same output guard. Preserve text/images and metadata; materialize supported binary blobs as private bounded files or return an explicit unsupported-content outcome. No Apps renderer, subscriptions, argument autocomplete or prompt slash-command UI initially.
- Contract/E2E fixtures include one tool, one argument-bearing prompt, one concrete resource and one resource template; prove cross-kind search when `kind` is omitted, filtered search, separate call/read routing, template-definition retrieval, empty/unsupported/failure visibility and no prompt role escalation. Pi contract tests verify that the very first model request contains each enabled server's name/short description exactly once, without requiring upstream connections or revealing credentials. These use the same connection and cancellation DST, not a second resource lifecycle machine.

### What the existing script mode does

`pi-mcp-adapter` exposes a separate default-on `mcpScript` tool. The model supplies JavaScript that can search/describe/call MCP tools, loop, filter intermediate responses, compose dependent calls or run `Promise.all`, and return a compact result. The extension executes it in the orb/client process using a worker thread, with a default 30-second deadline; cancellation/approval/output guards still apply. Its documented API returns `{ ok, data/error }` for calls and allows explicit `emit` output. It is not a security sandbox, not a durable workflow engine, and not a rollback/transaction mechanism. A script interrupted after a write can leave partial effects.

Its benefit is fewer model round trips and avoiding huge intermediate outputs in model context; its costs are an additional code-execution surface, call scheduling/cancellation ownership, and harder diagnosis of partial writes. **Recommendation: do not implement scripting initially.** Cloudflare `execute` already performs code execution on Cloudflare's server, and PostHog `exec` already offers a compact server-side command interface; both are callable via ordinary `mcp_call`. Neither requires a client-side JavaScript runner in our extension. Cross-server scripting can be considered only after an observed need.

### Claude Code comparison (public docs inspected 2026-09-08)

Source: [Claude Code MCP documentation](https://code.claude.com/docs/en/mcp#scale-with-mcp-tool-search). This is documented behavior, not inspection of Claude Code's private implementation or a captured model request.

- Current docs say tool search is **on by default**: tool names and server instructions load initially, while full definitions are deferred. `ToolSearch` makes selected schemas available as native tools using the provider's `tool_reference` mechanism; Claude then calls the actual MCP tool, rather than passing arbitrary arguments through one generic call tool. Consequently the initial name inventory still scales with tool count.
- `ENABLE_TOOL_SEARCH=auto` uses the 10%-of-context threshold; it is a selectable mode, **not the current documented default**. `auto:N`, forced enable/disable and per-server `alwaysLoad` are supported. Provider/model/proxy incompatibilities can require upfront schemas. These details have changed over time; do not perpetuate an older default as a current fact.
- Resource @ mentions retrieve resources as attachments, and Claude Code provides list/read tools when resources are supported. MCP prompts become slash commands (current display `/server:prompt`, also `/mcp__server__prompt`) whose results are injected into the conversation when invoked.
- Our selected interface takes the simpler provider-independent route: fixed search/call/read definitions; selected schemas arrive as ordinary tool-result content and are validated by our bridge before calls. No dependency on native deferred-tool protocol support, dynamic registration or a terminal slash-command UI. Search descriptions need to tell the model how to obtain the schemas; server inventories/instructions and returned results must remain bounded.

### Minimum runtime and consistency model

- Fetch a complete project-owned catalog at boot, then resolve its secret references against the existing boot secret snapshot. A referenced missing secret is a visible connection-specific configuration error, never an unauthenticated fallback. Defer enabling a newly configured connection until required secret writes have succeeded. A boot racing configuration/secret updates may see a missing binding and require a later restart; first cut need not add a distributed transaction across stores to hide this bounded race.
- A failed authoritative snapshot read must be reported as unavailable, not as an empty successful catalog. An individual upstream outage must not block ordinary coding or other MCP connections. Project-secret-store failures retain the existing readiness contract in `docs/credentials.md`.
- Fixed search/call/read tools keep the agent interface small. Sessions and a bounded in-memory tool catalog are owned by one runtime. Lazy connection uses per-connection singleflight; concurrent calls must not initialize competing sessions. Disconnect/reconnect on explicit use rather than running health checks while idle.
- Own operation deadlines, abort/close ordering, limited reconnect policy and status edges behind injected ports. Do not automatically replay an ambiguously executed tool call. Reconnect can repair a session for the next explicit attempt; it cannot prove that a previous write did not happen. Provider write annotations are hints, not sufficient proof for retries.
- **Own extension selected by the user (2026-09-08).** Use a small platform-owned Pi tool bridge over the official MCP SDK, with third-party protocol behavior tested at a narrow adapter boundary. The earlier off-the-shelf option was useful qualification evidence, but its real timers, backoff, caches and shutdown behavior would import an autonomous management subsystem we do not need. Reuse MCP protocol implementation, not terminal management panels or an entire extension lifecycle framework. Proposed first-party composition is documented in `docs/pi-adapter.md`.

Rejected as the intended product design: copying `.mcp.json` plus keyring/token files between orbs (wrong ownership and refresh races), guest-local callback/manual code pasting through conversation (secret/history exposure and avoidable friction), or implementing all Pi terminal UI just to add a server (browser setup link is sufficient).

## Safety, observability, and qualification

These are broader qualification constraints. OAuth-specific statements are future context, not shipped states or an implementation backlog. The first-slice behavior and narrower observability contract are specified above:

- Treat server metadata, tool descriptions and outputs as untrusted external content. Enabling project-wide MCP grants every orb/repository execution in that project the capability; OAuth consent is not per-tool approval. Keep the ability to disable connections and restrict capabilities explicit.
- Control-plane fetching introduces SSRF via the supplied URL, metadata, registration/token endpoints, and redirects. A public-HTTPS-first policy should reject userinfo/token-bearing URLs and private, loopback, link-local and cloud-metadata destinations, revalidate redirects/resolved addresses, and prevent DNS rebinding. Approved private endpoints require an explicit network policy, not turning validation off globally. Never forward credentials across an unapproved redirect/resource boundary.
- Durable queryable **edges**: proposal created/approved, login completed/failed/expired, credential invalidated, enabled/disabled, and a changed connection failure/recovery. Include connection ID/revision, originating orb, safe error code and operation correlation; no headers, tokens, callback query strings, or arbitrary remote error bodies. Runtime-only status events or temp trace files are not sufficient field observability. Healthy catalog/token reads log nothing.
- User sees pending authorization, usable, unavailable, or reconnect-required states. Tool failures name the connection and offer a safe setup/reconnect link; they must not silently disappear from discovery. OAuth connection status is distinct from a particular orb's MCP transport status.
- Qualification uses pinned-package contract tests plus a fake MCP/OAuth provider: initialize/list/call, output guards, cancellation, required approval without UI, lost streams, session expiry, token expiry while a connection remains open, auth-required, and catalog changes. Never automatically replay a possibly executed write on timeout or unknown outcome.
- **DST is a design input, not a test layer added later.** Domain services take simulation-friendly catalog/secret stores, MCP transport, credential resolver, clock/scheduler and status-event sink. First-party methods return typed `Result`/`ResultAsync`; immediate SDK/network adapters catch third-party exceptions. Any Pi-required exception is confined to the documented tool adapter.
- Keep the initial DST matrix small and invariant-focused: (1) catalog mutations versus snapshot reads/project deletion, asserting caller-project isolation, monotonic revisions and no post-delete publication; (2) simultaneous lazy connects versus abort/shutdown, asserting one owner, no leaked live clients, no late result publication and cleanup before close completes; (3) connection loss before/after tool acceptance, asserting no ambiguous write replay and an explicit user-visible outcome. Inject scheduling checkpoints around acquisition, connection, call completion and cleanup; inject failpoints at persistence/transport boundaries and retain replay traces. Existing project-secret DST owns bundle rotation/crash cases rather than duplicating them in MCP tests.
- When OAuth lands, add broker DST for concurrent refresh/login, duplicate callbacks, abandoned/expired attempts, crash before credential commit, and project/connection deletion racing refresh. Neither real SDK timers nor network sleeps belong inside these domain simulations; pinned-SDK transport contracts separately qualify the boundary.
- Before runtime changes ship, the required full E2E must prove: configure a connection for project P → orb A calls the fake HTTP MCP → new orb B in P uses it with no setup → orb C in another project neither discovers it nor receives its secrets. Cover restart-applied static-key rotation/removal, multiple auth headers, cancellation, unavailable server visibility and project deletion, with no credentials in transcript or browser reads. Real HTTP fixtures use assigned ports and explicit synchronization, not time-based readiness guesses. When OAuth ships, extend this to orb proposal → browser authorization → new same-project orb reuse → refresh/reconnect/disable. Live provider tests additionally qualify redirect registration, IAP behavior, discovery quirks, token lifetime, and provider restrictions.
