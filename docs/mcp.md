# Remote MCP

Pi's MCP tools run centrally through scoped Durable callables and request-time broker credentials. Native Claude uses a query-owned bridge on its execution host. Project configuration and OAuth authority remain control-plane-owned; neither harness owns refresh tokens.

## Historical native qualification

**Decision (2026-09-29; deployed 2026-10-02):** Pi 0.99.1 native MCP replaces the pi-orb-owned search/call/read bridge and connection manager outright. Native MCP and tool-search factories are installed in root and child sessions. Codemode is always on, even with an empty catalog, within each session's approved tools. Project configuration, static secret references, control-plane OAuth and direct orb→server transport remain. Local unit/infra, full Docker/browser, fresh native-image SDK probes and live provider reads passed. Dedicated-grant browser consent and real 401/refresh recovery also passed. Initial-auth rediscovery passed against real dedicated grants in an isolated Pi 0.99.1 SDK session; remaining acceptance boundaries are tracked in `TODO.md`. Production release `2db5225` passed all twelve release gates, including fresh native-image acceptance and lifecycle/identity smokes ([Deploy 36960393737](https://github.com/schani/pi-orb/actions/runs/36960393737)). General-purpose MCP access is included; explicitly restricted profiles remain restricted. Existing running orbs receive the new runtime through the normal stopped-compute replacement path.

**Qualification boundary:** scope observation and authenticated context measurement are separate from full GCE/browser acceptance. Synthetic observer tests qualify wiring and redaction, not provider authorization. The dated results, failed artifacts, independent baselines and explicit-child limits are in `docs/postmortems/2026-10-01-mcp-measurement-fixtures.md`; remaining provider acceptance is in `TODO.md`.

## Project configuration and authority

**Dependency security update (2026-10-07; not deployed):** control-plane OAuth and description probes use `@modelcontextprotocol/client@2.2.0`, which fixes OAuth credential forwarding to an MCP-server-selected authorization server ([GHSA-6qxp-vccf-f47h](https://github.com/advisories/GHSA-6qxp-vccf-f47h)). Pi uses its native MCP transport; Claude's OAuth bridge uses `@modelcontextprotocol/sdk@1.32.0`.

A project owns its revisioned catalog (at most 20 servers, 16 headers/server), not an account-wide set. Its Config → MCPs tab saves name, bounded description, HTTPS endpoint and OAuth or static secret references; Secrets owns key values. Custom headers remain supported through the API, although the narrow editor refuses to alter configurations it cannot represent. Presets cover PostHog bearer auth and Cloudflare/Datadog US5 OAuth. Catalog publication and secret removal share the project row lock: referenced secrets cannot be deleted; replacing a secret is allowed. Browser configuration changes apply on the next runtime start; OAuth reauthorization for an existing connection works without restarting. The short name/description inventory is appended to the agent context without connecting to servers or claiming they are healthy; the shared environment prompt directs setup to the project gear.

`GET /api/v1/projects/:projectId/mcp` returns `{revision, servers}`; `PUT` replaces the catalog with an expected revision. `GET /runtime/v1/mcp` uses the orb incarnation bearer and derives its project. Runtime boot resolves static bindings against its project-secret snapshot; missing authoritative snapshots fail readiness, not become an empty catalog. Control-plane description inspection is restricted to public HTTPS with socket-time DNS checks, disabled redirects, and no userinfo or fragments. The orb may connect to an approved private endpoint: allowing project code to reach one does not grant the control plane a private-network fetch primitive. No live catalog push, shared MCP session, gateway or fleet connection supervisor is introduced.

OAuth catalog entries carry immutable project/URL-bound `oauth: {id}`. Browser `GET .../mcp/:id/oauth` reports `connected | pending | auth_required`; `POST .../oauth/connect` returns `{url}` and `POST .../oauth/disconnect` returns `{status:"auth_required"}`. The stable `${PI_ORB_APP_ORIGIN}/api/v1/mcp/oauth/callback` exchanges authorization codes in the control plane and returns to the project's MCP tab. State, browser nonce, PKCE and single-use exchange ownership are fenced and time-limited. OAuth tokens, client secrets and verifiers belong to immutable control-plane secret versions, never project-secret snapshots, repository files, guest OAuth storage, browser reads or history. Catalog removal/auth-mode or URL replacement retires the grant; an old callback/refresh cannot resurrect it. Transactional `mcp_oauth_events` record safe consent, invalidation and refresh edges; `mcp_oauth_garbage` owns exact-version cleanup. The broker reuses leased refresh and generation CAS; refresh accepted upstream before a lost response is not recoverably atomic and can require new consent. `POST /runtime/v1/mcp/:id/token` accepts `{url, rejectedGeneration?}` and returns `{accessToken, expiresAt, generation}` after checking incarnation and current catalog ownership. Previously issued access tokens survive disconnect until expiry/provider revocation. This route does not expand the global model/GitHub broker capability enum.

Initial registration uses advertised dynamic client registration and authorization code + S256 PKCE. Discovery/registration/token requests use public HTTPS, socket-time DNS validation, disabled redirects, ten-second deadline and 1 MiB response cap. Callback headers disable storage/referrers; callback URLs must not reach ingress logs. Migration 018 and deployed logging exclusion are described in `docs/credentials.md` and `docs/postmortems/2026-09-11-release-logging-exclusion-iam.md`. Migration 026 adds safe `mcp_oauth_events.detail`: closed diagnostics (`invalid_grant`, `invalid_client`, `missing_refresh_token`, `unusable_refresh_response`) and bounded lifetime/rotation metadata, never remote bodies or credentials (`docs/postmortems/2026-09-26-provider-auth-failures.md`).

## MCP SDK security (2026-10-06; candidate, undeployed)

**Decision:** pin control-plane and runtime `@modelcontextprotocol/client` to2.2.0, with its exact core2.2.0, for [GHSA-6qxp-vccf-f47h](https://github.com/advisories/GHSA-6qxp-vccf-f47h). No other SDK version or sealed patch changes. Pristine2.0.0 contracts reproduce credential forwarding to an attacker-selected token endpoint and loss of issuer stamps during schema round trips;2.2.0 rejects mismatched stamped credentials before any token request and preserves stamps.

The control plane's direct exchange/refresh is not automatically protected by this upstream fix: persisted issuer, token endpoint and resource remain authoritative, without rediscovery. Regression contracts change discovery after preparation and require typed, sanitized issuer rejection with zero token requests. Production native Pi's tokenless broker transport independently ignores malicious challenge metadata: two original-server requests, two broker generations, zero attacker requests. Automatic SDK credential forwarding is not demonstrated reachable through these production paths; no deployed exposure or rotation conclusion follows. Existing OAuth/status history supplies durable sanitized outcomes; challenge text and credentials remain excluded. Scoped clean-install qualification passes99 MCP/security cases, workspace/E2E types and audit0, with all seals unchanged. Fresh browser/image/whole-source gates remain pending (`docs/testing.md`). Evidence: `/workspace/durable-github-qualification/diagnosis/mcp-upgrade-fix.md`.

## Central Pi boundary

`McpTools` uses native `@earendil-works/pi-mcp` clients behind typed scoped endpoints. Discovery registers canonical `mcp__server__tool` names, original JSON Schemas and server instructions/resources in the callable catalog. Root/child models expose only codemode; their authorized internal catalog controls nested calls (`docs/pi-adapter.md`). Resource URIs are interpreted by the selected MCP server, not an arbitrary filesystem/HTTP reader.

**Decision (2026-10-25):** validate each endpoint's complete tool batch before registering tools or resource access. Raw callable names and native code-mode identifiers must be unique within the batch and against shared catalog occupancy, including hidden entries. Serial discovery keeps the incumbent and rejects the later conflicting endpoint through the existing sanitized unavailable status and durable status-change publisher; unrelated endpoints continue. Exact re-registration of the same endpoint/upstream tool is allowed after transient failure. Changed aliases cannot take identifiers retained by cached callables. No automatic renaming or global catalog rejection.

Local in-memory MCP/native Harness regressions reproduce normalized-name code-mode failure and delimiter-name wrong-endpoint dispatch, then verify both discovery orders, whole-batch rejection, hidden incumbents, corrected responses and cached-tool recovery with endpoint-specific call counters. These synthetic cases do not establish a production incident or qualify browser/provider behavior; full-suite/E2E and release gates remain separate.

Validate original arguments against the raw server schema before native coercion, preparation, authorization, credentials or effects. Explicit null remains null; only omitted arguments default to `{}`. Preserve structured arrays/null in results. Invalid arguments receive a sanitized rejection, not remote/input text.

**Decision (2026-10-21):** preserve argument shape when oversized property descriptions exhaust the declaration budget: after the existing tag-free attempt, retry without descriptions, then fall back to `unknown`. This last fallback omits semantic instructions in comments; types, requiredness, references and caps remain unchanged. On native `invalid_arguments`, derive only missing top-level required names from the callable catalog, never native/remote diagnostic text or argument values. Quote names; bound them to 64 characters, 16 names and 1,024 characters of name text. Other validation failures remain generic; this is not a nested schema validator. Existing durable tool results retain the user-visible explanation.

Check the authenticated live schema before blaming credentials for argument rejection. PostHog `exec` required `command`, `context`, and `llm_model`; corrected help succeeded. Live discovery does not prove the historical process-cached schema. Evidence and limitations: `docs/postmortems/2026-10-21-posthog-exec-required-context.md`.

**Decision (2026-10-22):** MCP discovery starts automatically after native root/projection initialization and final admission, immediately before Harness resume. One context-owned background job publishes each server's result independently; neither startup nor unrelated code-mode preflight awaits it. The resource lease, not the incoming startup deadline, owns discovery. Revocation aborts it before Harness shutdown; resource close joins discovery and notifications even when cleanup fails. Local configuration reads and owner/admission checks remain fail-closed.

Configured namespaces exist immediately with pending descriptions. The real `mcp_status` description includes configured names, namespaces, descriptions and cached states, so native search can find a provider before tools arrive. `mcp_status({})` always returns cached progress immediately and starts/shares a background retry of failed servers after connectivity/consent changes. Cancelling its script does not cancel the context-owned job. Available schemas remain cached. Each endpoint publication rebuilds the bundle/registry; the next script's local preflight makes its tools callable without a status invocation or a new conversation/child.

Discovery remains serial and failure-tolerant. The SDK's 30-second timeout applies per JSON-RPC request, not the whole operation; pagination, OAuth and cleanup may extend it. No shared deadline or concurrency policy is added. Caller and transport HTTP signals are combined so cleanup retains its SDK timeout. Rejected: discovery triggered only by `mcp_status`; it hides configured tools and depends on model choice. See `docs/postmortems/2026-10-22-mcp-startup-deadline.md`.

Each invocation owns a native client and cancellable transport, resolves approved credentials afresh and joins cleanup. Failed optional servers do not block unrelated inference. Tool-call replay remains governed by native safety/admission rules; cancellation cannot undo accepted remote work. No refresh token or guest consent store.

Request-time broker fetch preserves generation fencing and bounded refresh. Reject redirects and sanitize non-success bodies; never persist headers, token values, challenge text or credential-bearing URLs. Native invalid-session recovery is distinct from unsupported optional JSON-RPC methods (`docs/pi-adapter.md`). MCP tools/resources are untrusted data; sampling, elicitation and MCP Apps do not automatically acquire browser interactions. Native prompts are not a product requirement.

## Claude POC boundary

**Local implementation (2026-10-04; not deployed):** control-plane project MCP configuration also feeds the co-located Claude SDK 0.3.289. Static URL/header bindings map directly to public `Options.mcpServers` HTTP entries. OAuth entries use public in-process `McpSdkServerConfigWithInstance` and the MCP SDK's raw request handlers; they forward tools, resources and prompts through a client using the existing request-time broker fetch and credential resolver. `tools/list` forwards native JSON Schema without converting it to a permissive Zod shape. This bridge introduces neither guest OAuth login/storage nor a new network service.

Each query owns its OAuth bridge. Query teardown closes both MCP ends, cancels request transport and awaits admitted operations; the next query creates fresh clients. Native Claude task ownership remains the aggregate-activity input. Safe connection/auth failure and recovery edges use the existing coalesced publisher and must enter the root's durable history. Native repository/CLI MCP configuration remains separate and available through Claude's selected settings sources. Dynamic upstream list-change notifications, sampling and elicitation are not forwarded by this bridge; fake-client contracts establish schema, credential refresh and cleanup behavior, not provider or native-child qualification.

## Visibility and replication

Discovery failures retain `durable.mcp_unavailable` lifecycle events with server, active phase, phase elapsed time, abort status, allowlisted SDK category and HTTP status/request timeout where available. No raw errors or credentials. Discovery and invocation failure/recovery edges share one publisher, appending native `orb.alert` entries without model input or a new turn. A separate cached MCP system section reuses the prompt section's `GenerationTask.beforeRequest` refresh for root/child requests, including requests prepared before discovery finished. Alert-publication failure records `durable.mcp_alert_failed` and does not stop later discovery. `mcp_status` returns sanitized results. Claude's query-owned edge publisher persists safe failures/recovery through root history. Healthy connections and repeated levels are silent; prompts, tokens and raw remote errors stay private.

Root/child native tasks retain authorized-call ownership and cancellation. Public nested summaries expose only committed parent-result details, not private child transcripts.

The codemode parent `tool_result` contains a bounded typed nested-call summary. Its disclosure shows child tool inputs, status, sanitized error, duration and available summary; it does **not** manufacture full child results. Incomplete or filtered summaries state that limit explicitly. Transient nested events are excluded from root live-tools projection; only committed parent summary is rendered. This keeps live and replicated views consistent without a separate child-history endpoint (`docs/pi-adapter.md`, `docs/web-ui.md`).

## Evidence, rejected alternatives and release boundary

**Fixture ownership decision (2026-10-08):** MCP E2E excludes desktop notifications. Best-effort asynchronous Luna summaries must neither gate MCP assertions nor consume the root/child mock's forward-only script. The test-owned HTTPS fixture routes only the exact summary system prompt and anchored user envelope to a repeatable local Responses SSE answer; ordinary inference, including Luna child turns, retains upstream bytes and authentication. No production summary switch or external mock change is needed. Deterministic tests cover absent/early/late/repeated summaries, held root inference, compressed forwarding and the real Luna SDK parser.

**Failure evidence (2026-10-08):** sanitized MCP E2E summaries use `test-failures/mcp-<uuid>.json`, included by CI/E2E's existing artifact glob and Deploy's failure-only `mcp-*.json` allowlist (14-day retention). Failure metadata includes content-free inference route counts. Retain mock ledgers before their 24-hour expiry; a missing summary request is not a matcher failure. The historical absence remains unexplained; requiring that optional request was independently an invalid test contract (`docs/postmortems/2026-10-08-mcp-summary-missing-request.md`).

The 2026-09-08 first slice used `@modelcontextprotocol/client@2.0.0`, lazy per-server connections and three fixed `mcp_search`, `mcp_call`, `mcp_read` tools, including prompt retrieval. That interface was chosen over direct schema exposure and scripting to bound context. Pi's native search/deferred tools and codemode now own that job; retaining both would duplicate discovery and connection ownership. `pi-mcp-adapter` 2.32.1 proved headless lifecycle binding, but its guest keyring/OAuth owner was unsuitable; `pi-mcp-extension` persisted guest credentials, and `@nklisch/pi-mcp-adapter` added more source-management machinery than boot snapshots need. A gateway was rejected after the user accepted project keys readable in the orb: it would add streaming/session routing, cancellation and recovery merely to hide keys from already-authorized project code. Static-key revocation still requires upstream provider revocation; OAuth disable stops new broker grants, not already-issued tokens. In-orb pending-proposal/CLI setup was rejected for this slice in favor of the project gear. These are historical reasons, not supported runtime interfaces.

The testing contract separates DST for broker authorization, generation fencing, lost writes and lifecycle races from installed-SDK transport/auth contracts, browser/runtime E2E and actual provider-account qualification (`docs/testing.md`). Unit contracts cover composition activation/HTTP publication/close, native alert binding, shared-section request refresh and tool retry ownership once each; browser E2E owns cross-layer presentation. Fake HTTPS success is not provider qualification. Historical transport/auth/session characterization is retained in `docs/references/native-mcp-qualification.md`; scope/context qualification is in `docs/postmortems/2026-10-01-mcp-measurement-fixtures.md`.

Historical Pi 0.99.1 live discovery, reads, real 401 recovery and same-session initial-auth rediscovery are recorded in `docs/postmortems/2026-09-30-native-mcp-qualification.md`. Human IAP-cookie-removal continuation, shared provider-UI revocation/reconnection, restored GlideOS reads and authenticated scope/context measurements are recorded there and in `docs/postmortems/2026-10-01-mcp-measurement-fixtures.md`. These results do not qualify later SDK upgrades, natural IAP expiry/password-MFA, isolated downstream-grant revocation or full native PiOrbAgent/browser initial-auth recovery. Remaining acceptance is in `TODO.md`.

**Status decision (2026-10-01):** the workbench renders API `connected` as **grant stored**: the status checks for a persisted OAuth secret version, not current upstream access. A stored MCP grant and successful discovery do not establish usable upstream-service authorization; the Cloudflare experiment demonstrated that distinction. Arbitrary tool errors are not grounds for OAuth invalidation or call replay. The negative probe retained no HTTP error code, so it does not establish a particular 401/403 or token-refresh failure.
