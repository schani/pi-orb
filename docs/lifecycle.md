# Orb lifecycle

## Claude uncertain-worker recovery

**Decided and implemented locally — 2026-10-06; undeployed.** An answered failed pull/delivery triggers a typed health inspection; reachability is not readiness. Only Claude's exact `claude_child_recovery_required` plus a valid opaque ownership episode authorizes one automatic whole-compute replacement. Other failed health remains terminal; local disposition I/O failure grants no recovery authority.

A state-version CAS claims the episode, enters `starting`, revokes the old runtime bearer and creates the existing incarnation-bounded discard intent. The retained `claude_recovery` JSON stores claimed episode identities and current disposed/replacement incarnations. Each episode can be claimed once across controller restarts and later episodes; repeated ownership fails visibly with exhaustion. Sleep and stale deployment generations decline the claim; Stop/archive/delete win through the existing state/version fences.

Shared reconciliation verifies `discardCompute` before finalization marks proof verified and advances incarnation. Provisioning then carries only that episode's verified proof for its replacement incarnation. No normal Stop/history-drain barrier or same-VM restart is used. Docker/GCE advertise whole-compute disposal; an unsandboxed process group cannot prove escaped-worker loss and does not authorize this recovery. Queued inbox UUIDs wait for canonical receipt replication before redelivery.

Lifecycle edges are `claude-recovery-claimed`, `claude-recovery-disposal-failed`, `claude-recovery-disposal-verified`, `claude-recovery-ready` and `claude-recovery-exhausted`, carrying reason, episode and incarnation only. Durable claim/error/proof columns reconstruct crash cuts. Healthy reconciliation is silent; interrupted work remains visible in native history. No automatic inference/tool replay or new UI status is introduced.


Orb states, reconciliation rules, idle auto-stop, and the orphan-host sweep. The host operations these rules drive are specified in `docs/host-provider.md`.

## Decisions

- **Incident rule (2026-10-04):** correlate guest shutdown admission, provider audit and durable lifecycle edges before attributing a restart to an extension error. Two scoped Spot preemptions preceded secondary loadout errors; they do not explain every prior restart. Preserve replay/admission fences when restoring services and distinguish interrupted checks from completed qualification. Evidence: `docs/postmortems/2026-10-04-spot-preemption-loadout.md`.

- We will implement stop/start and full restart recovery.
- We will not implement suspend/resume initially.
- **Decided 2026-09-17; implementation in progress, DST/tests first:** `pi-orb sleep <duration>` reuses controlled stop/start, the aggregate-work/upload/inbox drain, and a durable deadline. Due stopped sleeps wake through a source-aware system inbox notice combined into the first normal wake inference. Accepted commands and actual human input cancel; delayed upload notifications do not. No RAM suspend or new provider state. Full state, fence, expiry, failure, and cancellation contract: `docs/orb-sleep.md`.
- The runtime should report health and busy/idle activity to the control plane.
- The control plane distinguishes an idle but healthy runtime from an unhealthy runtime. Failed health checks can lead to restart. The first vertical slice stopped only on explicit requests; idle auto-stop is now a decided design (below).
- Initial lifecycle constants are a 5-second readiness health poll during create/start, a 30-second unreachable-runtime grace period, and a 15-minute create/start deadline; all use injectable clocks and may be tuned later. While an orb is `running`, the ~10-second history pull doubles as the liveness signal, so no separate health poll runs.
- Aggregate agent ownership, not a root-result/settled edge, supplies busy state. Native Durable children and Claude task/handoff holds remain busy through owned cleanup and durable publication (`docs/subagents.md`, `docs/claude-agent-sdk.md`).
- Arbitrary detached descendants are not active agent work after their launching invocation returns. A shell/SDK task registry cannot prove that all external processes ended; OS process inspection remains the separate question in `docs/open-questions.md`.

**Decided — compute incarnations are immutable; failed state invalidates compute, not the workspace (2026-08-12; implementation plan in `docs/compute-replacement.md`):** every terminal transition to `failed` durably requests disposal of the current compute incarnation while retaining the authoritative workspace and replicated history. The orb remains failed and consumes no replacement compute after cleanup. A later explicit Start or current-failure queued-message wake waits for disposal to be verified, then provisions a higher-incarnation clean VM/container/process on the retained workspace with a fresh runtime token. This is deliberately broader than `runtime_never_answered`: deterministic repository, configuration, integrity, or artifact failures may repeat on clean compute, but only after user/wake intent and never in an autonomous reprovision loop. Host updates use the same replacement mechanism instead of `ensureCurrentScript`-style mutation: a healthy running orb is untouched, while its next Start compares the immutable host-spec fingerprint — forward-only fenced by the committed deploy generation, so a draining stale revision cannot replace newer-spec compute — and replaces stale stopped compute before booting. Incarnation-bounded cleanup and incarnation-specific compute names prevent a late or stale delete from reaching a replacement. **Stage 1 implemented 2026-08-12:** every failure path uses the atomic failure/discard operation, shared reconciliation gates all non-deleting states on verified disposal, and start/wake provisions the advanced incarnation. Discard finalization deliberately does not bump `state_version`: it is preparation inside the same failure episode, so a wake admitted while cleanup is pending remains authorized; only `failed -> starting` consumes its one shot (`failed-wake-during-disposal` DST). Archival finishes disposal, provisions a clean incarnation when needed to read the retained workspace, seals history, then performs deletion-grade cleanup (`archive-failed-compute` DST). Durable discard errors drive both user detail and recovered-edge logging across control-plane restart. **Stage 2 implemented 2026-08-16:** providers stamp immutable host-spec fingerprints, the ordinary start path creates forward-only generation-fenced replacement intent for stale stopped compute, and the GCE in-place script/metadata repair machinery is gone (`docs/compute-replacement.md`).

**Decided and implemented — message-driven startup (2026-08-10, reshaped 2026-08-11):** the durable send-anytime inbox in `docs/runtime-protocol.md` reuses `starting` rather than adding a queued/waking lifecycle state. Inbox insertion and wake intent are transactional. From `stopped` or recoverable `failed`, send enters the ordinary start path; during `creating`/`starting`/`running` it only wakes reconciliation/dispatch; during `stopping` it records restart-after-stop and never bypasses the drain. An explicit stop ordered after the send clears the message wake but preserves the queued content, while a send ordered after stop sets the wake. A terminal boot failure leaves both the existing orb failure and the queued message visible rather than retrying forever. Accepted message insertion refreshes `last_busy_at`, so idle auto-stop cannot win immediately after user work arrives. The autonomous transition uses reason `queued_message` and edge logs include the message ID without content.

**Decided and implemented — there is exactly one message-driven transition (2026-08-11; explicit-Start wake corrected 2026-09-07):** admission (`enqueueOrbMessage`) records the message row, its wake intent, and `last_busy_at`; it performs **no** lifecycle transition. Until this change, admission carried its own inline `stopped`/`failed` → `starting` write — a second state machine in raw SQL, duplicated in the in-memory store, whose `transition` event was logged by the HTTP route and therefore existed only for HTTP callers. Now the per-orb reconciler's terminal backstop performs the transition through `casStartOrbForQueuedMessage`, the same single store transaction that already woke `stopped` orbs, and logs the `transition` edge itself, for every caller. Wake latency stays at one reconciler tick because admission and explicit Start set the orb's next reconcile attempt to *now*; the 30-second terminal backstop interval only bounds a wake whose nudge was lost with the process. An E2E caught explicit Start inheriting a stopped-orb deadline after control-plane restart (`docs/postmortems/2026-09-07-explicit-start-terminal-backstop.md`). **Correction (2026-10-15):** central agents have a second message-driven wake: `reconcileCentralAgent` moves a `failed` orb to `starting` through the same `casStartOrbForQueuedMessage`, logging the same `transition` edge, before central publication can retire the inbox row.

The rule that made this possible without giving up either half of the failed-orb contract is a **wake class carried by the intent**: each intent records `wake_state_version`, the orb `state_version` it was admitted against.

- A `stopped` orb wakes for **any** outstanding intent, whatever version it names — the standing, retryable intent of the 2026-08-10 decision below, unchanged.
- A `failed` orb wakes only for an intent naming its **current** `state_version`, i.e. a send the user made against the failure they are looking at. The wake bumps that version, so the same intent can never wake the orb again: a boot that fails afresh is not retried by the message that caused it, and a stranded intent from an older failure is inert. A new send is new user intent and buys exactly one further attempt.

This keeps "a send to a failed orb starts it" (previously the raw-SQL transition's job) and "terminal boot failure is not retried forever" simultaneously, with no second write to strand: the retirement of a failed-wake is the transition's own version bump, inside the same transaction. DST: `failed-orb-send-wakes`, `failed-orb-wake-is-one-shot`. Residual, accepted at POC scale: a stop and a send that genuinely overlap on a `failed` orb may linearize either way, because the stop's intent clear and its transition are two writes (see the clear-before-transition rule below); a stop *sequenced after* an admitted send is still final.

**Decided and implemented — how the inbox interacts with the rest of the reconciler (2026-08-10, from the five defects in the review of the first implementation; DST scenarios named below in `lifecycle.dst.test.ts`):**

- **The wake rule reads *any* outstanding wake intent, not the head of the FIFO.** The terminal backstop starts a `stopped` orb when any `queued`/`delivering` message carries `auto_start`, whatever its position: FIFO decides delivery order, never whether the orb comes up. Reading only the oldest message left an orb stopped forever whenever an older undelivered message preceded the one queued during `stopping` (`backstop-honors-any-wake-message`).
- **The wake decision and the transition are one store transaction** (`casStartOrbForQueuedMessage`), and the wake deliberately does **not** clear the intent. The intent stands until the message is delivered, failed, or explicitly stopped, so the wake is naturally retryable and has no second write that a store blip can strand — the failure mode that let a stale `auto_start` resurrect an explicitly stopped orb (`stale-wake-intent-resurrection`).
- **`failed` does not wake for a standing intent.** A persistent wake intent plus a host that cannot boot is an unbounded provision loop, so an intent that has already had its attempt never gets another — the "terminal boot failure is not retried forever" rule above. Originally this was implemented as "the backstop wakes `stopped` only", with a send arriving *at* a `failed` orb entering the start path through admission's own inline transition; since 2026-08-11 both halves live in the backstop, separated by the intent's `wake_state_version` (above).
- **Accepted Stop atomically cancels all timer and wake authority in every lifecycle state (decided 2026-09-17).** Cancellation and any lifecycle transition are one store operation. Success confirms cancellation of earlier timer/wake authority. Transaction failure rolls back its changes; lost commit acknowledgement returns an error with an unknown outcome. An already-`stopping` or `stopped` Stop may therefore perform a real cancellation and is not necessarily a no-op (`stale-wake-intent-resurrection`, `stop-cancellation-failure-is-honest`). Rejected: the prior best-effort exception answered `ok` when terminal-state wake clearing failed. It avoided a `503` for redundant UI requests, but knowingly allowed one unwanted wake and became unsound once Stop also cancelled scheduled sleep.
- **Liveness is evaluated on every `running` pass, ahead of inbox dispatch.** Delivery used to return early, so while any message was queued a dead runtime was never restarted: delivery timed out, pulls went silent, and the orb sat in `running` behind a host still observed `running` (`pending-message-blocks-liveness`). Ordering within a `running` pass is now: observe host → liveness/unreachable restart → claim and deliver the next batch → idle auto-stop. An outstanding batch returns before the idle check, so an undelivered message counts as activity and no orb is idle-stopped with user work in flight.
- **A successful delivery also refreshes the idle anchor** (added 2026-08-11 while writing `idle-stop-versus-send`). Admission refreshes `last_busy_at`, but admission and delivery can be arbitrarily far apart — a stopped orb boots for a minute, an unreachable runtime is retried for many more — so by the time the message actually reaches the runtime the anchor can already be older than the whole idle window. The outstanding batch protects the orb only until replication marks it delivered; the very next pass would then idle-stop an orb whose turn had just begun, before the ~10-second pull can report `busy`. The dispatcher therefore calls the monotone `touchLastBusy` when the runtime accepts a batch: the idle countdown measures from when the user's work *arrived*, not from when it was queued.
- **A successful delivery is a liveness success.** Liveness is "the runtime answered us recently", and until now only pulls could say so. With dispatch running behind the liveness check, a runtime that answered a delivery a second ago could still be restarted for pull silence accumulated while the delivery was in flight — a false positive of exactly the shape the 2026-08-05 egress-blip incident describes, but self-inflicted (it restarted the `busy-message-steers` scenario mid-delivery in ~1 schedule in 400). A delivery the runtime accepts therefore refreshes the baseline through `ControlState.noteRuntimeAnswered`, which is the first corroborating signal beside the pull; a delivery that times out or is refused refreshes nothing, so the unreachable restart keeps its teeth.
- **A non-retryable delivery rejection fails the batch instead of retrying it forever.** See `docs/runtime-protocol.md` for the terminal-failure rule and how it reaches the user; the reconciler logs one `message-batch-failed` edge with the batch ID, message count, and runtime error code — never message content.
- **A delivery is not delivered until its record replicates.** An acknowledgement is a hint, not a commit: the batch stays claimed and is redelivered every pass until the replicated inbox record marks its rows delivered, which is what makes every crash window between the two stores survivable. The runtime's own dedup — persisted session record, then in-process pending-batch set — is what keeps those redeliveries from starting a second turn. The crash-window schedules are listed in `docs/runtime-protocol.md`.

**Decided — idle auto-stop and orphan-host sweep (proposed 2026-08-01, decided and implemented 2026-08-03 with the visible-tab refinement):**

Idle auto-stop reuses existing machinery rather than adding a new lifecycle path:

**Admission fence added 2026-09-14:** a delayed request could acquire a child hold after the idle decision, yet the final drain still stopped the host. `stopping` with idle intent now prepares the runtime before draining: busy declines return to `running`; acceptance closes admission, including SDK-originated starts, and is persisted for the current execution lifetime. Lost preparation acknowledgements are retried without reopening work. Settings mutation ownership also blocks preparation, and a prepared runtime rejects new settings changes (integration regression, 2026-09-15; `docs/agent-settings.md`). Explicit Stop still interrupts uncooperative work. Prepare failure edges use `idle-stop-prepare-blocked`; declined attempts use transition reason `idle_stop_declined_busy`. The endpoint and lifetime semantics are in `docs/runtime-protocol.md`; evidence and the rejected snapshot-only repair are in `docs/postmortems/2026-09-14-idle-stop-admission-race.md`.

- The ~10-second history pull already returns `activity: idle | busy`. Add a `last_busy_at` column on the orb row (restart-stable, like `state_changed_at`; the wall clock is already injected). A pull observing `busy` — or any accepted mutating request, or an open live browser connection whose tab currently reports itself visible — refreshes it.
- When a `running` orb's reconciler observes `wallNow() - last_busy_at > idleStopAfterMs` (initial value: 15 minutes, matching Amp's pause window), it CAS-enters `stopping` with a persisted `stop_reason = 'idle'` so the UI can say "stopped (idle)" rather than presenting an unexplained stop; explicit Stop persists `manual`, while Start clears inhibition. From there the ordinary controlled-stop drain barrier applies unchanged. The effective idle anchor is `max(last_busy_at, state_changed_at, lastVisibleAt)`, so a freshly started orb always gets a full idle window. Two guards close timing holes: the reconciler also refuses to stop while the *most recent pull* observed `busy` (wall time can leap past the deadline — a clock jump or paused process — faster than pulls can refresh the persisted timestamp; found by DST), and `last_busy_at` writes go through a dedicated monotone `touchLastBusy` store operation with no `state_version` bump, so activity refreshes never conflict with lifecycle CAS or replication cursor writes.
- A browser connection counts as activity only while its tab is actually visible (decided answer to open question 10). Watching an agent work — or thinking about what to type next — should not power off the machine under the user, but a long-forgotten background tab must not keep a VM alive for days. The web client reports `document.visibilityState` over the live WebSocket: a presence frame on connect and on every `visibilitychange`. The control plane tracks the latest report per connection and treats the orb as browser-active only while at least one open connection has affirmatively reported `visible` — a connection that has not reported visibility counts as hidden, so the failure mode of a lost presence frame is an earlier stop, never a leak. A killed tab or slept laptop closes the socket, which removes the connection either way.
- Accepted limitation (open question 8 is resolved by the Pi SDK finding above; open question 9 stays open): detached background processes are outside aggregate owned-agent work and do not prevent idle stop. Amp ships the same trade-off with its 15-minute pause. If this bites, the answer is an OS-level signal (process/cgroup inspection in the runtime's health report), not a special background-job tool.
- DST coverage (implemented in `lifecycle.dst.test.ts` "idle auto-stop" and `orphan-sweep.dst.test.ts`): the idle deadline racing a just-accepted message burst (replica completeness holds whichever side wins); a busy runtime never idle-stopping even across simulated time jumps; a visible tab blocking the stop and a hide restarting the full countdown; and idle stop resuming correctly from persisted state alone after a control-plane restart with downtime.

**Workspace-upload activity requirement (decided 2026-09-08, implemented 2026-09-09).** An active file transfer counts as non-idle independently of model activity or browser-tab visibility. Protect the entire admitted transfer, including inter-chunk gaps and finalization, rather than merely touching `last_busy_at` at chunk arrival: transfer admission must serialize against the idle-stop decision so an accepted upload cannot lose to a stale idle check. This is lifecycle activity, not an agent-busy claim or a reason to show the model's streaming cursor. Completion, cancellation, failure, or abandoned-transfer expiry releases protection and refreshes the idle anchor so the normal idle window starts afresh; abandoned metadata alone must not keep an orb alive indefinitely. Explicit Stop, archive, and delete remain authoritative and can interrupt transfers. A finalized file's notification pending on a stopped orb waits for explicit startup and never requests wake. Durable transfer ownership/outcomes must let postmortem inspection reconstruct the protection interval without logging per chunk or reconcile tick. DST must cover admission versus idle-stop CAS, hidden/disconnected browsers, slow sinks and between-chunk delays beyond the idle window, terminal release, crash/expiry recovery, and explicit Stop versus notification acceptance. Implementation details, the five-minute activity lease, and its state-version/idle-CAS fence are in `docs/workspace-uploads.md`; live validation is tracked in `TODO.md`.

Idle auto-stop cannot, by construction, handle a host the database has no row for — no row means no reconciler, no history pull, and no idle signal. That is the separate **orphan-host sweep** (open question 23), and the two should ship together:

- A periodic control-plane loop (`orphanSweepLoop`, every 5 minutes, running as a third background task beside the poller and reconciler; one instance is enough since the operation is idempotent) calls `listManagedHosts` — already on the provider port for exactly this purpose; the GCE implementation lists by the `pi-orb-orb-id` label, Docker by its managed-container naming.
- Each observation is joined against the orbs table. A running host whose orb row says `stopped`/`failed` is already covered by the lifecycle-transition reconciliation below when `host_ref` matches; the sweep additionally catches rows whose `host_ref` was lost. A running host with *no* orb row at all — a provision whose commit was lost, or a database reset — is stopped and logged loudly as an integrity signal.
- The ordinary sweep only ever moves hosts toward "stopped"; it never starts or deletes anything, so a misfire costs a restart, not data. The deletion extension in `docs/orb-deletion.md` adds a separate, explicit path: while a `deleting` orb row and its durable tombstone prove destructive intent, the deletion sweep destroys matching hosts rather than treating them as unknown orphans.

## Central agent and eager execution — implemented locally (2026-10-03)

**Integrated candidate (locally process/Docker qualified 2026-10-05; undeployed).** Central inference/history is independent of execution startup after required initial resources load. Agent work warms execution in parallel; only VM-backed calls wait. Existing central polling and compute reconciliation run on independent tasks, never concurrent coroutines sharing one `SimulationTask`. Compute samples current handle work synchronously before deciding demand; resource-loading delay in central polling cannot block allocation. Evidence: `docs/postmortems/2026-10-04-central-reconcile-task-sharing.md`. Backend choice is independent of process/Docker/GCP (`docs/host-provider.md`). Lightweight stable handles retain metadata only for the control-plane process lifetime; browser subscriptions survive optional Harness unload/reopen. Passive history reads use PostgreSQL, never load a Harness. Unload only when the host is stopped and the agent quiescent; defer during active work and recheck persisted host state/admission before closing. Never interrupt children, waits, leases, persistence/publication or summaries, or boot/reopen solely to unload. No per-orb agent process/thread, LRU or new FSM.

### One execution lifecycle, derived agent activity

**Decision 2026-10-03:** retain `creating` for initial provisioning and `running` for ready compute, alongside `starting`, `stopping`, `stopped` and `failed`; these are execution states, not agent states. Merging creating/starting adds backend contract churn without enabling independence and is unnecessary for the process POC. Archive/archiving/delete retain whole-orb administrative authority. No agent-boot, VM-wait, or agent×VM cross-product FSM.

**Recovery decision (2026-10-20; implemented locally):** stopped compute, an empty delivery inbox and no loaded work do not establish persisted quiescence. Before unloading, central reconciliation checks persisted recovery demand through AgentPlane → selected harness → AgentPersistence. One read-only orb-indexed SQL query checks any task in `pending|running|waiting|completing` or submission in `queued|placed`, across all conversations, including children/background work. Demand continues through existing health/open/resume and admission fences; absence permits unloading; read/open failure returns a typed retry without unloading. Manual Stop, sleep, failed-state wake and archival authority remain unchanged. Passive reads never probe or open. No schema, persisted flag, history scan or payload decoding. Incident evidence: `docs/postmortems/2026-10-20-stopped-central-agent-recovery.md`.

Recovery emits condition edges `central-agent-recovery-requested` and `central-agent-recovery-failed`, with `source=persisted_work`, state/admission versions and failure stage/code. Quiet stopped orbs emit nothing. Probe/open failures, including answered failed health, use reconstructible ControlState memory exposed through existing `OrbView.lastError`, not database writes. Initializing health does not clear a blocked error; ready recovery, quiescence, inhibition and per-orb cleanup clear it. Successful native restart notices remain the conversation's recovery outcome.

Agent `idle`/`working` derives from root tasks, background children, admitted submissions and VM-tool waits. Housekeeping, public projection and Luna summaries do not demand VM boot. Central history remains available in every compute state without guest-history drainage. Central and compute reconciliation run concurrently and join both branches, so resource fetching does not delay allocation. Durable FIFO claims and dedup recheck agent admission before delivery. Only guest health resets execution liveness. Execution metadata hydration precedes publishing execution `running`; initialization failure is typed, durable and user-visible. Autonomous idle-stop does not abort central work or suspend its admission; stopped-and-quiescent unloading is separate from explicit Stop/sleep authority.

VM demand is **agent work OR existing upload/transfer holds OR unconsumed explicit Start/wake**. Eager warming is required, not merely permitted. A visible connected browser keeps a running VM from idle-stopping but never starts a stopped one. **Decided 2026-10-11, superseding the 2026-10-06 visible-browser warm:** opening a stopped orb must not start it; sending a message does (`queued_message`/`agent_work`). Rejected: warming on view — it started every idle-stopped orb the user merely looked at. The existing 15-minute idle grace retains an existing execution episode only; its timestamp cannot restart a stopped VM. Do not persist duplicate `agentReady` or `VMdesired` flags.

Current source has no separate desired-goal enum: the nine-state `OrbState` is both reconciliation intent and view. Presence is in-memory `ControlState.registerBrowserConnection` / `setBrowserVisibility` / `unregisterBrowserConnection`, requiring an affirmative visible report; periodic watched-activity persistence is an idle anchor, not a durable browser lease. Reuse these boundaries rather than inventing durable presence.

### Authority, Stop and recovery

**Legacy Pi startup decision (2026-10-08; implemented locally, undeployed):** optional per-orb startup preflight runs before explicit Start's early success, sleep cancellation or CAS. Central legacy Pi returns HTTP 409 with “This orb uses the old Pi backend. Create a new orb to continue.” through the existing action-error UI. Automatic inbox delivery terminally fails each claimed batch with that reason; no synthetic receipt, perpetual retry, compute-failed transition or VM/Git/model preparation is used. Start, health and delivery share the existing condition-edge detector and durable `central-agent-start-rejected` event (typed code, admission generation, public session ID, disposition). Repeated unchanged rejection is silent; batch failure remains visible. Failed cleanup retains its original startup verdict and records a separate `agent.startup_cleanup_failed` edge. Database outages remain retryable, not evidence of legacy or corrupt history. Passive history and Claude are unaffected. Locked compatibility/Native mutation fences: `docs/history-replication.md`.

Explicit Stop revokes new agent admission/dispatch and stops execution; `Harness.close()` suspends unfinished persisted tasks for authorized recovery. Browser connections have explicit conversation/execution scopes: central conversation subscriptions survive Stop and execution replacement, while execution terminals close immediately and cease contributing visible demand. Claude closes both scopes; deletion closes both, and central archival preserves conversation delivery only until finalization. Explicit root abort is terminal cancellation, not equivalent to close. **Correction (2026-10-06):** central retirement derives accepted cancellation from the committed current native run task's `abortRequested`, even when cancellation produces no terminal assistant. The existing operation outcome stays aborted through drain and resets for the next operation; historical receipts and reused public operation tokens cannot select the cancellation fact. Only completed operations enqueue Luna summaries. Native held-acquisition tests cover zero effects, public aborted/idle, later completed input and Stop/reopen suspension; current browser acceptance remains required. Scheduled sleep after work drains, archive and delete likewise override presence. Stop inhibition survives VM phase changes and control-plane restart through persisted `stop_reason = manual | sleep`. Migration `034_manual_stop.sql` preserves known pre-feature explicit-stop intent by converting only `stopped`/`stopping` rows with null stop reason to `manual`; idle/sleep reasons and unrelated failed/running rows are unchanged. Reopening or viewing migrated rows cannot resume unfinished work or warm execution before fresh input. Every explicit Stop advances command/state authority and `agent_admission_version`, including an already stopped orb; native central callers capture this revocation generation, not compute incarnation or lifecycle state version. Fresh Start or human input advances the generation when it clears manual/sleep inhibition; ordinary VM startup/recovery and cancellation of a not-yet-drained sleep preserve the active agent. Suspension carries the observed generation and advances the manager's authority floor, so an old Stop cannot close newer input and an old sampled open cannot undo revocation. Queued mutations recheck closing and durable admission when their serialized effect begins. Native alerts carry the expected generation through owner selection and revalidate inside the PostgreSQL receipt/effect transaction, preventing Stop→Start retargeting. Archive closes new admission while admitted work drains; completion revokes its generation. Pending sleep/archival does not revoke admitted continuations: identity authorization still permits their central inspection and alerts, while transactional spawn/sleep/archive/delete admission rejects pending sleep or archival. Persisted `sleep` always inhibits callers, even after the deadline row clears. Delete revokes immediately. Reconnects and heartbeats cannot undo Stop; fresh Start or new human input may supersede it under existing policy. Reading stopped or archived history never wakes execution.

Preserve existing bounded unexpected-host restoration and unreachable-host recovery, including deadlines, corroboration and retry caps; decoupling does not remove recovery. Terminal `failed` remains fenced against persistent demand: only fresh authorized intent buys another attempt under current failure-version policy. Affected VM waits fail with typed, user-visible outcomes while central operations continue. Never implicitly replay unsafe effects or rebind dispatched calls to replacement compute.

Central browser/inbox/auth paths use owner/project/orb authority, not guest tokens or incarnation, and have no host-readiness gate. The first model turn does wait for immutable Git resources persisted in PostgreSQL plus managed personal/project prompts and separate bundled `/opt/pi-orb/skills`. First-present instructions: `.pi/AGENTS.md` → `AGENTS.md` → `.agents/AGENTS.md`. Existing `.pi/skills`, even empty, wins; only absence allows `.agents/skills`. Acquisition/read failure never means absence. Safe tracked repository-local links are allowed, not ambient Claude/home/extensions discovery. Fresh initialization checks out `main` at the persisted exact SHA, then runs normal hooks; resume never resets dirty workspaces. Fetching and host allocation run concurrently; managed prompt refresh occurs at context creation/recreation boundaries. Central repository instructions and skill metadata come from the pinned Git snapshot and remain stable for the context. Execution readiness supplies only cwd, incarnation, PID, checkout commit and hook reports. VM tools wait for readiness and execute their admitted operation; explicit filesystem reads use the live workspace once ready. User shell commands retain execution/cancellation checks. Decision: resolved question 73 (Pi Durable) in `docs/open-questions.md`.

### Dispatch, UI and qualification

**Delivery presentation (2026-10-09; implemented and focused-test qualified locally, not deployed):** failed-orb `queued`/`delivering` rows display `blocked`, preserving durable status and inbox identity. Delivered-but-unreplicated rows remain delivered. Incident: [docs/postmortems/2026-10-09-glideos-delivery-blocked.md](postmortems/2026-10-09-glideos-delivery-blocked.md).

## Lifecycle transitions

The database state is desired/reconciliation intent as well as user-visible state. Every transition uses `state_version` compare-and-swap; provider operations remain idempotent, so competing reconcilers are harmless.

**Decided and implemented 2026-08-08 — per-orb reconciliation is concurrent:** one serial sweep formerly put minute-long archival/resource operations ahead of unrelated work; orb `a75e103d` waited 5m52s before its first provision attempt (`docs/postmortems/2026-08-08-serial-reconciler-head-of-line-blocking.md`). The scheduler now rescans every tick without awaiting orb work, launches each due orb on an independent task, and keeps a scheduler-local in-flight map so at most one reconciliation per orb runs in that process. Cross-orb concurrency is deliberately unlimited at the current POC scale; `SerializedAuthGate` serializes only within one owner, while database CAS and idempotent providers remain the correctness fence across brief multi-process revision overlap. Shutdown stops dispatching and drains in-flight work. A worker's unexpected rejection is surfaced as a fatal background-loop failure rather than detached or silently retried.

**Deletion extension implemented 2026-08-08.** `docs/orb-deletion.md` adds terminal-intent state `deleting`. It closes live access, revokes runtime-broker authorization, skips the history drain because the replica will be erased, destroys provider storage/compute and Tailscale identity, then transactionally removes history and the orb row. A short-lived tombstone and deletion sweep fence stale provisions and make cleanup recoverable; the tombstone, history, and orb row are removed together only after final absence checks.

**Project deletion required and implemented 2026-08-09.** `docs/project-deletion.md` composes this exact orb deletion path for every child. One atomic project command fences new orb creation and moves all existing children to `deleting`; a separate deterministic finalizer removes the project only after every child has completed deletion-grade absence checks. It introduces no provider-level project operation.

**Archival extension implemented 2026-08-08.** `docs/orb-archival.md` adds `archiving` and terminal `archived`. Archival first restores a readable runtime when needed, prepares the runtime's idle admission fence, and durably seals a pull-until-empty replica for that same compute; while busy preparation is declined it continues its own history pulls. The waiting edge is `archive-waiting-for-work`, preparation errors are persisted on the cleanup intent, and a successful seal records `admission_fenced:true`. The 2026-09-14 regressions are in `docs/postmortems/2026-09-14-idle-stop-admission-race.md`; it then reuses deletion's external cleanup, destroy, quarantine, and absence-check path, retaining the orb row and transcript. Archived orbs are permanently non-startable.

| Database state | Reconciler behavior                                                                                                                                                                                                                          |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `creating`     | Ensure the project owner's selected harness/GitHub auth, provision by orb ID, then wait for runtime ready.                                                                                                                                              |
| `starting`     | Ensure the project owner's selected harness/GitHub auth, observe/start or reprovision the retained host/filesystem, then wait for runtime ready.                                                                                                        |
| `running`      | Observe the provider and derive runtime liveness from the ~10-second history pull; broadcast/replicate normally.                                                                                                                             |
| `stopping`     | First finish any durable compute discard; otherwise reject new live connections, close existing proxies, perform the final history-pull barrier, stop the provider host, then mark stopped. A non-retryable drain failure atomically fails the orb and requests disposal. |
| `stopped`      | Start the orb when any outstanding inbox message carries the wake intent; otherwise perform no runtime work and reconcile an unexpectedly running host back to stopped.                                                                       |
| `failed`       | Preserve workspace/history/error, revoke old runtime authorization, and converge the fenced failed compute to absence. Start for explicit intent or a current-failure inbox wake (once) only after disposal finalizes; never autonomously provision replacement compute. |
| `deleting`     | Refuse all ordinary orb work; retry complete host, filesystem, Tailscale, and database cleanup as specified in `docs/orb-deletion.md`.                                                                                                        |
| `archiving`    | Refuse live mutations, restore runtime if needed, seal complete replicated history, then run shared destructive resource cleanup (`docs/orb-archival.md`).                                                                                     |
| `archived`     | Serve retained metadata/history read-only; never provision, start, or adopt a host.                                                                                                                                                             |

Commands:

- create inserts `creating` and wakes reconciliation;
- start is idempotent for `creating`, `starting`, or `running`; from `stopped` or `failed` it clears `last_error`, enters `starting`, and wakes reconciliation;
- stop atomically cancels scheduled sleep and message wake authority in every state; cancellation failure returns a typed retryable error without changing the orb or its authority; from `creating`, `starting`, `running`, or `failed` an accepted stop also enters `stopping`, while `stopping` or `stopped` retains its state;
- delete is idempotent while `deleting`, may enter it from every other state, and makes start/stop/rename/history/live operations conflict;
- archive is idempotent in `archiving`/`archived`, preserves history reads, and permanently conflicts with start; delete may upgrade an in-progress archive or remove an archived orb (`docs/orb-archival.md`);
- start while `stopping` returns `409 conflict`; the caller retries after stopped;
- currently implemented live runtime message requests are rejected once the database enters `stopping` because the control plane closes and refuses live proxy connections for that orb; under the send-anytime API, message inbox admission remains available in `stopping` and requests restart only after its drain completes.
- The process-local proxy gate records the durable `state_version` that entered `stopping`. It rejects a connection only while that marker is at least as new as the row the proxy read. Markers stay monotone for the process lifetime: a later start supersedes an older marker, while an older completion cannot erase a newer concurrent stop (`docs/postmortems/2026-09-07-stale-stopping-marker.md`).

Reconciliation rules:

- retryable provider/network failures leave the current transitional state unchanged and retry with deterministic-clock exponential backoff capped at 10 seconds;
- a non-retryable provider error or runtime `failed` response transitions to `failed`; this also applies to boot failure after automatic recovery from preemption, retaining workspace/history while disposing compute (`docs/postmortems/2026-09-30-preemption-boot-context.md`);
- **no loop retries a store `invariant` (decided 2026-08-11, from `docs/postmortems/2026-08-11-orb-message-jsonb-param-encoding.md`).** A `StoreError` with code `invariant` is a deterministic bug of ours — wrong SQL, a parameter the driver cannot encode (`docs/stack.md`) — and every retry reproduces it exactly. The reconcile loop, the history-pull loop, and the project-deletion sweep therefore park the affected orb/project after logging one edge (`reconcile-retry` / `pull-failed` / `deletion-retry` carrying `invariant=true`) instead of spinning at the backoff cap until someone deploys a fix. The park lives in process-local scheduling state, so a control plane restarted with the fix resumes normally, and the orb is never transitioned to `failed` for a bug in our own code. The same class answers a non-retryable HTTP 500 `internal` rather than a 503 that invites client retries;
- **Decision implemented 2026-08-09:** a returned runtime-health `status: "failed"` is terminal for that host boot and transitions `creating`/`starting` to durable `failed` with the runtime code and explanation in `last_error`; it is never a readiness level to poll. A runtime that owns bounded recovery stays `initializing` while it retries and returns `failed` only after exhaustion. This corrects the one-shot `clone_failed` wait found in `docs/postmortems/2026-08-09-private-repo-clone-outside-github-app-installation.md`. The DST scenario drives the formerly ignored retryable-labelled failure through prompt failure and eventual host stop, and the full-slice E2E proves the real runtime's inaccessible-repository error reaches the API. Failure-vs-cleanup ordering, repository-access preflight, and richer error classification are separate hardening decisions, not prerequisites for bubbling up the error through the existing failed-state/API/UI path.
- provider absence during `creating`/`starting` calls idempotent `provision(orbId, ...)` rather than assuming Docker/GCE semantics;
- provider absence or unexpected stop while the database says `running` transitions to `starting` and restores the host around the retained filesystem;
- a running provider whose runtime remains unreachable for a grace period is restarted with provider `stop`/`start`, without the controlled-stop drain because the runtime is already unhealthy; this rule applies in both `running` and `stopping`, so a pending drain is never stranded behind a dead runtime process inside a live host. What happens after the restart differs by state (decided 2026-08-06, below): `running` re-enters `starting`, while `stopping` stays put under a boot-sized grace and a one-restart cap;
- auth challenges and blocked cohorts are scoped by owner UUID and provider; selected harness auth (`pi` → Codex, `claude` → Claude) precedes independent GitHub auth. Completion CAS-reenters matching blocked `creating`/`starting` rows with a fresh `state_changed_at`; expiry/denial fails only that provider cohort. Same-owner Pi and Claude challenges cannot overwrite or clear each other (POC, 2026-10-04);
- retryable storage/upstream/publication and opaque Pi SDK errors leave the cohort transitional rather than moving it to `failed`; SDK classification is specified in `docs/credentials.md`;
- `auth-blocked`, `auth-resolved`, and `auth-failed` edges carry owner UUID and provider, never device codes, URLs, tokens, or credential bodies; Codex→GitHub blocker changes are edges too;
- an orb becomes `running` only after ready identity/session/commit data have been persisted;
- when an orb has been `creating` or `starting` longer than the create/start deadline (measured from `state_changed_at` with the injected wall clock), the reconciler transitions atomically to `failed` with a typed `deadline_exceeded` error, revokes authorization, and requests compute disposal; shared reconciliation owns provider deletion. A later start begins a fresh deadline, and OAuth device-login wait time never counts because completion re-enters the state with a fresh `state_changed_at`;
- a retryable controlled-stop pull/commit failure leaves the orb in `stopping` and the host running, as specified by the shutdown barrier;
- a non-retryable replication-integrity failure (unknown cursor, session-header mismatch, mapping/validation failure) — whether during `running` polling or a `stopping` drain — atomically transitions to `failed`, revokes authorization, and requests fenced compute disposal (see `docs/history-replication.md`); the same applies when a runtime cannot be restored to ready within the create/start deadline while a drain is pending;
- when stopping an orb that has never reached ready (`last_ready_at` null; set on every runtime ready — not `checkout_commit`, which is null for a repository without commits, decided 2026-10-06) and has no `harness_session_id`, no user request could have been accepted, so the control plane may skip the history drain and stop the provider directly;
- if the provider host is definitively absent or already stopped during `stopping`, there is no running runtime to drain; mark `stopped` directly — complete records left on the persistent filesystem are found on the next start.

The create/start deadline is held off while the repository's `.agents/setup` is running, because it is allowed twenty minutes of its own (`docs/orb-setup-hook.md`). The hold is anchored at the first `setup_running` report of a boot episode and bounded by `setupHookHoldMs` (22 minutes) from that anchor — enough for the hook *plus* the boot that follows it, which is why a later phase does not retire it: doing so would drop the orb straight onto an ordinary deadline the hook legitimately outlasted. Every in-memory hold ends once the episode is `createStartDeadlineMs + setupHookHoldMs` old by the durable `state_changed_at`, because control-plane restarts renew them (decided 2026-10-10, `docs/postmortems/2026-10-10-starting-deadline-restarts.md`). Three further rules make it safe:

- **It survives a single failed health probe, and ends on sustained silence.** Readiness probes during a boot contend with slow provider observes and are cancelled in bursts, so one cancelled request must not end a twenty-minute setup; but a runtime that has not answered for the boot-sized `postRestartGraceMs` is gone, and the hold ends rather than hiding that for twenty minutes. The `runtime_never_answered` boot sub-deadline is never held off at all, so a runtime that dies mid-hook is still caught by ordinary boot detection.
- **It survives a control-plane restart.** The anchor is in-process memory, and losing it is the one loss `noteStateEpisode` cannot call safe: a restart landing after a long hook would judge the boot by a deadline the hook had legitimately outlasted and fail a healthy orb. A restarted process reseeds the anchor from the runtime's own health report, which carries the setup hook's start time once the hook has finished.
- **A hook still running is `running_setup` only while the runtime is answering.** Otherwise the orb reads as `waiting_for_runtime`: telling a user a script is working when the runtime is gone is worse than saying nothing.

Use initial constants of a 5-second readiness health interval during create/start, a 30-second unreachable-runtime grace period, a 3-minute post-restart grace (below), and a 15-minute create/start deadline; while `running`, liveness is derived from the ~10-second history pull instead of a separate health poll. These use injectable deterministic clocks. Time spent waiting for the user to complete a displayed OAuth device challenge ends when that challenge expires rather than consuming a separate hidden timeout.

Add `state_changed_at` to the orb row for transition deadlines; ordinary replication writes must not alter it. `updated_at` remains a general row-update timestamp.

Idle auto-stop (above) enters `stopping` through the same transitions; it required no new lifecycle states — only the persisted `last_busy_at`/`stop_reason` columns and the reconciler's idle check.

**Decided — what follows an unreachable-runtime restart (2026-08-06, from `docs/postmortems/2026-08-05-unreachable-restart-livelock.md`):**

A restarted host is a booting host, and any liveness grace shorter than a boot concludes "unreachable" against it forever. The 2026-08-05 field incident did exactly that: 38 stop/start cycles in 38 minutes against a ~65 s COS boot under the 30 s unreachable grace, each cycle hard-stopping a VM roughly 2 s short of serving. The rules that replace "restart inline and keep waiting in place" are:

- **From `running` the restart hands recovery over instead of repeating it.** After the `stop`/`start` the reconciler CAS-transitions the orb to `starting` with a fresh `state_changed_at`, so the patient readiness path owns the rest: 5-second health polls, the `runtime_never_answered` boot sub-deadline, and the create/start deadline as the outer bound. The fresh `state_changed_at` also gives the new host incarnation a fresh boot-detection window. No code path restarts a host twice from `running`.
- **From `stopping` the restart stays put but is bounded twice over.** A pending drain cannot be handed to the readiness path — the orb must remain `stopping` — so the inline restart survives there under two bounds. The liveness baseline it seeds is granted `postRestartGraceMs` (3 minutes, comfortably above a ~60–70 s boot) rather than the ordinary 30-second grace, and at most one restart is attempted per `stopping` episode: if that baseline expires again with no pull success in between, the restarted runtime has demonstrably not returned and the drain fails at once with `drain_runtime_unrecoverable`. That outcome is now evidence-based; the stopping deadline remains only as the outer bound.
- **A revision adopts another revision's drain restart (decided 2026-09-07).** Provider observations carry the current host's last-start time. If it belongs to the stopping episode and is still inside `postRestartGraceMs`, a reconciler anchors its own grace to that start instead of restarting the same boot. It emits one `drain-restart-deferred` edge per newly observed start. Missing, malformed, future, older, or already-incorporated evidence preserves the existing bounded restart decision. This fixes a rollout race where two revisions restarted one host 39 seconds apart and the first revision exhausted its grace before obtaining a successful pull (`docs/postmortems/2026-09-07-mixed-generation-drain-restart.md`).
- A liveness baseline therefore carries the grace it is entitled to. A baseline seeded by a pull success, or by entering `running` (where the runtime has just answered a health check and is serving), gets the ordinary grace; only a baseline seeded by a host restart gets the boot-sized one.

Rejected: keeping the restart inline everywhere and merely enlarging the grace past a boot. That fixes the livelock's period, not its shape — a `running` orb still has no deadline of its own, so an unrecoverable host would cycle forever at a slower rate, and every cycle hard-stops a host that may still be flushing (the durability gap in `docs/history-replication.md`). Re-entering `starting` instead reuses machinery that already has a deadline, a boot-failure sub-deadline, and host-side diagnostic evidence.

**Decided — rolling budget for automatic restarts (2026-10-10):** an orb gets five automatic restarts per rolling hour. Each automatic `running` → `starting` restart (`no_host_ref`, `host_absent`, `host_observed_*`, `unreachable_restart`) and each central agent open that would resume unfinished tasks (`agent_recovery`, charged before resume) records its time in `orbs.auto_restart_times`. The sixth fails the orb as `restart_budget_exhausted`; a refused agent stays suspended. Plain `failed` leaves a central agent running, so this failure also sets `stop_reason = 'manual'` and advances `agent_admission_version`, as Stop does. Preemptions and deploy rollovers count. Explicit Start and a message wake clear the record. Evidence: orb 5b5ef18e reopened its agent in recovery 128 times between 2026-10-09 22:42Z and 2026-10-10 07:54Z, once per control-plane OOM (`docs/postmortems/2026-10-09-central-durable-oom-recovery.md`), without a compute restart; the budget would have failed it at 23:05:49Z. Not covered: guest-local restarts (Docker, process provider, systemd) that recover inside the liveness grace.

**Incident invariant (2026-10-16):** distinguish unreachable-recovery decisions, completed provider stop/start pairs, admitted recovery transitions and runtime readiness; none proves completed agent work. Attribute Spot preemption only with provider evidence, not timeout or stopped-host status alone. Unreachable recovery checks the snapshot budget after corroboration, before restart intent or provider stop/start; exhaustion uses the existing failure/discard CAS and agent-admission fence. The post-provider `starting` CAS still charges recovery; retryable provider failures consume no slot. This check does not reserve slots across concurrent recoveries. Evidence: `docs/postmortems/2026-10-16-c9a30a6d-restart-loop.md`.

**Decided — runtime-silence diagnostics (2026-10-16):** runtime transport failures include headers/body phase, elapsed time, HTTP status, syscall code, cancellation and endpoint origin in the existing error message; no response content, URL paths, queries or credentials. Existing pull-failure events retain these messages; failed health corroboration records `runtime-health-failed` with its error in the durable lifecycle log. Compare these remote failures with the native supervisor's local health and child-exit observations (`docs/host-provider.md`). GCE control-plane requests use the private VPC, not Tailscale. These observations do not establish the historical silence's cause or change restart policy.

**Decided — in-process reconciliation memory is scoped to one episode (2026-08-06, found by `mixed-generation.dst.test.ts`, docs/testing.md):**

Everything a control-plane process remembers about an orb between passes — the boot probe (and with it the `runtime_never_answered` clock), the drain status, a half-finished restart, and the liveness baseline with the grace it was granted — describes *one visit to one state*: this boot, this drain. That memory used to be cleared only by the transition that ended the episode, which the process itself had to make. A second reconciler that watched the episode but lost the CAS never cleared anything, and during a deploy rollover there is always such a reconciler (docs/testing.md: version skew is part of the model). It then judged the *next* episode by the previous one's clocks: a boot window that opened two minutes ago failed the next start as `runtime_never_answered` within seconds, and a restart grace from the previous drain failed the next drain as `drain_runtime_unrecoverable` on a runtime that was serving. Both denied service to a healthy orb, and both were reachable in the field the moment two revisions overlapped.

The rule: episode-scoped memory is keyed by the orb row's durable `state_changed_at`, checked at the top of every reconcile pass, and dropped whenever it changes. Deriving the window from the row rather than from an observed transition makes it hold for every reconciler, whether or not it made the transition — and forgetting is always safe, because it is exactly the state a control-plane restart loses and every path reseeds it from the row on the next pass. Within one episode the boot clock still restarts whenever the host is observed absent, stopped or failed, so `host_running_s` always describes the incarnation it names.

**Decided and implemented — measure runtime silence at the transport boundary and corroborate it (2026-09-07, `docs/postmortems/2026-08-05-egress-blip-false-unreachable-restart.md`):** the silence clock starts when a pull, delivery, or health request is handed to the runtime client and ends when the control plane receives any HTTP response. HTTP errors and malformed responses therefore prove reachability; connection failures and cancellation do not. Delay before the first runtime request cannot start the grace; later delay cannot trigger restart without fresh corroboration. The regression trace had two provider-observe timeouts and zero runtime calls during the interval that previously authorized a restart. The backend-independent candidate preserves this rule: `SdkAgentPlane` starts history/delivery silence immediately before transport, after its awaited provider observation and incarnation/cancellation checks. Placement, not adapter presence, selects central polling and activity policy; host SDK pulls retain guest liveness, busy activity and ordinary running-state polling.

After that grace, a successful provider observation is followed by a fresh bounded health request before restart. Any answer defers the restart. An answer received concurrently by a pull or delivery also vetoes a failed corroboration; the reconciler rechecks the same silence episode after the health request rather than acting on its earlier snapshot. The durable edge log records `unreachable-restart-deferred` with `runtime_answered_corroboration` or `silence_episode_changed`; a restart records `corroboration=health_no_answer`. “No response received” does not prove that the runtime failed to process a cancelled request. A control-plane egress partition can still make both runtime requests fail while provider access works; cross-orb corroboration remains in `TODO.md`. Interrupted-turn recovery remains the separate defense below.

**Claude boot continuation decision (2026-10-06; updated 2026-10-23 PDT, approved implementation underway, unqualified).** Claude uses its pure boot plan over retained root evidence: baseline, interrupted-root continuation, passive settled restart context, or non-triggering decline. A triggering boot claim precedes native submission and consumes one of three automatic interrupted-work attempts even if inference never starts; existing markers retain runtime/execution/incarnation identity, reason and prior head. Passive context is metadata, not resume authority; its zero-turn success cannot retire an active human operation. Interrupted human/tool work and scheduled `sleep_wake` remain triggering. Only genuine human input resets the budget; passive context, boot receipts, system inbox messages, compaction and completed notices do not. The root resumes its retained session; children are not replayed. Old child ownership clears only with a fenced execution-lifetime change, and uncertain human receipt remains fail-closed. Execution wording is neutral about restart cause and does not assume detached processes died on a runtime-only restart. Claims, declines and delivery failures remain visible replicated records; readiness reports edge-only `turnResume` outcomes. System inbox input, peer messages, compaction and successful notices cannot reset that budget. Exhaustion produces a visible non-triggering decline; it never silently reports successful recovery.

Configured identity-read failure is a typed initialization failure, not guessed identity (`docs/host-provider.md`).

**Decided — the reconciler's event log (2026-08-06, closing the last defect of `docs/postmortems/2026-08-05-unreachable-restart-livelock.md`):**

The control plane logs its lifecycle decisions, and only those. Every line is one grep-friendly `key=value` record prefixed `lifecycle:` and naming its orb, written through `domain/log.ts` on the `determined` task logger, which reaches stdout and therefore Cloud Logging. What logs:

- **every state transition**, from both the reconciler and the HTTP commands, with `from`, `to`, and why — a `stop_reason`, a failure `code` plus its message, `start_requested`/`stop_requested`, `idle_for_<n>s`, `unreachable_restart`, `drain_complete`, `host_observed_stopped`;
- **every provider operation the reconciler decides on** — `provision` (with `outcome=created|adopted|replaced`), `host-start`, `host-stop`, each with the host ref, the reason it was issued, and the provider's error if it failed. The unreachable-runtime restart additionally logs `unreachable-restart` with the grace that expired, whether that grace was `ordinary` or `post_restart`, and how long the runtime had been silent; the `stopping` one-restart cap logs `drain-restart-cap` *before* it fails the drain;
- **boot-detection outcomes** (`boot-failed reason=runtime_never_answered` with the probe count, how long the host had been running, and the host-side diagnose evidence when it was collected);
- **boot-hook outcomes** (`setup-failed` / `resume-failed` with the incarnation, the outcome, the exit code, and the in-orb log path — never the hook's output), logged on the `runtime_ready` transition that ends the boot episode and deduped as one condition per orb *per compute incarnation*: the same hook failing every boot of one incarnation is a level, not an edge, while a replacement incarnation runs the hook afresh and its outcome is a new edge (`docs/orb-setup-hook.md`). This edge is the *only* durable record the control plane keeps of a hook outcome: the user-visible `setup_failed` detail is relayed from the runtime's health report and held in per-process memory. A hook that succeeded logs nothing;
- **drain progress** — `drain-blocked` (once per retrying episode, piggy-backing on the drain status the UI already tracks), `drain-caught-up`, `drain-skipped`, `drain-integrity`;
- **inbox admission and dispatch decisions** — `message-queued` once per newly admitted message (message ID, the orb state that decided its wake intent), `message-batch-dispatched` once per batch the runtime newly admitted (batch ID, message count, observed `turn`/`steer`), `message-batch-failed` when a non-retryable runtime rejection fails a batch (batch ID, message count, runtime error code and message), and `stop-wake-clear-failed` when a no-op stop could not clear the wake intents it outranks. The `stopped`/`failed` → `starting` transition a queued message causes is logged by the reconciler that makes it (`transition ... reason=queued_message`), so it exists for every caller and not only for HTTP sends. Message content is never logged;
- **replication events that change an orb's fate** — the integrity failure that fails an orb, and the acceptance of a session rotation at a null cursor (`session-rotated`), which the store would otherwise perform silently;
- **failures at loop level** — the first failing pull of an episode (`pull-failed`), the first typed retrying reconcile of an episode (`reconcile-retry`) — both carrying `invariant=true` when the failure is a deterministic store bug that parked the subject instead of being retried, an unexpected concurrent worker rejection before it fails the supervised loop (`reconcile-task-crashed`; `poll-task-crashed` carries only `lane=central|history|name` and `error=unexpected`, never rejected content), a store outage that blinds a loop (`poll-loop-blind` and its `-recovered` partner), and the orphan sweep's stop decisions with their reason (`no_orb_row` or `stale_host_ref`);
- **code-mode resource failures** — `codemode.resource_failed` with `kind=out_of_memory|output_limit|callback_limit|sandbox_exit`, peak worker MiB, conversation and call (`docs/pi-adapter.md`).

The noise rule is the other half of the decision, and it is what makes the log usable: **a healthy fleet logs nothing.** Successful pulls, noop reconcile passes, readiness health checks, and the idle countdown are levels, not edges, and stay silent. Conditions that persist across ticks — a blocked drain, a store outage, a pending device login — log once when they start, not once per pass; `ControlState.noteCondition` is the shared edge detector for the ones without their own status field. Anything logged per tick would reproduce exactly the failure of the 2026-08-05 incident from the other side: 38 minutes of output that nobody can read.

**Exception (2026-10-11): code-mode memory samples.** While at least one code-mode worker is live, one `codemode.memory` JSON line per 10 s records worker and process memory; an idle process logs nothing. This is a level by design: a container OOM is a SIGKILL without warning, so only the state shortly before the kill can attribute it, and threshold edges would miss growth between crossings. It is bounded (at most six lines a minute, only during code-mode work) and is not a `lifecycle:` line, so the reconciliation grep stays edge-only. Details: `docs/pi-adapter.md`.

Rejected: log levels and a configurable verbosity. With edges-only there is nothing to turn down, and an incident is diagnosable from the default deployment rather than from a redeploy with debug logging enabled.
