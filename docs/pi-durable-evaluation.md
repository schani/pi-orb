## Pi 1.3 and native code-mode decision (2026-10-16; local implementation)

Upgrade the Pi family to **1.3.0** and use `createCodemodeExtension`/`createCodemodeTool` from `@earendil-works/pi-durable/codemode`. Upstream owns discovery, orchestration, nested tool tasks and deterministic replay; pi-orb decorates policy and presentation. The user chose less first-party orchestration and restart continuity. **Rejected:** retaining the custom wrapper would minimize the upgrade diff but retain its maintenance burden.

**Approved persistence:** native `CodemodeRunDoc`, `CodemodeJournalDoc`, `CodemodeStoreDoc` and owned nested tasks use existing PostgreSQL JSON task/document storage; no DDL. Future store writes commit only on success, rewind with history and fork as of the selected entry. **Legacy saved values (user-approved 2026-10-16, PDT; `docs/open-questions.md`, question 81):** no carryover/import from `orb.codemode-store`. A new native store starts empty, so native `load()` does not find legacy keys. Existing legacy records and existing native stores are not deleted or reset. Completed v1 receipts and conversation/public history remain unchanged: `ToolResultMessage.content` is still transcript content; the new implementation API is `ToolExecutionResult.output`. No unfinished-custom-task compatibility, blanket history rewrite, external-state operation or deployment is included.

Integration boundaries:

- **Capabilities.** Only `codemode` is model-callable. Underlying registrations have `callers:["tools"]`; native validation/preparation runs once, then catalog authorization/admission precedes effects. Each root open configures `tools:null` and `modelTools:[codemode]`. Children persist an explicit whitelist from their filtered extension and the same model offering: no `orb_spawn`, subagent tools or ambient registry capabilities. Public `Conversation.configure` accepts registration references and stores names in native `AgentDoc.tools`/`modelTools`.
- **Recovery.** Native `api.executeTool` owns nested task admission, hooks, task keys, cancellation and drain. Recorded seed, clock, start data and host-ordered deliveries reconstruct a script, not a VM snapshot. Version/fingerprint mismatch, expired deadline or divergent calls/arguments refuse **new** nested admissions. Already-admitted replay-safe pending children may retry independently, even when the parent refuses replay; current authorization/environment are checked again, but admission-time preparation/`beforeTool` hooks are not. Parent cleanup aborts those children. ACKed/completed callback receipts are reused; this is not physical exactly-once external execution. Version/deadline refusal needs no resumed VM; fingerprint/divergence checks may replay one. Native semantics require no custom orchestration: proof tracks original child TaskIds/keys, completed receipt reuse, no new admissions and no post-hold sentinel effect on refusal, not a universal zero-attempt/zero-VM assertion.
- **Raw MCP validation.** Check uncoerced arguments against the server's original JSON Schema before native preparation/hooks, authorization, per-call credentials or effects; discovery credentials are separate. Explicit null is preserved; only omitted/undefined arguments default to `{}`. Only accepted input reaches composed native preparation. Invalid input uses a fixed sanitized Harness-required rejection without private values in model output/public details. Raw schemas, complete result envelopes and deferred metadata remain intact. Runtime resource/template discovery stays lazy; HTTP 404 session expiry/reconnect is distinct from HTTP 200/JSON-RPC `-32601` optional-method fallback (`docs/pi-adapter.md`).
- **MCP refresh.** After discovery, reinstall instrumented root/child extensions through registry upsert and update existing child whitelists through public `Conversation.configure`. Native tool-phase `api.agent` is cached: upsert alone cannot refresh the current invocation. The DurableAgent adapter binds public `Harness.conversation`; composition delegates wrapped `api.agent` to that actual `Conversation.agent` resolver. Native `executeTool` remains unchanged. Existing roots and already-created children recover tools/instructions without recreation or a new upstream API. Discovery/refresh failure returns sanitized output without running the script.
- **Declarations/results.** Native discovery and prompt sections use the callable registry. Known text-only tools declare strings; `read` declares string or an image-block array; generic mixed callbacks declare string or a text/image-block array. Deferred MCP tools retain discoverable full raw result schemas, including arbitrary JSON `structuredContent` (arrays/null included), without forcing those declarations into the inline prompt. Native output has a completion/time header, numbered text items when needed, joined adjacent text and a final console block; it is not a JSON envelope.
- **Private presentation.** Committed `LiveDoc.nestedTools` slots retain native progress privately. Public live view folds only the execution-wait boolean through private `parentTaskId` links to the owning top-level tool. Final nested summaries whitelist ID/name/status/duration/explicit argument keys; raw arguments and private errors remain private, including divergence/validation failures. Native journal/task inputs retain actual values for execution and replay.
- **Charts/artifacts.** The `chart` global validates specs; successful native journal entries derive `LiveDoc` chart rows in their native commits; final charts decorate the native completion result in its transaction. Accepted charts survive reopen, error and cancellation without another journal/task document. Native `output.txt` spills route through scoped private PostgreSQL artifacts, with paths in that completion result. Binary writes are declined; image blocks remain inline. No guest/local temporary-file fallback or binary persistence is provided.
- **Resources.** Normalize the five-minute default deadline **before** native `persistStart`, so restart cannot extend it. Preserve the process-shared one-core CPU budget, 256 MiB QuickJS heap, callback caps (8 outstanding/256 total, including discovery; 8 MiB arguments/64 MiB replies), and text/image/item limits in `docs/pi-adapter.md`. Close/abort stops admission; worker/CPU/memory ownership drains through actual worker exit. The native Worker must remain referenced through physical termination exit; a termination request or finished execution is not drain completion (decision 2026-10-16; `docs/postmortems/2026-10-16-codemode-worker-exit-liveness.md`). One durable `codemode.resource_failed` edge includes orb/conversation/call identity and resource kind/peak; terminal results retain CPU/memory snapshots. Failed scripts commit no store writes; earlier effects remain. Heap limits and telemetry do not cap aggregate host memory or prove a fix for historical OOM/CPU/429 incidents.
- **Storage.** Effect-free invalid requests are recoverable `StorageRequestError`s; I/O, corruption and authority loss are fatal Session failures. `SessionFailed` retains typed owner-fence causes. Native mutation and required public projection remain one transaction.

## Storage target decision (2026-10-04)

**Decision:** authoritative Pi Durable persistence must use pi-orb's PostgreSQL, including private agent history/execution state and a separate user-visible transcript. Duplication is accepted for simple privacy and independent lifetimes: archive publishes/drains/seals the transcript, then deletes agent history/execution state while retaining the transcript. Canonical native entries plus thin public references are rejected for retention coupling. A separate SQLite authority is not an acceptable target: durability belongs in the existing database, not a second persistence system. Per-orb SQLite belongs to the earlier qualified process POC; the integrated candidate uses PostgreSQL. Earlier restart evidence does not qualify this candidate. Each causal mutation must atomically commit native state and all required public projection/enrichment/cursor/dedup updates in the same PostgreSQL transaction, including applicable receipts, admission and owner fences. No asynchronous projection-repair substitute; readers never see half-state and notifications follow commit. Remaining qualification is tracked in `TODO.md`; the unit-of-work, recovery and archive contract is in `docs/history-replication.md`.

**Native PostgreSQL SQL decision (2026-10-24; user-approved, implemented).** Implement Durable's `Storage` contract in first-party PostgreSQL queries with explicit orb-namespace predicates, table names and bound positional parameters. Prefer explicit SQL construction over dialect translation so scoping and binding are reviewable. Preserve the existing schema, data and `Storage` semantics, owner/admission fences and atomic native/public mutation transaction. Qualification requires the upstream storage conformance suite on both PGlite and network PostgreSQL; earlier results do not qualify this implementation. Current-source process-host acceptance, hosted receipts and qualification limits: `docs/testing.md`.

**Pi Durable 1.1.0 baseline (2026-10-12; historical local receipt).** `PgStorage` ports upstream SQLite storage's scan `order`: conversation, task and submission scans default ascending, entries descending, and a cursor carries and enforces its order; the upstream storage conformance suite passes on PGlite and PostgreSQL 16. The 1.0.2 `pi.provider` conversation document (Codex prompt-cache session) needs no allowlist: public projection reads only entries, and publication dirtiness ignores non-identity documents. Older conversations gain it lazily on their next generation, the same path a new conversation takes. The remote execution environment satisfies the 1.0.3 interface: binary readers are host-side handles paged in 1 MiB responses (`read`, `info`, `scanLines` run on the orb, so the `read` tool no longer transfers whole files); directory readers page one `listDir`; `watch` returns `not_supported` because no pi-orb path watches the workspace; argv `exec` and per-chunk stream names cross the wire; `ShellExecOptions.window` is not forwarded, so the host delivers every chunk and reports no omission. These are breaking wire changes between control plane and orb runtime; running orbs restart onto the matching runtime.

This decided storage before production adoption. Question 72 (Pi Durable) in `docs/open-questions.md` records the subsequent adoption approval; live recovery qualification remains separate. No dual-store compatibility phase is required.

## Integrated architecture

The same private-authority/public-projection adapter runs against PostgreSQL and PGlite. Owner leases use the database clock; an instance-bound bounded drain capability permits already-admitted cleanup after admission revocation, never new submission/model/effect dispatch. Archive atomically checks/seals the current public head and purges private native state, repository snapshots and artifacts; delete removes both lifetimes. Stable handles retain metadata only; passive transcript reads query PostgreSQL without loading a Harness. Stopped-and-quiescent unloading is deferred while work remains, rechecks persisted state, and never aborts work or boots compute merely to unload.

**Teardown rule (2026-10-18):** native failure can close storage before owner-fenced drain activation. A matching, database-validated owner may finish draining already-closed storage; it grants no new writes. Join Harness/resource teardown before compute destruction, and retain genuine cleanup/fence failures. Evidence: `docs/postmortems/2026-10-18-central-drain-close-race.md`.

**Lost-owner retirement decision (2026-10-23; implemented locally):** after verifying the storage capability, a database owner-guard rejection returns typed `owner_lost`, not a cleanup error or permission to drain-write. Native Harness/storage, publication, summaries and resources must still finish before manager replacement. Foreign storage, unavailable SQL, native/publication and resource cleanup failures remain errors; an aborted ownership signal alone proves nothing about the database owner. Close retains its joined result; the existing manager may replace a successfully retired agent without resetting itself. Failed authority releases remain tracked and retry only the idempotent database release, never Harness/resource teardown. Renewal/drain cause codes and final close outcome/stage use existing lifecycle edges. No schema, prompt or manager-policy change. Reproduction and qualification: `docs/postmortems/2026-10-23-agent-lease-loss-drain.md`.

**Placement decision (2026-10-18):** immutable per-orb harness selection is `pi|claude`, independent of process/Docker/GCP host selection. Pi runs centrally with PostgreSQL authority and execution-only guests; Claude stays host-native with filesystem resume authority. Central Claude is rejected (`docs/claude-agent-sdk.md`). AgentPlane dispatches health, inbox, stop and replication using the persisted harness. Native Claude keeps owner/harness authentication, pull replication and guarded runtime detail fallback. No new persisted placement state. Qualification is exact-source and provider-specific (`docs/testing.md`).

`Harness.close()` suspends unfinished tasks; Stop alone does not manufacture terminal cancellation records. An admitted explicit root abort can terminally cancel native root/child tasks, without fabricating an assistant-abort public entry. The focused composed PostgreSQL/PGlite proof and its limits are in `docs/testing.md`.

## Ownership and execution

**Placement decision (2026-10-04):** central agents default to asynchronous JavaScript objects in the existing control-plane Node process, not one OS process per orb. No per-orb WorkerThread without demonstrated need. Earlier “worker” terminology referred to a JavaScript object, not a separate process. Stop/Sleep must not terminate the shared process. Each orb has a lightweight stable agent handle for the lifetime of its control-plane process, separate from optional expensive Harness/resources; browser subscriptions survive unload/reopen. **Integrated candidate (locally qualified 2026-10-05):** unload those resources once the host is stopped and the agent is quiescent. If the host stops during active central work, defer unloading until idle and recheck that the host is still stopped. Never interrupt work, children, waits, leases, pending persistence/publication or summaries; inference/MCP remain independent while the host is not running. Do not reopen resources or boot a VM solely to unload them. This supersedes the earlier host-stop-independent eviction policy. **Rejected:** LRU/resource-pressure eviction is unnecessary for the first version; no thresholds or additional FSM are needed.

**Rejected, 2026-10-03:** guest-incarnation-owned Harnesses and upfront `env.ready` in environment factories couple control-plane inference/MCP to VM boot. VM-only lazy factories require independent ownership and central-first inbox/browser admission; removing only the readiness call is insufficient.

**Decision, implemented locally 2026-10-03:** the central agent, browser conversation and inbox delivery must be available before execution readiness. Credential requirements remain. The earlier POC permitted early inference/MCP under partial context; the 2026-10-04 target below supersedes that first-turn permission. Reuse existing lifecycle orchestration with a lazy, incarnation-fenced `ExecutionEnv`: only host-backed operations wait. Eager host boot in parallel is required whenever agent work or a qualifying visible connected browser demands execution; keep execution while either remains, subject to explicit Stop/sleep/archive/delete and terminal-failure fences. The 15-minute grace retains an existing episode, never restarts one. The concrete execution lifecycle, derived aggregate work, dispatch fences and acceptance criteria are in `docs/lifecycle.md`; no agent×VM FSM is proposed. Model/authority instance identity must not be keyed to host incarnation, so host boot failure does not terminate the conversation. Explicit Stop still stops agent work and execution, fencing all pending waits and reprovisioning until fresh authorized intent. Cancelling one tool wait fences only its late dispatch/start authority; surviving independent work or browser demand may still start/keep execution. The current backend is a local process, not a VM; this target also governs future VM adoption. Instruction acquisition/adoption policy is [question 73 (Pi Durable)](open-questions.md).

Recovered live tasks produce a passive `pi-orb.harness-restarted` notice with safe task identities. It is visible in product history but excluded from model input; it does not trigger inference or assert that all guest processes died. Unsafe interrupted effects remain ambiguous.

**Decision, 2026-10-03:** ordinary process-host Stop/Start, including host-spec replacement, preserves the central conversation and authority (SQLite in this historical POC). It requires no additional transcript notice and creates no synthetic model input or inference. Only unfinished-work Harness recovery produces the passive `pi-orb.harness-restarted` notice described above. Explicit Stop/Start adopts fresh managed instructions and retains model/thinking settings for the next real user turn; execution-only idle/replacement is not a managed-instruction refresh guarantee. Scheduled sleep is different: its wake delivers one combined restart/sleep-finished model context and one `pi-orb.sleep-wake` history event.

The requested child surface is generic start/steer/observe/wait/list/cancel, with inherited ordinary configuration and no profile system. MCP/codemode reuse standalone Pi libraries; native orb tools route through application services. The CLI remains for hooks and shell workloads. Acceptance outcomes live in `docs/testing.md`.

**POC integration, 2026-10-03:** MCP uses canonical `mcp__server__tool` names without aliases. Failed optional servers do not block boot; code-mode preflight retries only unavailable discovery before creating its callable snapshot, so consent recovery needs no restart. Newly recovered tools are callable through code-mode; the initial direct-tool registry is not refreshed. Sanitized connection/authentication edges are persisted in tool-result diagnostics and projected into browser history. Compact tool-result manifests expose their committed detail key, not diagnostic text; status assertions must disclose that detail. Central discovery failures persist `durable.mcp_unavailable` with authoritative `needs-auth|unavailable`, fixed `stage=discovery` and sanitized adapter error category; the category alone does not distinguish missing grants from transport failure. OAuth rejection retains generation-aware broker refresh. Execution-host CLI alerts retain the authenticated local endpoint and forward bearer/incarnation-scoped requests to the central native alert writer, without model input. Permanent guest initialization failures propagate through readiness into terminal health instead of leaving creation waiting indefinitely. Bash failures retain bounded output and safe exit/timeout diagnostics; arbitrary exception details remain hidden.

## Assessment

Pi Durable fits the *agent harness*: committed task progress, ownership and recovery address problems pi-orb currently implements around Pi's coding-agent SDK. It does not replace the SDK's complete product surface. **Current proposal (2026-10-02): qualify a central, control-plane-owned Durable harness**, with one Harness object and storage namespace per orb in the existing control-plane Node process. This could remove substantially more coordination than a local swap. The process prototype is authorized; production adoption remains unapproved.

## Potential gains

- Durable task checkpoints and ownership can replace bespoke agent recovery and child-task bookkeeping, including recorded interrupted work and an observable task graph.
- Queued submissions provide request identity and retry-safe admission; they do **not** make external tool effects exactly once. Replayed calls need explicit safety or compensation.
- Background compaction and atomic application documents offer simpler persistence boundaries for agent-local state, subject to durability qualification.
- Central authoritative PostgreSQL-backed harness state could eliminate the orb-local-history → replica split: runtime history pulls, cursors and integrity checks, VM-history drain/seal, duplicate control-plane/local inbox delivery-ack envelopes, and the replica↔live agent WebSocket handoff. This is an architectural gain from **central ownership**, not from `watch` alone. The browser still needs authorized transcript projection, reconnect and gap handling. Browser independence, stopped-orb history and multiple viewers already work today.

## Central ownership and remaining boundaries

- The control plane retains durable admission, wake intent, lifecycle fencing, host reconciliation, notices, crash guards and user-visible failures. Database-idempotent submissions do not magically make wake intent atomic across adapters; define and test their consistency and recovery.
- Use a stable per-orb handle with separately loaded Harness/resources and a storage namespace in the shared control-plane Node process: Stop/Sleep must close only that orb's Harness, not the process. There is no public per-conversation suspension API to assume. Validate store APIs, ownership and a PostgreSQL adapter against the intended concurrency and host-loss semantics; upstream ships no PG adapter or cross-process owner lock.
- One owner must fence stale workers/hosts and tolerate Cloud Run worker shutdown, background CPU limits, reopen/resume and overlapping revisions even with `max instances = 1`. Prefer one simple ownership rule over a speculative scheduler. Host lifecycle and guest `.agents/setup`/`.agents/resume` hooks remain separate.
- Existing archived normalized transcripts can remain; active SDK JSONL is **not** Durable's native store. Cutover needs an explicit decision, not assumed transparent resume or backwards-compatibility scaffolding. Central history still needs normalized authorized projection and browser reconnect/gap recovery; raw views are not public transcripts.
- Non-agent holds (uploads, terminal, ports, hosted files, lifecycle) remain part of busy/drain decisions. Product background children must count as busy and participate in whole-operation abort, unlike Durable's ordinary default that excludes background subtrees.
- An orb-side `ExecutionEnv` adapter is narrower than the old agent runtime, but still owns real workspace filesystem access, shell streaming, cancellation and output spill semantics. Unsafe effects remain ambiguous after interruption; incarnation fences must reject commands against a stale host. Guest terminal, uploads, ports and hosted files do not disappear.
- Central model authentication and MCP can reuse control-plane brokers and reduce guest-held secrets. Untrusted extensions, codemode and remote project tool code must **not** receive control-plane administrator capabilities; sandbox code and scope injected callbacks. This is separate from agent placement. Identity, media, browser protocol, product telemetry and host persistence remain project-owned.

## Safety and durability limits

- The built-in CodingTools default to `unsafe`, including `read`; custom tools may explicitly set `safe`. Replay requires `safe` classification both at recorded intent and registered tool. An interrupted unsafe operation records failure rather than silently rerunning. Treat side-effecting calls and human-visible recovery as separate policy choices.
- Inspected SQLite storage uses WAL with `synchronous=NORMAL`: it survives process crashes, but newest acknowledged commits can be lost on power/host failure. That matters for a local Harness on Spot VMs. JSONL's optional `fsync: true` syncs appended data but the inspected path does not sync the main commit marker. A central PostgreSQL backend would need its own tested commit, failover and host-loss semantics; do not infer durability from a successful local restart.
- One process owns a store at a time; Durable provides no cross-process ownership lock, shipped PostgreSQL adapter or bundled Durable remote execution transport. Separate pi-server/client packages provide service transport, not automatic Harness or `ExecutionEnv` remoting. SQLite file locking is not a substitute for Harness ownership.
- `watch` gives a bounded current snapshot/update stream, not durable cursor replay. Even with central storage, browser reconnect needs an authorized history query and gap recovery. Raw prompt/task views can contain secrets or hidden agent context: project only authorized fields, never publish raw views to browser/history wholesale.
- `close` suspends without terminal outcomes; `abort` cancels terminally, so preemption must not use user abort. `open` alone does not dispatch: `resume`, submission or wait starts scheduling; writes while busy queue. After generation preparation, recovery reuses a pinned request cutoff rather than rerendering current system sections. Qualify whether boot-loaded instructions and host notices become visible **before** resumed inference, and how a queued write interacts with it. [Upstream generation](https://github.com/earendil-works/pi/blob/9b3c19da5cffc4c5e8b6bd74c45abc1ab6bfcd16/packages/durable/src/harness/generation.ts#L119-L209), [spec: model recovery](https://github.com/earendil-works/pi/blob/9b3c19da5cffc4c5e8b6bd74c45abc1ab6bfcd16/packages/durable/docs/spec.md#L3395-L3409), [spec: busy raw writes](https://github.com/earendil-works/pi/blob/9b3c19da5cffc4c5e8b6bd74c45abc1ab6bfcd16/packages/durable/docs/spec.md#L4450-L4463), [session](https://github.com/earendil-works/pi/blob/9b3c19da5cffc4c5e8b6bd74c45abc1ab6bfcd16/packages/durable/src/session/session.ts#L350-L373).
- Task admission is not exactly-once external execution; failpoints must cover commit-before/after tool effect, model response, child completion and host interruption. No performance, cost or failure-rate claims are made from source inspection.

## Pi 1.4 decision (user-approved 2026-10-22, PDT)

**Approved persisted-state scope:** `docs/open-questions.md`, question 82. Published [1.4.0](https://github.com/earendil-works/pi/tree/v1.4.0), not unreleased main, requires persisted-state changes:

- One PostgreSQL/PGlite migration widens the existing `durable_pg_tasks.status` CHECK for `sleeping`. Existing task `record` JSON stores `state.until`, its checkpoint and `TaskRecord.restarts`; no new columns/tables. Sleeping tasks remain unfinished in recovery-demand, busy and drain checks. Graceful close returns running tasks to pending; crash recovery counts consecutive interruptions without state progress and parks at five by default.
- Native `CodemodeStoreDoc` writes a base after 64 deltas using existing revision storage; values, rewind/as-of-fork semantics and document version remain unchanged. Six custom document definitions use explicit `checkpointWhen: () => false` to preserve their existing delta policy.
- No completed-history rewrite, store-value reset/import, auth-file migration or persisted trace carriers. Default Chord telemetry contexts are no-ops; propagation stays off. Parking must explain the pause to the user and retain safe task/reason facts through existing `server.error` and durable `harness.reported_failure` / `harness.execution_blocked` edges; no new flags.

Parking is not a fatal storage failure. Root snapshots and the existing Abort operation remain available; the existing `server.error` explains that Abort abandons the interrupted turn before fresh input. A derived, nonpersisted snapshot notice replays through the normal central browser handshake, including late attachment through `StableAgentHandle`; terminal settlement removes it. The existing browser error frame uses `central_agent_paused`, cleared only when the operation settles; unrelated errors remain. Reopen, ordinary Start and queued input preserve restart counters, never silently retry a parked task. Independent background children do not fail root health; `cancel_subagent` commits cancellation control before calling the bound public Harness abort and waiting for scope drain. The native abort clears restart bookkeeping.

Source comparison finds unchanged native task/document versions, code-mode module version and VM inputs, not proof of transparent unfinished-task replay. Preserve replay refusal for fingerprint/version mismatch, divergence or expired deadlines, and unsafe-effect restrictions. Completed receipts, public history and native store values remain readable; unfinished scripts obey native replay rules, not a general live-upgrade guarantee.
