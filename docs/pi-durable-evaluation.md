## Storage target decision (2026-10-04)

**Decision:** authoritative Pi Durable persistence must use pi-orb's PostgreSQL, including private agent history/execution state and a separate user-visible transcript. Duplication is accepted for simple privacy and independent lifetimes: archive publishes/drains/seals the transcript, then deletes agent history/execution state while retaining the transcript. Canonical native entries plus thin public references are rejected for retention coupling. A separate SQLite authority is not an acceptable target: durability belongs in the existing database, not a second persistence system. Per-orb SQLite belongs to the earlier qualified process POC; the integrated candidate uses PostgreSQL. Earlier restart evidence does not qualify this candidate. Each causal mutation must atomically commit native state and all required public projection/enrichment/cursor/dedup updates in the same PostgreSQL transaction, including applicable receipts, admission and owner fences. No asynchronous projection-repair substitute; readers never see half-state and notifications follow commit. Remaining qualification is tracked in `TODO.md`; the unit-of-work, recovery and archive contract is in `docs/history-replication.md`.

This decides storage, not production adoption. Question 72 (Pi Durable) in `docs/open-questions.md` remains open for ownership, security, supported-product parity and recovery qualification. No dual-store compatibility phase is required.

## Integrated candidate (rebased 2026-10-05; scoped validation passed; undeployed)

The same private-authority/public-projection adapter runs against PostgreSQL and PGlite. Owner leases use the database clock; an instance-bound bounded drain capability permits already-admitted cleanup after admission revocation, never new submission/model/effect dispatch. Archive atomically checks/seals the current public head and purges private native state, repository snapshots and artifacts; delete removes both lifetimes. Stable handles retain metadata only; passive transcript reads query PostgreSQL without loading a Harness. Stopped-and-quiescent unloading is deferred while work remains, rechecks persisted state, and never aborts work or boots compute merely to unload.

This integration is undergoing fresh validation, not qualified by earlier gates. ## Assessment

Pi Durable fits the *agent harness*: committed task progress, ownership and recovery address problems pi-orb currently implements around Pi's coding-agent SDK. It does not replace the SDK's complete product surface. **Current proposal (2026-10-02): qualify a central, control-plane-owned Durable harness**, with one Harness object and storage namespace per orb in the existing control-plane Node process. This could remove substantially more coordination than a local swap. The process prototype is authorized; production adoption remains unapproved.

**Earlier local-only assessment (2026-10-02), superseded as the first recommendation:** one Harness inside each orb preserved the existing boundary and avoided remote execution, workspace access, latency and trust changes. It also preserved the replica split and most of its machinery; that omission underweighted centralization. A local prototype remains a narrower fallback, not the recommended first test.

Measured local integration scope, **not an upper bound on central simplification or a deletion estimate**: 671 physical lines in focused recovery/child files plus portions of the 2,054-line runtime `agent.ts`; about 5,963 lines of broadly affected runtime integration versus ~55,000 production TypeScript physical lines across pi-orb. These surfaces overlap. No defensible central or net LOC count exists without a parity implementation.

## Potential gains

- Durable task checkpoints and ownership can replace bespoke agent recovery and child-task bookkeeping, including recorded interrupted work and an observable task graph.
- Queued submissions provide request identity and retry-safe admission; they do **not** make external tool effects exactly once. Replayed calls need explicit safety or compensation.
- Background compaction and atomic application documents offer simpler persistence boundaries for agent-local state, subject to durability qualification.
- Central authoritative PostgreSQL-backed harness state could eliminate the orb-local-history → replica split: runtime history pulls, cursors and integrity checks, VM-history drain/seal, duplicate control-plane/local inbox delivery-ack envelopes, and the replica↔live agent WebSocket handoff. This is an architectural gain from **central ownership**, not from `watch` alone. The browser still needs authorized transcript projection, reconnect and gap handling. Browser independence, stopped-orb history and multiple viewers already work today.

## Central ownership and remaining boundaries

- The control plane retains durable admission, wake intent, lifecycle fencing, host reconciliation, notices, crash guards and user-visible failures. Database-idempotent submissions do not magically make wake intent atomic across adapters; define and test their consistency and recovery.
- Use a stable per-orb handle with separately loaded Harness/resources and a storage namespace in the shared control-plane Node process: Stop/Sleep must close only that orb's Harness, not the process. There is no public per-conversation suspension API to assume. Validate store APIs, ownership and a PostgreSQL adapter against the intended concurrency and host-loss semantics; upstream ships no PG adapter or cross-process owner lock.
- One owner must fence stale workers/hosts and tolerate Cloud Run worker shutdown, background CPU limits, reopen/resume and overlapping revisions even with `max instances = 1`. Prefer one simple ownership rule over a speculative scheduler. Host lifecycle and guest `.agents/setup`/`.agents/resume` hooks remain separate.
- Existing archived normalized transcripts can remain; active SDK JSONL is **not** Durable's native store. Cutover needs an explicit decision, not assumed transparent resume or backwards-compatibility scaffolding. Central history still needs normalized authorized projection and browser reconnect/gap recovery; raw views are not public transcripts.
- Non-agent holds (uploads, terminal, ports, hosted files, lifecycle) remain part of busy/drain decisions. Product background children must count as busy and participate in whole-operation abort, unlike Durable's ordinary default that excludes background subtrees.
- An orb-side `ExecutionEnv` adapter is narrower than the old agent runtime, but still owns real workspace filesystem access, shell streaming, cancellation and output spill semantics. Unsafe effects remain ambiguous after interruption; incarnation fences must reject commands against a stale host. Guest terminal, uploads, ports and hosted files do not disappear.
- Central model authentication and MCP can reuse control-plane brokers and reduce guest-held secrets. Untrusted extensions, codemode and remote project tool code must **not** receive control-plane administrator capabilities; sandbox code and scope injected callbacks. This is separate from agent placement. Identity, media, browser protocol, product telemetry and host persistence remain project-owned.

### Reuse assessment

**Earlier reuse assessment (2026-10-02):** the broad inventory below is subject to the supported-product scope decision above; it does not authorize every listed SDK feature. The process POC's generic child surface supersedes profile-porting as its requirement.

- Port agent session/tool/history mapping, root/child lifecycle, cancellation, settings, prompts and context. The Pi coding-agent extension API is not natively compatible with Durable definitions: port or adapt native MCP/codemode broker and discovery, subagent profiles/spawn/steer/results receipts, image read, and the current browser input contract. `@gotgenes/pi-subagents` is a third-party extension named for its author/namespace; pi-orb currently uses a patched fork for cancellation and parent-wake behavior, not a core Durable feature. Preserve resource loading and broker diagnostic auth seams.
- Reuse coding-agent's exported `ModelRuntime`, settings and resource-loading helpers where appropriate, plus context/skills helpers and the existing normalized history schema. This is not a rewrite of every Pi-related library.
- Built-in Durable `read` does not support images, and the inspected demo excludes them; that does **not** establish that Durable cannot accept image inputs anywhere. Test image-bearing tools and model messages separately.
- Reassess SDK-specific patches case by case rather than assuming they all survive or all disappear. The AI diagnostic patch likely remains relevant. In particular, do not assume the custom-turn preparation patch is eliminated: boot notices and freshly loaded instructions must be ordered before any resumed inference.

One possible placement runs `CodemodeSandbox` centrally with **only scoped injected callbacks**: project `read`/`bash` callbacks could call the orb through authorized RPC, while MCP callbacks use the central broker. Each `sandbox.execute()` creates a fresh Node Worker (Bun worker on Bun) and QuickJS WASM VM; this library-owned sandbox lifetime is separate from agent placement, not a per-orb agent WorkerThread; calls cross back to supplied callbacks on the host thread ([host](https://github.com/earendil-works/pi/blob/9b3c19da5cffc4c5e8b6bd74c45abc1ab6bfcd16/packages/codemode/src/runtime/host.ts), [worker](https://github.com/earendil-works/pi/blob/9b3c19da5cffc4c5e8b6bd74c45abc1ab6bfcd16/packages/codemode/src/runtime/worker.ts)). The script receives no direct filesystem, network, process or `require` capability by default. CPU-bound QuickJS runs off the **host event loop**; asynchronous injected calls message to host callbacks and return results. Synchronous callbacks and JSON serialization can still block that loop. A worker thread is **not** a separate security principal: callbacks retain host permissions, and the VM memory limit is not a process quota. Central placement is authorized for the process POC; production sandbox isolation, scoped authorization and resource qualification remain separate acceptance requirements.

### MCP/codemode adapter, not a rewrite

**Pre-candidate adapter audit (2026-10-04):** `pi-mcp` client and `pi-codemode` sandbox are independent libraries used unchanged; pi-orb's wrappers are narrow adapters, not forks. The standalone MCP client implements resources and server instructions. The central Durable adapter exposes only tools and does not load the coding-agent SDK MCP extension. The matrix records an adapter exposure gap, not a standalone-library limitation or an approval to add features.

Today pi-orb composes native SDK `createMcpExtension` and `createCodemodeExtension` in [`apps/orb-runtime/src/pi/extensions/index.ts`](../apps/orb-runtime/src/pi/extensions/index.ts); both operate in the same session/tool catalog (see [`native-mcp-sdk.contract.test.ts`](../apps/orb-runtime/src/pi/native-mcp-sdk.contract.test.ts)). This proves the existing SDK route, **not** a ready Durable adapter. Standalone MCP async calls compose with sandbox-injected async functions. The proposed bridge would register `defineTool` definitions, discover MCP tools, map schema/names and validate authorized callable arguments; route environment calls through fenced orb RPC and MCP through scoped broker callbacks; translate text/images, typed errors and progress; bridge Chord `Context` cancellation to sandbox/tool `AbortSignal`; and close connections/workers. Sandbox schemas render model declarations but **do not validate nested arguments**: callable adapters must validate them. Durable validates outer tool parameters; its outer replay classification/checkpoint does not automatically checkpoint nested calls inside one codemode script. [Durable tool API](https://github.com/earendil-works/pi/blob/9b3c19da5cffc4c5e8b6bd74c45abc1ab6bfcd16/packages/durable/src/harness/define.ts), [codemode README](https://github.com/earendil-works/pi/blob/9b3c19da5cffc4c5e8b6bd74c45abc1ab6bfcd16/packages/codemode/README.md), [MCP README](https://github.com/earendil-works/pi/blob/9b3c19da5cffc4c5e8b6bd74c45abc1ab6bfcd16/packages/mcp/README.md).

### Wrapper vendoring rationale (2026-10-04)

The [vendoring audit](/workspace/orb-feedback-evidence/wrapper-vendoring-audit.md) supports a small extraction of **~500–700 portable TypeScript lines** (estimate): descriptions/namespaces, catalog budget, BM25 discovery, result formatting and truncation policy. Reuse public parser, grammar, declaration renderers and sandbox exports; do not vendor those libraries. The whole SDK extension is not drop-in, and a fake `AgentSession` would import unnecessary behavior without Durable guarantees. The candidate selected this focused extraction, retaining source provenance/version/hashes, adaptation notes, copyright and complete MIT notice. The estimate remains historical; the initial worker report measured 547 TypeScript lines.

The candidate implements the required capture/finalization of nested output, diagnostics and details before script-result conversion; preserve full MCP results, output schemas, namespaces/exposure and server instructions; route remote execution through existing authorization, admission and cancellation; provide scoped accessible spill artifacts; retain the `orb.codemode-store` Durable document (`history:'latest'`, `fork:'initial'`), atomic changed-key writes via `api.commit` only on success, and sanitized durable nested-call/store/spill/failure telemetry with user-visible failures. `only` mode must hide direct declarations while keeping authorized nested calls callable for root and children. Copying wrapper policy supplies none of those guarantees and requires no new child implementation.

**Pre-candidate nested-result finding:** results are not universally envelopes. Built-in Durable `createBashTool()` (not a durable-shell promise) streams success through `api.output` and returns `{}`; direct Harness finalization materializes that output. The earlier nested catalog invocation bypassed successful-output finalization, so the script receives `{}` and streamed output is not automatically included in codemode's explicit final content. Bash failure capture already retains a bounded 50 KiB byte-tail in `ToolError.output`; codemode's message-only rejection drops that captured output. These were distinct adapter gaps, corrected by candidate materialization and bounded typed failures; they did not imply absence of all capture or empty output for every bash outcome.

### Service protocol boundary

`pi-client` exposes a transport-neutral client root and `pi-server` a listener abstraction; an ordered-byte browser WebSocket adapter needs qualification (including bundling), not a new agent loop. Pi-orb would define its own Chord Session/management services and normalized, filtered history projection. Upstream [`experimental/services`](https://github.com/earendil-works/pi/blob/9b3c19da5cffc4c5e8b6bd74c45abc1ab6bfcd16/packages/coding-agent/src/experimental/services/README.md) has source-only `AgentController`, `Models`, `SessionDirectory`, management and `Transcript` examples excluded from the npm package; its active `ConversationView` is neither complete history nor a privacy-safe public transcript. Protocol framing does not supply authentication or a principal in service contexts. `attachClient` receives Chord `Context`; the server constructs an abort-scoped context without propagating an authenticated transport principal. Authenticated connection admission alone cannot scope viewer-specific directories or history queries: qualify scoped host/router composition or an upstream identity-propagation seam. Custom transports and service schemas remain adequate integration seams. Reconnection, history gap recovery and worker lifetime remain application-owned. [Server README](https://github.com/earendil-works/pi/blob/9b3c19da5cffc4c5e8b6bd74c45abc1ab6bfcd16/packages/server/README.md), [client README](https://github.com/earendil-works/pi/blob/9b3c19da5cffc4c5e8b6bd74c45abc1ab6bfcd16/packages/client/README.md).

## Safety and durability limits

- The built-in CodingTools default to `unsafe`, including `read`; custom tools may explicitly set `safe`. Replay requires `safe` classification both at recorded intent and registered tool. An interrupted unsafe operation records failure rather than silently rerunning. Treat side-effecting calls and human-visible recovery as separate policy choices.
- Inspected SQLite storage uses WAL with `synchronous=NORMAL`: it survives process crashes, but newest acknowledged commits can be lost on power/host failure. That matters for a local Harness on Spot VMs. JSONL's optional `fsync: true` syncs appended data but the inspected path does not sync the main commit marker. A central PostgreSQL backend would need its own tested commit, failover and host-loss semantics; do not infer durability from a successful local restart.
- One process owns a store at a time; Durable provides no cross-process ownership lock, shipped PostgreSQL adapter or bundled Durable remote execution transport. Separate pi-server/client packages provide service transport, not automatic Harness or `ExecutionEnv` remoting. SQLite file locking is not a substitute for Harness ownership.
- `watch` gives a bounded current snapshot/update stream, not durable cursor replay. Even with central storage, browser reconnect needs an authorized history query and gap recovery. Raw prompt/task views can contain secrets or hidden agent context: project only authorized fields, never publish raw views to browser/history wholesale.
- `close` suspends without terminal outcomes; `abort` cancels terminally, so preemption must not use user abort. `open` alone does not dispatch: `resume`, submission or wait starts scheduling; writes while busy queue. After generation preparation, recovery reuses a pinned request cutoff rather than rerendering current system sections. Qualify whether boot-loaded instructions and host notices become visible **before** resumed inference, and how a queued write interacts with it. [Upstream generation](https://github.com/earendil-works/pi/blob/9b3c19da5cffc4c5e8b6bd74c45abc1ab6bfcd16/packages/durable/src/harness/generation.ts#L119-L209), [spec: model recovery](https://github.com/earendil-works/pi/blob/9b3c19da5cffc4c5e8b6bd74c45abc1ab6bfcd16/packages/durable/docs/spec.md#L3395-L3409), [spec: busy raw writes](https://github.com/earendil-works/pi/blob/9b3c19da5cffc4c5e8b6bd74c45abc1ab6bfcd16/packages/durable/docs/spec.md#L4450-L4463), [session](https://github.com/earendil-works/pi/blob/9b3c19da5cffc4c5e8b6bd74c45abc1ab6bfcd16/packages/durable/src/session/session.ts#L350-L373).
- Task admission is not exactly-once external execution; failpoints must cover commit-before/after tool effect, model response, child completion and host interruption. No performance, cost or failure-rate claims are made from source inspection.

## Qualification scope

The process POC is authorized, tests first. Acceptance includes deterministic scheduling/failpoints and replay traces for ownership, worker overlap/shutdown/reopen, admission/wake consistency, child cancellation/drain, unsafe-tool interruption and stale-host fencing; process-kill/reopen acceptance; separate production adoption requires host-loss and database-failover qualification; remote filesystem/shell streaming/cancellation/spill; browser reconnect, history privacy and user-visible outcomes. Verify MCP/codemode isolation, broker auth, settings, managed personal/project prompts, supported image/skill behavior, boot-notice/current-instruction ordering, archive/history continuity and active-session cutover within the supported-product scope above. Persist diagnostic edges and expose failures to users, rather than relying on worker/guest stdout. Passing these gates informs adoption; it does not approve it.
