## Response copy (Corner action selected and implemented, 2026-09-16)

**Selected: Corner action.** Every non-empty assistant response has the shared copy icon at the top right of its first non-empty text block. A historical response with multiple text blocks still has one action: placement belongs to the first block while copied source joins every non-empty text block in original order with `\n\n`. This minimal boundary preserves existing tool grouping. Short, long, fenced-code and mixed-block responses reserve the action width so content cannot overlap it or overflow. Phone response blocks also reserve the action's 44px height, and feedback stays in the narrower content lane. Desktop reveals the action when its response block is hovered or contains keyboard focus, not when an unrelated part of the surrounding agent turn is hovered. Touch and phone layouts keep it visible; phone targets are 44px square. Inline tail was rejected after use by user preference.

Copy uses raw Markdown source, preserving fences, links, emphasis and whitespace rather than copying rendered text. Reasoning, tool calls/results, images, errors, custom events, user messages and empty thinking/tool-only responses are excluded. Before commit, the protocol exposes only live text-block identity, so each non-empty live text block is one truthful copy boundary. Normal live/history handoff retains the renderer's existing ownership: the live action leaves with its block and the committed record action replaces it; source-text equality is never used to deduplicate.

The action uses `copyToClipboard`, including its established user-gesture textarea fallback for plain-HTTP deployments. Success shows a green icon with an accessible `copied` announcement and no visible text; exhausted clipboard paths say `copy failed`, never success. Both are announced, and the button's accessible name changes with the result. Failed feedback and its action remain visible until another attempt. Existing fenced-code copy remains independent. Copying is browser-local: no runtime call, persistence, protocol change or telemetry.

**Batch notification revised 2026-09-09:** a multiple-file selection must generate a single agent message, not one per file. The backend atomically registers the selection before transfers begin and notifies once every member is stored or cancelled. Failed members remain retryable; explicit cancellation excludes them from the eventual successful-file list. Retries and recovery reuse one batch message identity and immutable body. Separate selections remain independent. This supersedes the first implementation's per-file notification simplification.

**Initial proposal (refined by implementation as documented in `docs/workspace-uploads.md`):** choose multiple files in the header dialog and upload independently of the composer draft. Finalize each file before notifying the model; never expose a partial file at its announced path. Send one model-visible, persisted notification per selection batch listing only successfully finalized files, their exact paths, and sizes, without embedding arbitrary file contents or automatically executing/extracting them. Preserve original names when possible, assign a distinct name on collision rather than silently overwriting, and make retries reuse the transfer identity so they do not duplicate files or notifications. User-visible transfer state distinguishes file-storage success from notification-pending/failure; durable operation outcomes make that distinction reconstructable. Uploaded files follow workspace retention, not hosted-file publication semantics.

Placement, ordinary-inbox notification, and running-only admission are resolved in `docs/open-questions.md`, question 61. Transfer API, backend, and frontend are now implemented; remaining live-platform validation is tracked in `TODO.md`.

**Streaming data-flow proposal:** the browser creates a small metadata-only transfer session, then sends sequential bounded `File.slice` request bodies (proposed chunk size: 4 MiB) through the authenticated control plane to the runtime, which incrementally hashes/counts and writes them to an owned staging file on the workspace disk. The control plane forwards the request stream with backpressure and never parses file bodies as JSON, multipart collections, or whole buffers. File bytes never enter PostgreSQL, WebSockets, message history, or model input. Chunking bounds individual requests below Cloud Run's HTTP/1 request limit and limits the effect of infrastructure buffering; it does not claim control over browser, IAP, or platform internals. Memory scales with bounded per-transfer buffers and actual concurrent transfers, not total file length. The user explicitly declined separate concurrency admission/limiting machinery; retain sequential chunk sending and backpressure, without claiming a concurrency-independent process memory bound. File-size, quota, and deadline policy is tracked separately in `docs/open-questions.md`, question 59.

Each request binds transfer identity, expected byte offset, and bounded chunk length; the runtime serializes writes per transfer, acknowledges only durable committed offsets, and recovers/truncates any unacknowledged staging tail before further writes. A lost acknowledgement is reconciled by querying that offset instead of blindly appending. Completion checks total length and accumulated digest, durably publishes the file without replacement, and enqueues the notification through the existing message inbox. Workspace-persisted transfer metadata owns recovery across runtime restart; a stable batch-derived message identity and immutable notification body let a retry reconcile inbox acceptance without creating a duplicate message. File publication and inbox acceptance are not one transaction: the crash windows require explicit recovery, not a claim that atomic rename solves both. A successfully stored file with notification pending remains an explicit user-visible outcome. An interrupted transfer does not request startup or claim success. **Decided (2026-09-08):** if Stop wins before notification inbox acceptance, keep the notification pending until explicit startup, without restarting compute. Inbox acceptance must suppress upload-driven wake under that race, not merely perform a separate running-state precheck. Question 60 in `docs/open-questions.md` records the resolution.

**Transfer activity requirement (decided 2026-09-08):** the whole active transfer, including inter-chunk gaps and finalization, prevents idle auto-stop even with an idle agent and hidden browser tab. This must not masquerade as model busy activity. Terminal outcomes release protection; abandoned transfers expire rather than protecting compute forever. Explicit Stop still wins. Admission/idle-stop ordering, idle-anchor refresh, durable observability, and required DST are specified in `docs/lifecycle.md`.

**Notification decision (2026-09-08):** use the existing durable message inbox, starting an idle agent or steering an active one as an ordinary message does. The earlier context-only proposal is rejected for its dedicated adapter operation, safe-boundary scheduling, and additional recovery/testing burden. Ordinary inbox delivery and history replication carry the notification without the control plane inventing replica records.

**Validation proposal:** production transfer/inbox coordination runs under DST with simulated streams, disk durability, clocks, inbox acceptance, and lifecycle fences. Assert no notice before durable publication, no duplicate final file/notice on retry, no silent overwrite, no stale-incarnation mutation, bounded per-transfer outstanding chunks, and eventual recovery/cleanup once faults cease. Force crashes at chunk-write/flush/offset-commit, publication/metadata-commit, and inbox-acceptance/notification-ack boundaries; include retry, concurrent same-name uploads, cancel, disk full, stop/replacement/archive/delete, and replication/live handoff schedules. No dedicated context-only scheduler or global concurrency-limiter DST is needed. Fake persistence must distinguish volatile writes from durable state. Real socket/stream adapter tests verify backpressure and cancellation; filesystem contracts establish that the fakes match actual behavior. Chromium/runtime E2E proves binary byte identity, running-only upload visibility, and ordinary inbox delivery; live Cloud Run/IAP validation establishes large-file transfer and measured per-transfer memory bounds, which DST cannot prove.

## Comprehensive frontend failure handling (current proposal, 2026-09-03)

A field report found that submitting a message after the Google IAP browser session expired appeared to do nothing; reloading then entered Google authentication. The current HTTP adapter collapses a failed IAP redirect/CORS exchange into a generic network error, and the orb page renders mutation errors above the transcript, far from the sticky composer where the user is looking. This is a general failure-model and placement defect, not just missing auth copy.

The proposed model has one typed browser transport boundary and small UI state machines rather than a notification framework or query-cache dependency:

- classify `auth_required`, `offline`, `timeout`, validated control-plane HTTP errors, invalid responses, WebSocket protocol failures, cancellation, and unexpected framework failures separately; user-facing copy is derived from those facts rather than embedded in the adapter;
- test IAP's documented AJAX behavior (the `X-Requested-With` request signal) against the live deployment and use an explicit 401 as the primary expired-session signal if validated; because browser WebSockets cannot set that header, classify a suspicious live/terminal socket close with a bounded same-origin HTTP probe rather than guessing that every disconnect means expired auth;
- route by scope: auth is persistent app-wide state, a foreground mutation owns an error adjacent to its initiating control, a failed initial read owns the page, and polling/socket degradation marks data stale or reconnecting without repeating banners;
- cover every browser boundary, not only conversation submission: route-critical project/orb/history/message reads; partial project-orb, secret, and search reads; project/orb create and rename forms; secret writes; start/stop/archive/delete lifecycle mutations; shell and abort requests; background polls/history refreshes; agent and terminal WebSockets; and local Clipboard, FileReader, Notification, and React render boundaries. A shared transport classifier is exhaustive, but a generic global error queue is rejected because only the operation owner knows whether to preserve a form, mark a section stale, reconcile an ambiguous mutation, or retry;
- preserve user intent until success is authoritative. The composer clears only after the durable message `202`; a transport timeout says the result is unconfirmed, not that the server did not receive it; retries reuse the exact message ID and body. Other ambiguous mutations reconcile their resource before offering retry unless their contract is idempotent;
- enter IAP reauthentication through a same-tab top-level reload; opening another copy of the app was rejected after field testing because it left the original tab visibly expired and made recovery appear ineffective. The orb composer persists its per-orb text, mode, and image attachments in tab-scoped session storage and restores them after the round trip; other recoverable forms must gain equivalent scoped preservation before this broader proposal is complete;
- add bounded deadlines to foreground HTTP calls, ensure every pending action reaches a terminal reducer state, and put a route-level React error boundary around unexpected render failures while keeping expected failures in `Result` values;
- expose sanitized copy plus a correlation/diagnostic identity when available. Record transport class, route template, operation kind, build, and recovery outcome without message text, secret values, URLs carrying user input, or attachment bytes. Authentication telemetry may be blocked by IAP and can be submitted only after connectivity returns; IAP access logs remain the authority for intercepted requests.

**Session-expiry presentation decided and implemented 2026-09-03.** Use the **Session ribbon**: a persistent app-wide strip above the route chrome says `session expired` and offers **sign in again**. The 2026-09-03 second line warning that changes and live updates may be paused was dropped on 2026-09-04: a strip that stays on screen until sign-in already says the session is not working. A 401 from any browser API request activates it. Every API request sends IAP's AJAX signal (`X-Requested-With: XMLHttpRequest`) so expiry returns a classifiable 401 instead of a Google redirect flattened into a CORS/network error. Live unauthenticated probes on 2026-09-03 confirmed the real edge returns HTML `302` to Google without the signal and HTML `401` without a redirect with it (`docs/testing.md`). The sign-in action performs a same-tab top-level reload, allowing IAP to run its ordinary Google redirect and return directly to the requested hash; opening a second app tab was rejected after field testing because it neither repaired nor cleared the original tab. Non-empty composer text, explicit mode, and image attachments are mirrored to per-orb `sessionStorage`, removed after the composer returns to its empty message state, and restored after reload; a storage denial or quota failure is contained at that browser boundary and shown in the orb's existing notice surface rather than silently promising preservation. Whenever a still-mounted window regains focus it also calls the state-free `GET /api/v1/session` reachability probe, and a request begun after the last 401 must reach the application before the ribbon clears. Request sequence ordering prevents an older concurrent success from incorrectly clearing a newer auth failure. The compact orb header and the project index remain sticky immediately below the ribbon.

The ribbon communicates the shared authentication cause; it does not replace operation-local outcomes. Existing action errors remain where the operation owner can say whether a form was preserved, a mutation was rejected, or an outcome is uncertain. Generic transient toasts are rejected as the primary treatment because they disappear, detach from the affected action, and are easy to miss. A modal is reserved for an operation that cannot safely leave the current state, not ordinary session expiry. [`design-prototypes/frontend-error-handling.html`](../design-prototypes/frontend-error-handling.html) contains the implementation plan, complete request-coverage map, failure matrix, selected Session ribbon, and four alternatives. The remaining comprehensive operation-local work is tracked in `TODO.md`.

## Frontend-only development (decided 2026-08-06)

**Shared-preview verification rule (2026-09-09):** after fixture-backend or shared-protocol changes, fully stop and restart the frontend process. Do not rely on Vite's internal config reload: Node can retain old external protocol exports while browser HMR loads a new client, and a failed backend reload can leave stale middleware serving HTTP 200. Inspect the actual process's startup/reload logs and smoke-test the changed operation on the exact shared service before calling it updated. Fresh-instance E2E on another port does not establish that a long-running preview loaded the change. Back up needed fixture state first; process restart resets it. Evidence and recovery: `docs/postmortems/2026-09-09-stale-frontend-preview.md`.

Two Docker-free development compositions exist and must not be confused:

- **Full service with process-hosted orbs:** run `npm run dev:local` for the control plane/SQLite/process supervisor and `npm run dev --workspace @pi-orb/web` for the normal web server. This exercises real Pi runtimes, lifecycle, protocol, replication, credentials, and model inference, but runs repository code unsandboxed (`docs/host-provider.md`).
- **Frontend-only fixture:** run only `npm run dev:frontend`. Vite replaces the HTTP/WebSocket backend in process; no control plane, database, orb process, Pi session, or model call exists.

The web workspace's in-process fixture is activated by Vite's `frontend` mode. Run it with:

```sh
npm run dev:frontend
```

This starts only Vite and needs no PostgreSQL, Docker, control plane, runtime, credentials, or model service. It is not the frontend command for `npm run dev:local`; that full-service composition uses the normal `npm run dev --workspace @pi-orb/web` command in a second terminal. The fixture owns the `/api/v1` HTTP routes and live agent/terminal WebSocket upgrades on the Vite server. It starts with a running orb and short conversation, the long-history performance orb, a starting orb with an OpenAI device-login challenge, and an archived orb. The all-project index fixture also seeds fieldnotes with two stopped orbs, homelab with a failed backup orb, and an empty scratchpad project so cross-project navigation, failure state, and title-plus creation are immediately usable; messages receive a simulated streamed echo, user-shell commands receive simulated streamed command output and persisted `pi.bash_execution` records (including excluded-context state), the terminal shade receives a deterministic binary echo/prompt over the real terminal controls, and start, stop, project/orb creation, history reload, and abort use the real browser-facing contracts. Newly created fixture orbs remain in `creating` for about 10 seconds before becoming `running`, so the editable-while-send-is-unavailable composer behavior can be exercised manually.

The fixture includes a small fixed **frontend fixture · session active** development control in the lower-right corner. **expire session** changes only the fixture transport boundary: it terminates fixture WebSockets and makes every `/api/*` request return an IAP-like HTML 401; **restore session** admits requests again. Reloading the page while expired—what the real ribbon action does—skips an external identity page, restores the fixture session, and returns to the same hash, modeling a successful same-tab IAP round trip. Manual toggles also dispatch an ordinary window-focus event, so production `SessionRibbon` code performs its real `/api/v1/session` probe and state transition. The control and its private `__pi_orb_fixture` endpoints are injected by the Vite plugin and do not exist in the React tree or production build. `npm run test:e2e:frontend` drives this exact fixture control in Chromium and proves HTML-401 detection, ribbon visibility, same-tab load, hash retention, session recovery, and composer-draft restoration.

The fixture is a transport-level adapter, not a mock branch in React. Production UI code still calls the same relative HTTP URLs, validates the same `@pi-orb/protocol` schemas, and runs the same WebSocket reducer. This keeps frontend-only behavior representative and makes protocol drift fail visibly. It is intentionally ephemeral and process-local: restarting Vite resets all fixture data, and it is for manual UI development rather than backend or E2E correctness. Normal `npm run dev --workspace @pi-orb/web` retains the proxy to the real control plane.

## Dashboard orb update age and ordering (decided and implemented 2026-08-26; placement revised 2026-09-04)

## Visual design (decided 2026-09-04)

The UI uses **Signal / Boards**, selected from [`design-prototypes/signal-boards.html`](../design-prototypes/signal-boards.html). The exploration trail is [`design-prototypes/ui-redesigns.html`](../design-prototypes/ui-redesigns.html) (ten directions), [`design-prototypes/mono-minimal-variations.html`](../design-prototypes/mono-minimal-variations.html) (five typography variations of the selected monospace direction), and [`design-prototypes/signal-dashboard-variants.html`](../design-prototypes/signal-dashboard-variants.html) (three dashboard layouts). The prototype ships in its **wrap-fixed** overflow mode only; masonry, sideways scrolling, and the dense 220px column were rejected. The dashboard's weight problem — a board that looked unfinished at one project and thin at three — was studied separately in [`design-prototypes/signal-dashboard-substantial.html`](../design-prototypes/signal-dashboard-substantial.html) as six proposals: a full-height ruled board, a fleet strip with a system footer, large type, a recent-activity ledger, a fixed slot grid, and the combination that shipped (strip, footer, full-height columns, and moderate type). The combination won because it is the only one that holds at every project count without inventing content: the ledger and the slot grid both fill space with rows and boxes that say nothing new.

It replaces the "Reading Room" variant of the Manuscript × Gutter design, whose serif reading typography, warm paper palette (`#f8f3e9` / `#221c12` / terracotta), turn gutter with `Y`/`O` marks and rails, and rounded per-project panels were made for a reader being introduced to a product. There is one user, who already knows what this is; the dashboard's job is to say what every orb is doing at a glance, and the transcript's job is to be read. Light mode only remains an explicit product decision.

Decisions:

- **One face, one grid.** The existing system `--mono` stack (`ui-monospace`, SF Mono, Menlo, Consolas, Liberation Mono) at 13px on a 20px line, tabular numerals, everywhere. No webfonts. Headings are uppercase bold with `letter-spacing: .08em`. Size ranks exactly two things, both on the dashboard board and both since 2026-09-04: the project name and the New Project heading at 18px on a 24px line, and the orb name at 14px on a 22px line. Everything else, including every other heading, stays at 13px on the 20px line.
- **White ground, black ink, three greys, two signal hues.** `--w #fff`, `--k #000`, `--g1 #f2f2f2` (fills), `--g2 #999` (hairlines, disabled), `--g3 #555` (secondary text); `--ok #1a7e37` for alive-right-now and `--bad #b42318` for gone-wrong, each with a pale background. Every lifecycle state also owns a hue (`--st-busy/idle/start/stop/fail/arch/del`) used wherever that state appears.
- **1px black rules, `#f2f2f2` hairlines, zero radius, no shadows, no gradients.** Focus and the current row are inversion (black ground, white text), not a tint. Links are a 1px underline and invert on hover.
- **State is an Instrument tile (revised 2026-09-17).** Every orb state uses the same SVG asset in tabs and the UI: ring for idle, dots for busy, hourglass for transition, minus for stopped, slender crescent for sleeping, cross for failed, inset box for archived, arrow for archiving, and bin for deleting. The neutral tile carries π. Each UI tile is 16px with a native state tooltip and accessible name (decorative where adjacent text already names the state). A row carrying a state also carries a 2px left border in that hue, dotted while deleting. This supersedes the 2026-09-04 font-dependent text glyphs: uniform geometry and favicon/UI consistency outweigh avoiding the cached SVG request.
- **One inline icon sprite** (`apps/web/src/components/Icons.tsx`, rendered once by the app shell): `pen`, `archive`, `bin`, `minus`, `x`, `copy`, drawn 16×16 inside 20×20 icon-only buttons (revised 2026-09-07) with `aria-label` and `title`. Icon buttons never carry text; text actions (`new orb`, `abort`, `copy` in prose) never carry an icon. Header `start`/`stop` changed to the selected L2 solid icons and upload uses U1 (2026-09-09). **Every delete is red** and inverts to a red ground on hover.
- **No app header and no brand.** The dashboard is the home screen and renders as the page; the orb page identifies itself by orb and project name. A brand line repeated on every route is the clearest case of the UI talking about itself.
- **Projects are columns.** The dashboard is a grid of fixed 316px columns (`repeat(auto-fill, 316px)`, `grid-auto-rows: minmax(min-content, 1fr)`, `align-content: stretch`), left-aligned, columns separated by 1px black vertical rules and each row closed by a black rule; the page scrolls vertically. A column has a black-ruled header (18px name + config gear + red bin on a 24px line), its working orbs, an optional archive, and finally `new orb`. Fixed width was chosen over fluid columns and masonry because a project column is a list of short lines: fluid columns stretch names across dead space, and masonry reorders columns as data changes, which destroys the muscle memory of where a project sits. 316px, widened from 300px on 2026-09-04, is what the larger project name needs before it starts truncating.
- **The board fills the viewport between two 24px lines (2026-09-04).** A **totals strip** rules the top: four tabular cells separated by 1px black vertical rules — `N PROJECTS`, `N ORBS`, `N BUSY`, `N FAILED`, bold number and uppercase grey label — counted in the browser off the loaded projects and orb lists (`dashboardTotals` in `apps/web/src/lib/project-orbs.ts`); orbs, busy, and failed count the working set only. A project whose orb list is still in flight contributes nothing yet and gets no placeholder: the strip states what is known, and a number that briefly rises is honest about a list still arriving. A **footer** is held against the bottom of the viewport, stating `<host provider> host · <database kind> · v<version>` in grey from `GET /api/v1/system` (`docs/control-plane-api.md`); before it answers the footer is an empty line, present but silent, so nothing below it moves. The footer says nothing about the fleet — a count of booted hosts would repeat the strip and go stale between reloads. Between the two, the board carries `min-height: calc(100dvh - 48px)` and stretches its rows into it, so a column holding one orb still rules from the strip down to the footer instead of leaving the lower two-thirds of the screen as blank paper.
- **An orb entry is two lines** behind its 2px hue: a 22px line of glyph and 14px name (bold when busy or failed, grey when stopped or archived), then a 20px line of age with the archive and red delete icons right-aligned, with 4px of padding above and below so entries read as blocks rather than a continuous ledger. A failed orb adds a third red line carrying `lastError`, so the reason a boot failed is on the dashboard rather than one navigation away. A deleting orb adds its cleanup blocker as a grey line.
- **The archive is a `<details>` footer** on `#f2f2f2` (`▸ archive · n`, `▾` when open), entries in the same format with delete only. A project with no shelved orbs renders no footer at all (2026-09-04): an empty shelf is a line spent saying nothing. This keeps the 2026-08-09 separation of retained transcripts from active work and its state/action rules, but retires the side-by-side two-shelf layout, its `working set` / `archive shelf` headings, and its empty-shelf sentences: a column is already the working set, and a shelf heading in a 316px column costs a line to repeat what the rows show.
- **New Project is the last cell**, marked by a dashed left rule: `NEW PROJECT`, `project name`, `repository URL`, and a black `Create project` button. Keeping creation last, after every existing project, is unchanged from the 2026-08-08 "Compact strip" decision and for the same reason; the orientation sentence under the heading is retired.
- **Missing-resource and create-orb pages are plain lines** in the same language with a `Back to dashboard` link, and no header.
- **Two panes on the orb page.** A 236px project index with a black right rule sits beside the transcript column. The selected Stacked index now contains every project's working set under its uppercase project name, plus an optional archive disclosure — the `n working` count was dropped 2026-09-04 because the rows below are the count — each row `glyph | name | age` behind its 2px state hue, the current orb inverted; project metadata and each list-project-orbs endpoint are fetched immediately and every 2 seconds while mounted, and rows appear as each list loads. This replaces lifecycle-triggered fetching: that request-saving approach left sibling titles/status and even title-only changes to the current orb stale. The existing individual current-orb poll remains independent, with no list-to-current-orb reconciliation or additional missing-orb checks. Fleet poll cycles do not overlap; failed reads retain the last successful list with a visible scoped error. Unmount and committed project mutations discard outdated responses; cross-project navigation does not reset fleet data. Its first row (2026-09-04) is a 24px `PI-ORB` linking to the dashboard, above the project name and under a black rule, so the index renders even before the list arrives. The dashboard gets no brand line: the choice among a full-width brand bar, this index row, and a breadcrumb orb header ([`design-prototypes/signal-brand-line.html`](../design-prototypes/signal-brand-line.html)) took the index row because it adds no line to the transcript column and keeps the link in the same top-left corner on both screens. The index scrolls itself while the transcript scrolls the document, so window-level scroll pinning is unchanged. A right-aligned + in each project title uses the same native project-scoped creation route as the dashboard; it replaces the former bottom `new orb` line. The gear and red bin share that right-aligned action group. There is no app header and no find on this route.
- **A 24px sticky orb header:** orb name and rename pen | state glyph in its hue with the state word (and `· busy` when the runtime reports activity) | upload icon when running, Start/Stop icons when available, archive icon, red bin. The project chip was dropped 2026-09-04: the index beside the header already carries the project name. `start` and `stop` render only when the state accepts them rather than sitting there disabled. Orb id, state version, checkout commit, preview host/ports, live connection text, and notification controls stay omitted as clutter. Lifecycle and authentication diagnostics remain immediately below the header, each a 1px black box on the transcript's `···` system prefix; since 2026-09-04 the device-login notice says `expires in 9m` rather than the raw expiry timestamp, and says nothing once the code has expired. The former archived notice (`this transcript is read-only and the orb can never be started again`) is retired: the header glyph says `archived`, and the absent composer and absent start action say the rest.
- **Authored records use the full width without a speaker gutter (revised 2026-09-16).** User turns are black bands with white, normal-weight prose; orb turns are white. Neither shows an author label, but visually hidden `You:` / `Orb:` text preserves assistive attribution. Outstanding queued/steering/delivered/failed messages use the same user paper behind a dotted 2px white left rule with their status word retained; failed-message diagnostics use the original red ink on white so they remain readable. Non-author types keep their information: shell records retain the compact `32px` `sh` prefix and persisted `! command` block with output/status footer; compaction remains a full-width rule with `context compacted` over its summary disclosure; thinking, tools, custom/system records, and model errors remain inside orb paper.
- **Scheduled sleep presentation (implemented locally 2026-09-17; not deployed).** Existing lifecycle status shows the pending `sleepUntil`; a stopped orb with that field uses the shared sleeping crescent across dashboard, index, header, favicon, and Find. No controls or duplicate explanation are added. Provisional system inbox rows render as notices, never human bands, and retire only when a replicated event carries their inbox IDs. Wake, expiry, error, and guard outcomes remain visible through the ordinary lifecycle/history surfaces. Contract: `docs/orb-sleep.md`.
- **Markdown in the transcript** uses the one 13px face: `h1`–`h6` are uppercase bold at body size, inline code and fenced code/text blocks share the same `#f2f2f2` gray background (revised 2026-09-04); fenced blocks retain their 1px black border. Every fence renders only boxed content and a corner copy action, with no header or formatting-type label regardless of language (revised 2026-09-04). Limiting header removal to plain-text fences was rejected: labels such as `ts` are equally unwanted. Space beside the scrollable content is reserved for the copy action so it never covers source.
- **Live activity uses the black-and-white Bit register (revised 2026-09-16).** The eight-frame, three-digit 16px-high tile replaces the blinking streaming cursor, including the waiting-before-output case. Its selection, implementation and tests are recorded above. The former `working…` line remains rejected as redundant; the composer and terminal keep their 13px monospace, 20px-row full-cell carets (2026-09-04 geometry decision). Both composer and transcript respect reduced motion. **Activity validity (2026-09-08, unchanged):** the marker requires a running orb, an open live connection, and current runtime busy activity. Any non-open connection status invalidates activity and operation ID without discarding transcript output or composer drafts; reopening alone cannot revive busy. Lifecycle changes hide the marker immediately, before connection cleanup. This prevents missed idle events from leaving stopped orbs marked busy. Deterministic reducer/selector regressions live in `apps/web/src/pages/OrbPage.test.ts`. The original Chromium validation held completion/idle frames, then proved Stop removed the old cursor without clearing output/drafts and Start/reconnect did not revive it. The new marker preserves that authority rather than inventing liveness from animation. Existing lifecycle diagnostics remain authoritative; there are no new durable events or repeated UI labels.

- **Consolidated tool activity (decided and implemented 2026-08-12; presentation revised 2026-09-04).** Consecutive tool calls render as the selected **Activity Rail** direction from `design-prototypes/tool-call-consolidation.html`: one collapsed summary per available semantic category inside the agent turn. Each category is a 1px-bordered 20px row — `▸`/`▾` marker | `label · headline` truncating to one line | metric right — and reasoning renders through the same `ActivityRailRow` component and CSS geometry, not a parallel lookalike, so marker position, row height, and columns cannot drift by category. Reasoning's label is `thinking`. A category of exactly one call names the actual file or command in its headline instead of `1 file …` / `1 command ran`, with the full value as the native title tooltip; larger runs drop the headline and count in the metric (`2 ran`, `2 files`, `+42 −7`). Read summaries count distinct paths: repeated reads of one file show that file's path exactly as a singleton read would. Expanded rows append their requested line range (for example `provider.ts:180–329`) so separate calls to the same path remain distinguishable. A completed category with nothing to report shows no metric; the former `complete` word was noise. Do not invent categories for tools the agent does not have; unknown tools retain a name-based fallback category. An expanded body sits on `#f2f2f2`: per-file rows keep their own output disclosure, while each command is a flat block — `run` prefix, bold command, output, and a green `✓ completed` or red `✕ failed` footer — because a command's output is what the reader came for. Parallel-execution wrappers have no presentation of their own. A maximal run ends at visible assistant prose, a user record, or another visible non-tool boundary. Live calls use the same category rail with running/completed/failed state, omit unavailable arguments and output, and colour marker, label, and metric by outcome: running green, failed red, completed neutral except explicit success signals. Live calls disappear once their persisted call ID is present so the live-to-history handoff never duplicates a call. Live reasoning, output, and tool state extend the final persisted agent record whenever no user/shell boundary intervenes; they must not create a second orb record merely because the persisted/live handoff occurred mid-operation. An exact persisted text/reasoning block suppresses its matching transient block during that handoff.
- **Fluid width.** No max-width constraint — the transcript fills its pane at any size.
- **Composer (presentation revised 2026-09-04).** Sticky at the viewport bottom, full-bleed inside the transcript column, opaque so records scrolling behind it never bleed into the input. It is one row plus any attachments: a bold prefix column, the textarea, and — right-aligned, level with its first line — the `abort` text action when an operation can be aborted. There is no send button (removed 2026-09-04): ⌘⏎ / Ctrl⏎ is the only send gesture, and a pending request shows nothing. The placeholder is `Message the orb…` in message mode and `Run a shell command… (⌘⏎ to run)` in the shell modes; the message placeholder's 2026-08-05 paste-images and ⌘⏎ hints were dropped on 2026-09-04 as help text. **The prefix glyph carries the mode (2026-09-04):** `>` for message, `!` for shell, `!!` for excluded shell, in the same 32px column as the transcript prefixes. The bracketed mode chip and the second composer line are retired — the glyph the user just typed says the mode, and a chip repeating it beneath was the same fact twice. The `message` / `shell` / `excluded shell` status text survives only as a visually hidden `aria-live="polite"` region for assistive technology. Chat scrolls in the normal document flow with bottom-pinned auto-follow (scroll pinning in `apps/web/src/lib/scroll-pin.ts`). Auto-follow runs before paint and distinguishes delayed programmatic scroll events from reader scrolling, so rapid consecutive appends cannot incorrectly release the pin. Opening or creating an orb focuses the textarea without scrolling the document; submitting keeps focus there so the next message can be written immediately. The textarea starts at four lines and can be resized vertically, never below four lines (2026-09-04). Its focused, collapsed selection has a full-cell block caret that inverts the character beneath it. `ComposerCaret.tsx` measures a hidden text mirror on edits, selection, scrolling, and resize; the real textarea still owns input, wrapping, keyboard navigation, selection, and accessibility. The overlay hides on blur or range selection, and IME composition restores the native caret. Native `caret-shape: block` was tested and rejected because Chromium still renders a shorter glyph-height block; merely changing its shape does not meet the shared-height requirement. Native reveal-scroll can expose only 17px of a 20px cell at the bottom; the composer completes that partial scroll rather than hiding the caret. A fully offscreen selection does not pull the reader back. Browser fixture tests cover geometry, navigation, selection, composition, wrapping/resizing, scroll, and terminal metrics. With the send-anytime inbox (`docs/runtime-protocol.md`), message-mode send remains enabled while busy, starting, stopped, or failed; acceptance clears the composer only after the durable HTTP `202`, and each outstanding message appears exactly once in transcript position as a muted user turn labeled `queued`, `steering`, or briefly `delivered` until the corresponding runtime history record replaces it. The 2-second outstanding-message poll discards responses from requests that started before the last successful enqueue (mutation-epoch guard in `apps/web/src/lib/queued-messages.ts`, decided 2026-08-11), so a stale in-flight snapshot can never clobber an optimistically appended just-sent message. If several submissions were waiting when dispatch became possible, their separate turns collapse into one committed user turn with an empty line between the original messages. Shell modes remain enabled only on an idle live runtime.
**Field finding and fix (2026-08-12) — monotonic delivered inbox/history handoff.** The browser filtered a message out of its polled inbox state as soon as `GET .../messages` reported `delivered`. That status is committed by replication before the browser has necessarily applied the matching `history.record`, so independent inbox-poll and live-WebSocket schedules created a blank interval; if the live record was missed during a connection gap, the message and response stayed absent until reload loaded database history. The browser now retains every delivered row as a provisional turn until a locally applied native history record names it in `details.messageIds`. Seeing delivered without that record immediately refreshes database history; the refresh merges the replicated prefix ahead of any newer live suffix instead of replacing live state. Deterministic tests cover delivered-before-history, identity-based retirement, and prefix/live-suffix merging. The full unit suite and process-provider E2E pass; Docker-backed E2E could not run in the implementation environment because the Docker executable is unavailable.

- **Orb links in messages (decided 2026-09-08).** Typing `@` opens the existing Find modal for orb names across projects, including archived orbs. Picking one replaces that `@` with its absolute orb URL and returns the caret to immediately after the URL. Escape leaves the `@` intact and returns focus to the composer. Neither shell mode triggers this behavior. Loading and partial search failures remain visible in the modal; see `docs/dashboard-find.md` for the picker contract and implementation.

- **Shell composer modes (decided 2026-08-05; face rule retired 2026-09-04).** The composer stores explicit `message | shell | excluded_shell` state, shown as the prefix glyph and announced as exactly `message`, `shell`, or `excluded shell`. The `!`/`!!` prefixes are editing gestures rather than visible textarea content: typing `!` at offset zero changes message → shell, then shell → excluded shell, without inserting a character. With a collapsed caret at offset zero, Backspace reverses excluded shell → shell → message without deleting command text. Pasting/replacing the whole input with leading `!`/`!!` normalizes to the corresponding mode and prefix-free body. The former serif-versus-monospace face switch is gone: the UI has one face, and the prefix glyph plus the placeholder already state the mode. An empty shell command cannot be submitted. Image attachments may remain when entering shell mode, but any attached image prevents shell submission and shows validation feedback; nothing is discarded silently. An accepted send clears the body and returns to message mode; rejection or disconnection preserves body, mode, and attachments.
- **Compact sticky orb header (revised 2026-08-08; restyled 2026-09-04).** The header is one 24px line over a black rule, described above. Its 2026-08-08 “Instrument Panel” predecessor — a 64px strip with a state-coloured top edge, the `pi-orb` brand, a rounded state badge, and edge-locked full-height buttons — is retired: the brand repeated the route, the badge repeated the glyph, and 64px of chrome bought nothing the line does not. Activating the pen still replaces the name with the rename form and immediately focuses its text field.
- **Project editing (revised 2026-09-09).** The former inline name-only pencil (2026-08-09, restyled 2026-09-04) is replaced by the shared Config dialog's General tab, which edits name and repository URL. Configuration is disabled once permanent deletion begins; failures stay in the owning dialog/header.
- **Project working set and archive (decided 2026-08-09; activity revised 2026-08-13; presentation revised 2026-09-04).** Each project divides its orbs into a primary working set and an archive. `archiving`, `archived`, and `deleting` orbs occupy the archive; all other lifecycle states remain in the working set. Every entry carries the shared SVG state tile immediately left of the orb name, with the state word as its accessible name and `title`. Lifecycle state selects the stopped, transitional, failed, or running glyph; a running orb whose ordinary API snapshot reports `activity: busy` uses the busy glyph rather than being mislabeled idle/running. Unknown activity falls back to running. The dashboard refreshes its project and orb lists every 2 seconds while mounted, keeping names, activity, lifecycle states, counts, and working/archive membership current. The former deletion/archival-only polling left ordinary title and activity changes stale; polling now runs regardless of lifecycle work, without a push channel. Actions are rendered only when the state accepts them: working rows offer archive and delete, archiving/archived rows offer delete only, and deleting rows offer neither. This was selected from five project-list prototypes; the separation keeps retained transcripts accessible without letting a growing archive dominate active work.
- **Dashboard project creation (decided and implemented 2026-08-08; presentation revised 2026-09-04).** Creation sits after every existing project, as the dashboard's last cell, so the working project list is the dashboard's primary content while adding another project stays fast and low-ceremony. The 2026-08-08 “Compact strip” horizontal row and its line of orientation copy are retired for the stacked New Project column above; its validation and API errors remain visible as red lines in that cell.
- **Link-native orb creation (decided and implemented 2026-08-09).** Each project's **new orb** action is a real link to `#/projects/:projectId/orbs/new`. For dashboard activation, direct navigation, and modified/new-tab activation, each destination-page instance generates its own browser-side orb UUID, performs the idempotent create request, shows progress or a retryable error, and replaces itself with canonical `#/orbs/:orbId` after success. Ordinary + activation inside the orb index instead creates in place and transitions directly through the persistent orb shell; the intermediate creation route is bypassed so it cannot unmount the workspace. Generating on ordinary index activation or in each new destination, rather than keeping an ID in the link, ensures repeated Command/Ctrl-clicks and context-menu opens each create a distinct orb. This preserves native link behavior without unsafe side-effecting GET requests or changing the required missing-orb behavior of canonical orb URLs. A missing project renders the project-specific missing-resource page.
- **Preview host omitted from header (revised 2026-08-08).** `OrbView.previewHost` remains the Tailscale port-exposure contract (`docs/ports.md`), but the orb header no longer renders a `Ports:` line. Port exposure is infrastructure behavior rather than primary chat-header state; a future dedicated ports surface can expose it without restoring the verbose header metadata.
- **Orb deletion (required and implemented 2026-08-08).** The orb header and project list expose a destructive delete action with explicit confirmation that the checkout and conversation history will be lost. The orb remains visibly `deleting`, including a sanitized cleanup blocker when retries fail, until final `404` removes it from the project list. There is no undo; see `docs/orb-deletion.md`.
- **Project deletion (required and implemented 2026-08-09).** The shared project header in dashboard and orb index exposes a red delete action with confirmation that the project, every orb, all checkout/files/compute resources, and all conversation history will be permanently deleted. The project remains visible as `deleting` — greyed, ordered last, with config, `new orb`, and delete disabled and its column body replaced by the durable child progress/blocker line — and is polled until backend completion removes it; the browser never implements deletion as an orb-by-orb request loop. See `docs/project-deletion.md`.
- **Orb archival (implemented 2026-08-08).** The header and project list offer archive separately from delete, confirming that checkout/files/compute are destroyed while conversation history and metadata remain. `archiving` exposes its seal/cleanup blocker; `archived` stays in project lists and opens as a read-only history page with no composer or start/stop controls. Rename and permanent delete remain available. Copy must never suggest an archived orb can be restored; see `docs/orb-archival.md`.
- **Device-code copy (decided 2026-08-07).** Authentication banners copy exactly `actionRequired.userCode`, never the verification URL. Because trusted local and tailnet development uses plain HTTP, the button falls back to a temporary selected textarea when the secure-context Clipboard API is absent or denied, and reports both success and failure in its visible label.
- **Open-tab turn notifications (decided 2026-08-06; header control removed 2026-08-08; in-page diagnostics removed 2026-08-14).** Notification state and permission controls are not shown in the compact orb header. On first opening an orb page with permission still at the browser's `default`, it immediately requests notification permission; browsers that require a user gesture may suppress that best-effort request, and the UI does not spend persistent header space on a fallback control. Every live Luna `turn_notification` attempts an OS notification when permission is granted, including while the orb page is foregrounded — suppressing foreground notifications was rejected after it made a manual completion test appear broken. The resulting shown/skipped/failed decision is written to the browser console but does not produce an in-page banner; desktop-notification status banners were removed because they clutter the conversation after every turn. The Notification API generally works on HTTPS or localhost, not the plain-HTTP tailnet development URL. The notification title uses the orb's current user/auto-generated display name when present and falls back to `Orb <id>` only while unnamed. Because first-turn auto-naming runs concurrently, receipt of `turn_notification` performs one ordinary orb-resource refresh before constructing the notification; a ref supplies the last known name if that refresh fails, without reconnecting the live socket when naming completes. The orb/operation pair is the notification tag and local deduplication key; clicking focuses and navigates to the orb. Same-tag browser replacement suppresses duplicates from multiple open tabs. Notifications are deliberately best-effort: no service worker, Web Push subscription, persistence, or reconnect replay exists, so closing all orb pages means receiving no notification.
- **Chat Markdown and URL linkification (decided and implemented 2026-08-05).** User and assistant messages use the same GFM Markdown pipeline in committed and streaming content. Its autolink-literal extension makes web URL literals clickable while composing with the syntax tree, so code spans/blocks and existing link syntax are never linkified a second time. Displayed custom messages, reasoning, and compaction summaries remain literal non-Markdown text and pass through a dedicated URL tokenizer instead of an ad-hoc regular expression. Only HTTP(S) and `www.` web URLs are linked; email and other schemes remain text. Generated external links open in a new tab with `noopener noreferrer`. Tool inputs and outputs remain verbatim code-like text and are deliberately not linkified.
- **Markdown code-block copy (decided and implemented 2026-08-26; presentation revised 2026-09-04).** Every fenced code block in user, committed assistant, and streaming assistant Markdown carries one copy action. All blocks omit the redundant language header (revised 2026-09-04); the copy action sits in the top-right corner with reserved space beside the scrollable content to avoid covering source. The button copies source code only, excluding the Markdown fence and any presentation labels; the parser-added final newline is removed while all source indentation and trailing spaces are preserved. Success and failure are reported through the accessible label and title rather than a second icon. Copy uses the secure-context Clipboard API when available and the existing temporary-textarea fallback on plain-HTTP local and tailnet deployments. Inline code, tool input/output, and persisted shell blocks do not gain this Markdown-specific action.
