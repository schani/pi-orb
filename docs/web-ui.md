# Web UI

The UI must support two modes without visibly changing data sources:

- **Stopped/unavailable orb:** show the complete replicated history from the control plane database.
- **Active orb:** first show database history, then attach live updates after the database cursor while the host may still be starting.

The first UI needs to display at least:

- user and assistant text as Markdown, for both committed history and live streaming;
- reasoning/thinking when available and permitted;
- tool-call and tool-result status, with inputs and outputs available only through collapsed disclosures by default;
- compaction summaries;
- persisted and live user-shell commands as preformatted command/output blocks, including exit, cancellation, truncation, and excluded-from-context status;
- runtime state such as starting, working, idle, stopped, or failed;
- on a running orb, the floating interactive terminal specified in `docs/terminal.md`, kept separate from persisted composer shell records.

Remaining UI questions include rendering unknown content blocks, large/truncated tool output, and image storage. Transient token deltas are ephemeral presentation events and are reconstructed after reconnect through ordinary live events; they are not stored in PostgreSQL.

## Missing resources (decided 2026-08-08)

A direct URL for a resource that does not exist stays at that URL and renders a resource-specific message (for example, “Orb doesn't exist”) with a link to the dashboard. Silently redirecting to the dashboard was rejected because it hides whether the resource was deleted, the URL is stale, or navigation failed. This behavior applies consistently to every resource type and to unknown application routes; unknown routes render “Page doesn't exist.”

## Frontend-only development (decided 2026-08-06)

Two Docker-free development compositions exist and must not be confused:

- **Full service with process-hosted orbs:** run `npm run dev:local` for the control plane/SQLite/process supervisor and `npm run dev --workspace @pi-orb/web` for the normal web server. This exercises real Pi runtimes, lifecycle, protocol, replication, credentials, and model inference, but runs repository code unsandboxed (`docs/host-provider.md`).
- **Frontend-only fixture:** run only `npm run dev:frontend`. Vite replaces the HTTP/WebSocket backend in process; no control plane, database, orb process, Pi session, or model call exists.

The web workspace's in-process fixture is activated by Vite's `frontend` mode. Run it with:

```sh
npm run dev:frontend
```

This starts only Vite and needs no PostgreSQL, Docker, control plane, runtime, credentials, or model service. It is not the frontend command for `npm run dev:local`; that full-service composition uses the normal `npm run dev --workspace @pi-orb/web` command in a second terminal. The fixture owns the `/api/v1` HTTP routes and live agent/terminal WebSocket upgrades on the Vite server. It starts with one running orb and a short conversation, a starting orb with an OpenAI device-login challenge for testing the authentication UI, and an archived orb so the dashboard's archive shelf is visible immediately; messages receive a simulated streamed echo, user-shell commands receive simulated streamed command output and persisted `pi.bash_execution` records (including excluded-context state), the floating terminal receives a deterministic binary echo/prompt over the real terminal controls, and start, stop, project/orb creation, history reload, and abort use the real browser-facing contracts. Newly created fixture orbs remain in `creating` for about 10 seconds before becoming `running`, so the editable-while-send-is-unavailable composer behavior can be exercised manually.

The fixture is a transport-level adapter, not a mock branch in React. Production UI code still calls the same relative HTTP URLs, validates the same `@pi-orb/protocol` schemas, and runs the same WebSocket reducer. This keeps frontend-only behavior representative and makes protocol drift fail visibly. It is intentionally ephemeral and process-local: restarting Vite resets all fixture data, and it is for manual UI development rather than backend or E2E correctness. Normal `npm run dev --workspace @pi-orb/web` retains the proxy to the real control plane.

## Per-orb browser-tab identity (decided and implemented 2026-08-09)

Once the orb and its parent project have loaded, the orb chat route sets the HTML page title to `{project name} · {orb name}` so multiple open orb tabs are distinguishable. An orb that has not yet been auto-named uses `untitled orb` as its name. While either resource is loading, after leaving the orb route, and for missing resources, the title is the neutral `pi-orb`.

## Per-orb favicon status (decided and implemented 2026-08-07)

The orb chat route makes its coarse state visible in the browser tab through a small, static set of SVG favicon variants derived entirely in the web client from state it already has; this requires no API or runtime-protocol change. The project-list route and an orb that has not loaded use the neutral pi-orb mark.

For an orb route, `stopped` gets the stopped variant; `running` gets the running variant; and a `running` orb with an open live connection reporting `activity: busy` gets the busy variant. Busy has priority over running. A disconnected or reconnecting tab must not present stale runtime activity as current, so it falls back to running until synchronization reports busy again. Transitional (`creating`, `starting`, `stopping`) and `failed` lifecycle states have distinct variants rather than being mislabeled as one of the three primary states.

The marks remain distinguishable at 16px by glyph/fill as well as color and avoid animation. Running/idle uses light green to suggest that the orb is ready for the user; busy uses the darker UI green, not the error-associated terracotta. `index.html` installs the neutral icon before React loads. Mounting an orb page updates that one icon link rather than accumulating links; leaving the route restores neutral. The pure status mapping and link replacement are unit-tested in `apps/web/src/lib/favicon.test.ts`; the SVG assets live under `apps/web/public/favicons/`.

## Dashboard orb update age and ordering (decided and implemented 2026-08-26)

The dashboard working set and archive shelf show each orb's age since its last update, not since creation, in a compact human form containing exactly one number and one unit (for example, `14 minutes` or `3 days`), without a timestamp, leading separator, or `ago` suffix. The largest whole useful unit is selected from minutes, hours, days, weeks, months, and years; an orb updated less than a minute ago reads `1 minute`. Ages refresh once per minute while the dashboard remains open. Within each shelf, orbs are sorted by `updatedAt` descending so newly created and most recently changed orbs appear first. Abbreviated orb hashes are removed from the dashboard.

Placement adapts to the space available to each shelf rather than only to the viewport: a sufficiently wide shelf uses the selected **Inline chronicle** treatment, placing age after the title; a narrow shelf uses the selected **Editorial subline** treatment beneath the title. A CSS container query makes this compose with the existing side-by-side shelves, their stacked tablet layout, row/action wrapping on phones, and unequal working/archive column widths. The decision was selected from the eight directions in [`design-prototypes/orb-age.html`](../design-prototypes/orb-age.html).

## Dashboard Find (decided and implemented 2026-08-26)

The dashboard provides a route-scoped Command-K / Control-K Find for project names, GitHub repository URLs, and working or archived orb names. Find uses the selected centered **Index card** presentation and generic app-search shell/core/source contracts so other routes can add their own Command-K sources without coupling to dashboard resources. Every result is a real anchor: orb results use `#/orbs/:orbId`, while project results use `#/projects/:projectId`, an addressable focused-dashboard route that scrolls to and focuses that project. The dashboard header has no persistent Find hint. Orb result context mirrors the dashboard's current identity treatment with parent project, shelf, and formatted update age; it never restores the removed abbreviated hash, and age is not searchable. The card maintains exactly one pointer/keyboard selection, ignores stationary-pointer events caused by result redraws, replaces result sets without an empty-frame flash, and horizontally aligns its close control with result arrows. Ordinary click, Command/Ctrl-click, middle-click, copy-link, and context-menu behavior remain native. A missing focused project stays at its URL and renders “Project doesn't exist” with a dashboard link. The complete architecture is specified in `docs/dashboard-find.md`; the selected design and four rejected presentation alternatives remain in `design-prototypes/dashboard-find.html`, with a formatted architecture at `design-prototypes/dashboard-find-architecture.html`.

## Project secrets configuration (decided and implemented 2026-08-28)

The project-scoped, write-only secret contract is in `docs/credentials.md`. The dashboard uses the selected **Sealed card** presentation: a project-scoped entry point opens a focused modal over the still-recognizable dashboard, listing names and update ages but never values and supporting add/replace/remove. The card keeps project scope explicit and states that changes apply on the next orb start. It closes through its visible close control, Escape, or a successful same-context navigation; unsaved name/value input is not discarded by an accidental backdrop click.

[`design-prototypes/project-secrets.html`](../design-prototypes/project-secrets.html) preserves the original five-direction surface study: Inline ledger, Settings folio, selected Sealed card, Margin vault, and Paste desk. Sealed card was chosen because secret management is occasional and deliberate: it preserves dashboard location, focuses attention while a write-only value is present, and does not permanently enlarge every project panel or create a broader project-settings information architecture before one is needed. The batch paste direction was rejected initially because one malformed or accidentally repeated name could rotate several credentials at once; individual writes make each destructive replacement explicit.

**Entry placement revised and implemented 2026-08-31.** Use the selected **Identity metadata** treatment: a quiet key-marked `N secrets configured` link (`no secrets configured` at zero) sits directly below the repository URL and opens the Sealed card. The prototype's trailing `project environment` text is omitted as redundant. This places the inventory with project identity while separating it from the right-aligned `new orb` action in position, shape, typography, and color. The former adjacent `secrets` text action is rejected because proximity and matching typography made occasional configuration look like a peer creation action. [`design-prototypes/project-secrets-entry.html`](../design-prototypes/project-secrets-entry.html) preserves this selection and the four rejected alternatives—Project command menu, Vault edge tab, Project utility footer, and Environment seal. Open question 46 is resolved in `docs/open-questions.md`.

## Visual design (decided)

The UI uses the "Reading Room" variant of the Manuscript × Gutter design, chosen from a design exploration (five initial directions, then a Manuscript × Gutter hybrid, then five typography variations). Decisions:

- **Paper/ink palette, light mode only.** Warm paper ground (`#f8f3e9`), ink text (`#221c12`), terracotta accent (`#a03e1c`). No dark mode — explicit product decision.
- **Reading typography.** Agent prose is set in a Charter/Iowan Old Style serif stack at 17.5px/1.7; user messages are larger italic serif "margin notes" on terracotta blocks; headings and buttons use small-caps serif; structural meta (labels, chips, tool output, orb ids) is quiet monospace. All fonts are system stacks — no webfonts.
- **Turn gutter.** Every chat turn carries a gutter column: a marked square (`Y` filled terracotta for the user, `O` outlined ink for the agent) with a fading vertical rail. Adjacent agent-side records (assistant, tool results, displayed events) group into a single agent turn; compaction renders as a full-width dashed divider crossing the gutter.
- **Consolidated tool activity (decided and implemented 2026-08-12).** Consecutive tool calls render as the selected **Activity Rail** direction from `design-prototypes/tool-call-consolidation.html`: one collapsed summary per available semantic category inside the agent turn. Edits and writes report unique files plus additions/removals when Pi's persisted patch provides exact totals, commands report invocation and failure counts, and reads report files. A persisted category containing exactly one tool call shows the actual file path or command instead of `1 file …` / `1 command ran`; the fixed headline column truncates it with an ellipsis without moving the metric column, while the full value remains available as the native title tooltip. Read summaries count distinct paths: repeated reads of one file show that file's path exactly as a singleton read would; users who care about the separate calls can expand the category. Expanded rows append their requested line range (for example `provider.ts:180–329`) so separate calls to the same path remain distinguishable. Live calls fall back to the count wording until their arguments are persisted. Do not invent categories for tools the agent does not have; unknown tools retain a name-based fallback category. Category markers occupy the center of the Orb turn's existing gutter column, directly over its rail, rather than drawing a nested rail. Reasoning and every tool category render through the same `ActivityRailRow` component and shared CSS geometry—not parallel lookalike implementations—so marker position, row height, label position, and headline columns cannot drift by category. The label column uses one shared bounded width (`clamp(96px, 10vw, 150px)`) independent of the optional right metric's width, keeping every headline at exactly the same horizontal coordinate without wasting space on wide screens. Reasoning's collapsed disclosure is a labeled rail row, and expansion reveals the existing reasoning body. Expanding a tool category reveals its individual calls without inserting a divider between the category row and those calls; the row's divider moves visually to the bottom of the expanded call list. Per-file read rows omit a redundant `complete` suffix. Each completed command is a second disclosure that reveals the command's existing output and error styling. Parallel-execution wrappers have no presentation of their own. A maximal run ends at visible assistant prose, a user record, or another visible non-tool boundary. Live calls use the same category rail with running/completed/failed state, omit unavailable arguments and output, and color category markers and category labels by outcome: completed tool groups are green, failed groups terracotta/red, and running groups animated green; persisted reasoning remains neutral ink while live reasoning uses running green. Live calls disappear once their persisted call ID is present so the live-to-history handoff never duplicates a call. Live reasoning, output, and tool state extend the final persisted agent turn on its existing `O` gutter whenever no user/shell boundary intervenes; they must not create a second Orb turn merely because the persisted/live handoff occurred mid-operation. An exact persisted text/reasoning block suppresses its matching transient block during that handoff.
- **Fluid width.** No max-width constraint — the manuscript fills the window at any size.
- **Composer.** Sticky at the viewport bottom, full-bleed, with an opaque stacking layer above transcript content so rails and activity markers scrolling behind it never bleed into the input; mode-sensitive serif/monospace input, round ink send button (`↑`, ⌘⏎ shortcut), small-caps terracotta abort in the same row, and a mode status line immediately below the input; chat scrolls in the normal document flow with bottom-pinned auto-follow (scroll pinning in `apps/web/src/lib/scroll-pin.ts`). Auto-follow runs before paint and distinguishes delayed programmatic scroll events from reader scrolling, so rapid consecutive appends cannot incorrectly release the pin. Submitting keeps focus in the textarea so the next message can be written immediately. With the send-anytime inbox (`docs/runtime-protocol.md`), message-mode send remains enabled while busy, starting, stopped, or failed; acceptance clears the composer only after the durable HTTP `202`, and each outstanding message appears exactly once in transcript position as a muted gray user turn labeled `queued`, `steering`, or briefly `delivered` until the corresponding runtime history record replaces it. The 2-second outstanding-message poll discards responses from requests that started before the last successful enqueue (mutation-epoch guard in `apps/web/src/lib/queued-messages.ts`, decided 2026-08-11), so a stale in-flight snapshot can never clobber an optimistically appended just-sent message. If several submissions were waiting when dispatch became possible, their separate gray turns collapse into one committed user turn with an empty line between the original messages. Shell modes remain enabled only on an idle live runtime.
**Field finding and fix (2026-08-12) — monotonic delivered inbox/history handoff.** The browser filtered a message out of its polled inbox state as soon as `GET .../messages` reported `delivered`. That status is committed by replication before the browser has necessarily applied the matching `history.record`, so independent inbox-poll and live-WebSocket schedules created a blank interval; if the live record was missed during a connection gap, the message and response stayed absent until reload loaded database history. The browser now retains every delivered row as a provisional turn until a locally applied native history record names it in `details.messageIds`. Seeing delivered without that record immediately refreshes database history; the refresh merges the replicated prefix ahead of any newer live suffix instead of replacing live state. Deterministic tests cover delivered-before-history, identity-based retirement, and prefix/live-suffix merging. The full unit suite and process-provider E2E pass; Docker-backed E2E could not run in the implementation environment because the Docker executable is unavailable.

- **Shell composer modes (decided 2026-08-05).** The composer stores explicit `message | shell | excluded_shell` state, and its status line displays exactly `message`, `shell`, or `excluded shell`. The `!`/`!!` prefixes are editing gestures rather than visible textarea content: typing `!` at offset zero changes message → shell, then shell → excluded shell, without inserting a character. With a collapsed caret at offset zero, Backspace reverses excluded shell → shell → message without deleting command text. Pasting/replacing the whole input with leading `!`/`!!` normalizes to the corresponding mode and prefix-free body. Message mode keeps the Reading Room serif face; shell modes use the existing `var(--mono)` system stack (`ui-monospace`, SF Mono, Menlo, Consolas, Liberation Mono). An empty shell command cannot be submitted. Image attachments may remain when entering shell mode, but any attached image prevents shell submission and shows validation feedback; nothing is discarded silently. An accepted send clears the body and returns to message mode; rejection or disconnection preserves body, mode, and attachments.
- **Compact sticky orb header (revised and implemented 2026-08-08).** The orb chat route uses the selected “Instrument Panel” design: a 64px sticky strip with a state-colored top edge, `pi-orb` brand, orb name, pen-icon rename action, project-name tag, lifecycle state, and edge-locked start/stop/delete controls. Project and orb identity occupy one line. Orb id, state version, checkout commit, preview-host/ports text, live connection/activity text, and notification controls are deliberately omitted as header clutter. Activating the pen replaces the title with the rename form and immediately focuses its text field. On narrow screens the project tag and then the global brand hide before orb identity or lifecycle controls; the state label collapses to its colored dot at phone widths. Lifecycle and authentication diagnostics stay in the conversation area immediately below the header.
- **Inline project rename (decided and implemented 2026-08-09).** Each dashboard project heading has a pen-icon action immediately after its name. Activating it replaces the heading with an immediately focused inline name form; save updates only the display name, while cancel preserves it. Rename is disabled once permanent project deletion begins, and validation or API failures remain visible in that project panel.
- **Project-list working set and archive shelf (decided 2026-08-09; activity revised 2026-08-13).** Each project divides its orbs into a primary working set and an inset archive shelf. `archiving`, `archived`, and `deleting` rows occupy the shelf; all other lifecycle states remain in the working set. Every row uses the existing favicon immediately left of the orb name instead of a text state bubble, while hover and keyboard focus reveal the represented state. Lifecycle state selects the stopped, transitional, failed, or running glyph; a running orb whose ordinary API snapshot reports `activity: busy` uses the busy glyph rather than being mislabeled idle/running. Unknown activity falls back to running. The dashboard deliberately does not poll or open a push channel for activity yet, so this observation changes on an ordinary dashboard resource reload. Actions are rendered only when the state accepts them: working rows offer archive and delete, archiving/archived rows offer delete only, and deleting rows offer neither. This was selected from five project-list prototypes; the separation keeps retained transcripts accessible without letting a growing archive dominate active work.
- **Dashboard project creation (decided and implemented 2026-08-08).** The creation surface follows the selected “Compact strip” direction and sits after every existing project at the bottom of the dashboard. It is titled **New Project**, pairs that heading with one line of orientation copy, and places project name, repository URL, and the terracotta primary action in one horizontal row. At narrow widths the fields and full-width action stack vertically. Keeping creation last makes the working project list the dashboard's primary content while retaining a fast, low-ceremony path to add another project.
- **Link-native orb creation (decided and implemented 2026-08-09).** Each project's **new orb** action is a real link to `#/projects/:projectId/orbs/new`. Each destination-page instance generates its own browser-side orb UUID, then performs the idempotent create request, shows progress or a retryable error, and replaces itself with canonical `#/orbs/:orbId` after success. Generating in the destination rather than keeping an ID in the dashboard link ensures repeated Command/Ctrl-clicks and context-menu opens each create a distinct orb. This preserves native link behavior without unsafe side-effecting GET requests or changing the required missing-orb behavior of canonical orb URLs. A missing project renders the project-specific missing-resource page.
- **Preview host omitted from header (revised 2026-08-08).** `OrbView.previewHost` remains the Tailscale port-exposure contract (`docs/ports.md`), but the orb header no longer renders a `Ports:` line. Port exposure is infrastructure behavior rather than primary chat-header state; a future dedicated ports surface can expose it without restoring the verbose header metadata.
- **Orb deletion (required and implemented 2026-08-08).** The orb header and project list expose a destructive delete action with explicit confirmation that the checkout and conversation history will be lost. The orb remains visibly `deleting`, including a sanitized cleanup blocker when retries fail, until final `404` removes it from the project list. There is no undo; see `docs/orb-deletion.md`.
- **Project deletion (required and implemented 2026-08-09).** Each project panel exposes **Delete project** with confirmation that the project, every orb, all checkout/files/compute resources, and all conversation history will be permanently deleted. The project remains visible as `deleting`, disables new-orb creation, shows durable child progress/blockers, and is polled until backend completion removes it; the browser never implements deletion as an orb-by-orb request loop. See `docs/project-deletion.md`.
- **Orb archival (implemented 2026-08-08).** The header and project list offer archive separately from delete, confirming that checkout/files/compute are destroyed while conversation history and metadata remain. `archiving` exposes its seal/cleanup blocker; `archived` stays in project lists and opens as a read-only history page with no composer or start/stop controls. Rename and permanent delete remain available. Copy must never suggest an archived orb can be restored; see `docs/orb-archival.md`.
- **Device-code copy (decided 2026-08-07).** Authentication banners copy exactly `actionRequired.userCode`, never the verification URL. Because trusted local and tailnet development uses plain HTTP, the button falls back to a temporary selected textarea when the secure-context Clipboard API is absent or denied, and reports both success and failure in its visible label.
- **Open-tab turn notifications (decided 2026-08-06; header control removed 2026-08-08; in-page diagnostics removed 2026-08-14).** Notification state and permission controls are not shown in the compact orb header. On first opening an orb page with permission still at the browser's `default`, it immediately requests notification permission; browsers that require a user gesture may suppress that best-effort request, and the UI does not spend persistent header space on a fallback control. Every live Luna `turn_notification` attempts an OS notification when permission is granted, including while the orb page is foregrounded — suppressing foreground notifications was rejected after it made a manual completion test appear broken. The resulting shown/skipped/failed decision is written to the browser console but does not produce an in-page banner; desktop-notification status banners were removed because they clutter the conversation after every turn. The Notification API generally works on HTTPS or localhost, not the plain-HTTP tailnet development URL. The notification title uses the orb's current user/auto-generated display name when present and falls back to `Orb <id>` only while unnamed. Because first-turn auto-naming runs concurrently, receipt of `turn_notification` performs one ordinary orb-resource refresh before constructing the notification; a ref supplies the last known name if that refresh fails, without reconnecting the live socket when naming completes. The orb/operation pair is the notification tag and local deduplication key; clicking focuses and navigates to the orb. Same-tag browser replacement suppresses duplicates from multiple open tabs. Notifications are deliberately best-effort: no service worker, Web Push subscription, persistence, or reconnect replay exists, so closing all orb pages means receiving no notification.
- **Chat Markdown and URL linkification (decided and implemented 2026-08-05).** User and assistant messages use the same GFM Markdown pipeline in committed and streaming content. Its autolink-literal extension makes web URL literals clickable while composing with the syntax tree, so code spans/blocks and existing link syntax are never linkified a second time. Displayed custom messages, reasoning, and compaction summaries remain literal non-Markdown text and pass through a dedicated URL tokenizer instead of an ad-hoc regular expression. Only HTTP(S) and `www.` web URLs are linked; email and other schemes remain text. Generated external links open in a new tab with `noopener noreferrer`. Tool inputs and outputs remain verbatim code-like text and are deliberately not linkified.
- **Markdown code-block copy (decided and implemented 2026-08-26).** Every fenced code block in user, committed assistant, and streaming assistant Markdown uses the selected **Quiet Icon** direction from `design-prototypes/code-block-copy.html`: a compact icon-only button overlays the block's top-right corner without consuming a utility-header row. The button copies source code only, excluding the Markdown fence and any presentation labels; the parser-added final newline is removed while all source indentation and trailing spaces are preserved. A check or warning icon gives visible success or failure feedback and the accessible label updates with the outcome. Copy uses the secure-context Clipboard API when available and the existing temporary-textarea fallback on plain-HTTP local and tailnet deployments. Inline code, tool input/output, and persisted shell blocks do not gain this Markdown-specific action.
