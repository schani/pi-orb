# Web UI

The UI must support two modes without visibly changing data sources:

- **Stopped/unavailable orb:** show the complete replicated history from the control plane database.
- **Active orb:** first show database history, then attach live updates after the database cursor while the host may still be starting.

The first UI needs to display at least:

- user and assistant text as Markdown, for both committed history and live streaming;
- reasoning/thinking when available and permitted;
- tool-call and tool-result status, with inputs and outputs available only through collapsed disclosures by default;
- compaction summaries;
- persisted and live user-shell commands as preformatted command/output blocks, including exit, cancellation, truncation, and excluded-from-context status;
- runtime state such as starting, working, idle, stopped, or failed;
- on a running orb, the floating interactive terminal specified in `docs/terminal.md`, kept separate from persisted composer shell records.

Remaining UI questions include rendering unknown content blocks, large/truncated tool output, and image storage. Transient token deltas are ephemeral presentation events and are reconstructed after reconnect through ordinary live events; they are not stored in PostgreSQL.

## Missing resources (decided 2026-08-08)

A direct URL for a resource that does not exist stays at that URL and renders a resource-specific message (for example, “Orb doesn't exist”) with a link to the dashboard. Silently redirecting to the dashboard was rejected because it hides whether the resource was deleted, the URL is stale, or navigation failed. This behavior applies consistently to every resource type and to unknown application routes; unknown routes render “Page doesn't exist.”

## Frontend-only development (decided 2026-08-06)

Two Docker-free development compositions exist and must not be confused:

- **Full service with process-hosted orbs:** run `npm run dev:local` for the control plane/SQLite/process supervisor and `npm run dev --workspace @pi-orb/web` for the normal web server. This exercises real Pi runtimes, lifecycle, protocol, replication, credentials, and model inference, but runs repository code unsandboxed (`docs/host-provider.md`).
- **Frontend-only fixture:** run only `npm run dev:frontend`. Vite replaces the HTTP/WebSocket backend in process; no control plane, database, orb process, Pi session, or model call exists.

The web workspace's in-process fixture is activated by Vite's `frontend` mode. Run it with:

```sh
npm run dev:frontend
```

This starts only Vite and needs no PostgreSQL, Docker, control plane, runtime, credentials, or model service. It is not the frontend command for `npm run dev:local`; that full-service composition uses the normal `npm run dev --workspace @pi-orb/web` command in a second terminal. The fixture owns the `/api/v1` HTTP routes and live agent/terminal WebSocket upgrades on the Vite server. It starts with one running orb and a short conversation, a starting orb with an OpenAI device-login challenge for testing the authentication UI, and an archived orb so the dashboard's archive shelf is visible immediately; messages receive a simulated streamed echo, user-shell commands receive simulated streamed command output and persisted `pi.bash_execution` records (including excluded-context state), the floating terminal receives a deterministic binary echo/prompt over the real terminal controls, and start, stop, project/orb creation, history reload, and abort use the real browser-facing contracts. Newly created fixture orbs remain in `creating` for about 10 seconds before becoming `running`, so the editable-while-send-is-unavailable composer behavior can be exercised manually.

The fixture is a transport-level adapter, not a mock branch in React. Production UI code still calls the same relative HTTP URLs, validates the same `@pi-orb/protocol` schemas, and runs the same WebSocket reducer. This keeps frontend-only behavior representative and makes protocol drift fail visibly. It is intentionally ephemeral and process-local: restarting Vite resets all fixture data, and it is for manual UI development rather than backend or E2E correctness. Normal `npm run dev --workspace @pi-orb/web` retains the proxy to the real control plane.

## Per-orb browser-tab identity (decided and implemented 2026-08-09)

Once the orb and its parent project have loaded, the orb chat route sets the HTML page title to `{project name} · {orb name}` so multiple open orb tabs are distinguishable. An orb that has not yet been auto-named uses `untitled orb` as its name. While either resource is loading, after leaving the orb route, and for missing resources, the title is the neutral `pi-orb`.

## Per-orb favicon status (decided and implemented 2026-08-07)

The orb chat route makes its coarse state visible in the browser tab through a small, static set of SVG favicon variants derived entirely in the web client from state it already has; this requires no API or runtime-protocol change. The project-list route and an orb that has not loaded use the neutral pi-orb mark.

For an orb route, `stopped` gets the stopped variant; `running` gets the running variant; and a `running` orb with an open live connection reporting `activity: busy` gets the busy variant. Busy has priority over running. A disconnected or reconnecting tab must not present stale runtime activity as current, so it falls back to running until synchronization reports busy again. Transitional (`creating`, `starting`, `stopping`) and `failed` lifecycle states have distinct variants rather than being mislabeled as one of the three primary states.

The marks remain distinguishable at 16px by glyph/fill as well as color and avoid animation. Running/idle uses light green to suggest that the orb is ready for the user; busy uses the darker UI green, not the error-associated terracotta. `index.html` installs the neutral icon before React loads. Mounting an orb page updates that one icon link rather than accumulating links; leaving the route restores neutral. The pure status mapping and link replacement are unit-tested in `apps/web/src/lib/favicon.test.ts`; the SVG assets live under `apps/web/public/favicons/`.

## Visual design (decided)

The UI uses the "Reading Room" variant of the Manuscript × Gutter design, chosen from a design exploration (five initial directions, then a Manuscript × Gutter hybrid, then five typography variations). Decisions:

- **Paper/ink palette, light mode only.** Warm paper ground (`#f8f3e9`), ink text (`#221c12`), terracotta accent (`#a03e1c`). No dark mode — explicit product decision.
- **Reading typography.** Agent prose is set in a Charter/Iowan Old Style serif stack at 17.5px/1.7; user messages are larger italic serif "margin notes" on terracotta blocks; headings and buttons use small-caps serif; structural meta (labels, chips, tool output, orb ids) is quiet monospace. All fonts are system stacks — no webfonts.
- **Turn gutter.** Every chat turn carries a gutter column: a marked square (`Y` filled terracotta for the user, `O` outlined ink for the agent) with a fading vertical rail. Adjacent agent-side records (assistant, tool results, displayed events) group into a single agent turn; compaction renders as a full-width dashed divider crossing the gutter.
- **Fluid width.** No max-width constraint — the manuscript fills the window at any size.
- **Composer.** Sticky at the viewport bottom, full-bleed; mode-sensitive serif/monospace input, round ink send button (`↑`, ⌘⏎ shortcut), small-caps terracotta abort in the same row, and a mode status line immediately below the input; chat scrolls in the normal document flow with bottom-pinned auto-follow (scroll pinning in `apps/web/src/lib/scroll-pin.ts`). Auto-follow runs before paint and distinguishes delayed programmatic scroll events from reader scrolling, so rapid consecutive appends cannot incorrectly release the pin. Submitting keeps focus in the textarea so the next message can be written immediately. The textarea remains editable while sending is unavailable (for example, while the agent is busy), allowing a draft without enabling deferred queueing; only the send control is disabled.
- **Shell composer modes (decided 2026-08-05).** The composer stores explicit `message | shell | excluded_shell` state, and its status line displays exactly `message`, `shell`, or `excluded shell`. The `!`/`!!` prefixes are editing gestures rather than visible textarea content: typing `!` at offset zero changes message → shell, then shell → excluded shell, without inserting a character. With a collapsed caret at offset zero, Backspace reverses excluded shell → shell → message without deleting command text. Pasting/replacing the whole input with leading `!`/`!!` normalizes to the corresponding mode and prefix-free body. Message mode keeps the Reading Room serif face; shell modes use the existing `var(--mono)` system stack (`ui-monospace`, SF Mono, Menlo, Consolas, Liberation Mono). An empty shell command cannot be submitted. Image attachments may remain when entering shell mode, but any attached image prevents shell submission and shows validation feedback; nothing is discarded silently. An accepted send clears the body and returns to message mode; rejection or disconnection preserves body, mode, and attachments.
- **Compact sticky orb header (revised and implemented 2026-08-08).** The orb chat route uses the selected “Instrument Panel” design: a 64px sticky strip with a state-colored top edge, `pi-orb` brand, orb name, pen-icon rename action, project-name tag, lifecycle state, and edge-locked start/stop/delete controls. Project and orb identity occupy one line. Orb id, state version, checkout commit, preview-host/ports text, live connection/activity text, and notification controls are deliberately omitted as header clutter. Activating the pen replaces the title with the rename form and immediately focuses its text field. On narrow screens the project tag and then the global brand hide before orb identity or lifecycle controls; the state label collapses to its colored dot at phone widths. Lifecycle and authentication diagnostics stay in the conversation area immediately below the header.
- **Inline project rename (decided and implemented 2026-08-09).** Each dashboard project heading has a pen-icon action immediately after its name. Activating it replaces the heading with an immediately focused inline name form; save updates only the display name, while cancel preserves it. Rename is disabled once permanent project deletion begins, and validation or API failures remain visible in that project panel.
- **Project-list working set and archive shelf (decided and implemented 2026-08-09).** Each project divides its orbs into a primary working set and an inset archive shelf. `archiving`, `archived`, and `deleting` rows occupy the shelf; all other lifecycle states remain in the working set. Every row uses the existing coarse-state favicon immediately left of the orb name instead of a text state bubble, while hover and keyboard focus reveal the full lifecycle state. Actions are rendered only when the state accepts them: working rows offer archive and delete, archiving/archived rows offer delete only, and deleting rows offer neither. This was selected from five project-list prototypes; the separation keeps retained transcripts accessible without letting a growing archive dominate active work.
- **Dashboard project creation (decided and implemented 2026-08-08).** The creation surface follows the selected “Compact strip” direction and sits after every existing project at the bottom of the dashboard. It is titled **New Project**, pairs that heading with one line of orientation copy, and places project name, repository URL, and the terracotta primary action in one horizontal row. At narrow widths the fields and full-width action stack vertically. Keeping creation last makes the working project list the dashboard's primary content while retaining a fast, low-ceremony path to add another project.
- **Link-native orb creation (decided and implemented 2026-08-09).** Each project's **new orb** action is a real link to `#/projects/:projectId/orbs/new`. Each destination-page instance generates its own browser-side orb UUID, then performs the idempotent create request, shows progress or a retryable error, and replaces itself with canonical `#/orbs/:orbId` after success. Generating in the destination rather than keeping an ID in the dashboard link ensures repeated Command/Ctrl-clicks and context-menu opens each create a distinct orb. This preserves native link behavior without unsafe side-effecting GET requests or changing the required missing-orb behavior of canonical orb URLs. A missing project renders the project-specific missing-resource page.
- **Preview host omitted from header (revised 2026-08-08).** `OrbView.previewHost` remains the Tailscale port-exposure contract (`docs/ports.md`), but the orb header no longer renders a `Ports:` line. Port exposure is infrastructure behavior rather than primary chat-header state; a future dedicated ports surface can expose it without restoring the verbose header metadata.
- **Orb deletion (required and implemented 2026-08-08).** The orb header and project list expose a destructive delete action with explicit confirmation that the checkout and conversation history will be lost. The orb remains visibly `deleting`, including a sanitized cleanup blocker when retries fail, until final `404` removes it from the project list. There is no undo; see `docs/orb-deletion.md`.
- **Project deletion (required and implemented 2026-08-09).** Each project panel exposes **Delete project** with confirmation that the project, every orb, all checkout/files/compute resources, and all conversation history will be permanently deleted. The project remains visible as `deleting`, disables new-orb creation, shows durable child progress/blockers, and is polled until backend completion removes it; the browser never implements deletion as an orb-by-orb request loop. See `docs/project-deletion.md`.
- **Orb archival (implemented 2026-08-08).** The header and project list offer archive separately from delete, confirming that checkout/files/compute are destroyed while conversation history and metadata remain. `archiving` exposes its seal/cleanup blocker; `archived` stays in project lists and opens as a read-only history page with no composer or start/stop controls. Rename and permanent delete remain available. Copy must never suggest an archived orb can be restored; see `docs/orb-archival.md`.
- **Device-code copy (decided 2026-08-07).** Authentication banners copy exactly `actionRequired.userCode`, never the verification URL. Because trusted local and tailnet development uses plain HTTP, the button falls back to a temporary selected textarea when the secure-context Clipboard API is absent or denied, and reports both success and failure in its visible label.
- **Open-tab turn notifications (decided 2026-08-06; header control removed 2026-08-08).** Notification state and permission controls are not shown in the compact orb header. On first opening an orb page with permission still at the browser's `default`, it immediately requests notification permission; browsers that require a user gesture may suppress that best-effort request, and the UI does not spend persistent header space on a fallback control. Every live Luna `turn_notification` attempts an OS notification when permission is granted, including while the orb page is foregrounded — suppressing foreground notifications was rejected after it made a manual completion test appear broken. The resulting shown/skipped/failed decision is written to the browser console and shown as an in-page diagnostic. The unavailable diagnostic explains the secure-context requirement: the Notification API generally works on HTTPS or localhost, not the plain-HTTP tailnet development URL. The notification title uses the orb's current user/auto-generated display name when present and falls back to `Orb <id>` only while unnamed. Because first-turn auto-naming runs concurrently, receipt of `turn_notification` performs one ordinary orb-resource refresh before constructing the notification; a ref supplies the last known name if that refresh fails, without reconnecting the live socket when naming completes. The orb/operation pair is the notification tag and local deduplication key; clicking focuses and navigates to the orb. Same-tag browser replacement suppresses duplicates from multiple open tabs. Notifications are deliberately best-effort: no service worker, Web Push subscription, persistence, or reconnect replay exists, so closing all orb pages means receiving no notification.
- **Chat Markdown and URL linkification (decided and implemented 2026-08-05).** User and assistant messages use the same GFM Markdown pipeline in committed and streaming content. Its autolink-literal extension makes web URL literals clickable while composing with the syntax tree, so code spans/blocks and existing link syntax are never linkified a second time. Displayed custom messages, reasoning, and compaction summaries remain literal non-Markdown text and pass through a dedicated URL tokenizer instead of an ad-hoc regular expression. Only HTTP(S) and `www.` web URLs are linked; email and other schemes remain text. Generated external links open in a new tab with `noopener noreferrer`. Tool inputs and outputs remain verbatim code-like text and are deliberately not linkified.
