The package's manager-unit commit is `cf7bee6862f978b202756080920403cb96ad633c`; the installed core plugin reports only `devel`, so its nested build SHA cannot be recovered from the package. Review of matching core-plugin source `07372db475afc8702a079ff8b3afac411143f620` explains why the unit ordering was insufficient: manager readiness covers early initialization, while instance-ID first-boot work runs in the late stage. An early metadata/setup failure can be swallowed; the late stage retries metadata, then first boot and OS Login run concurrently. First boot replaces each key through temporary files and publishes guest attributes. OS Login can reload or restart SSH. Thus manager `READY` is not a host-key completion signal, and a late writer/restart can expose a different key after SSH readiness. The deleted journal prevents proving that exact schedule occurred in the failed validator.

The correction keeps Google as the sole producer. Sealing checks the package, effective unit properties, and enablement contract; readiness independently checks the three expected key types. SSH requires a oneshot barrier after the manager. `/etc/google_instance_id` is an identity check, not a completion signal: source review found it is written before platform setup. The barrier opens only when that ID matches metadata, the ECDSA, ED25519, and RSA private/public pairs agree, and each corresponding guest attribute equals its local public key. Its elapsed 90-second deadline covers the audited roughly 30-second late metadata retry and stays inside the unit's two-minute limit, including one-second metadata request caps. Failure leaves SSH closed and a journal message identifies the barrier failure. The validator records the local ED25519 fingerprint at readiness and after acceptance; strict SSH checking authenticates the peer on both connections. A confirmed SSH warning or local fingerprint disagreement fails immediately as typed `ssh_host_key_mismatch`.
