# Control-plane CPU pressure and Cloud Run 429s

Investigated 2026-10-09. Reported orb: `0a82766c-9226-45ca-b0d5-ef91b9d7e39c`.

## Evidence

All times UTC. Read-only Cloud Logging, Monitoring and service-description queries:

- Serving revision `pi-orb-issuer-00047-czn`, 100% traffic; one minimum/maximum instance, one vCPU, 1 GiB memory, configured concurrency 80. Image digest `sha256:433f987d4f6a954ddf21a260562a9b3a8ad725ce8c254f54f0de5da30c51469f`.
- Between 14:45 and 15:12, 388 request logs returned 429; first at 14:58:23.923827, last at 15:10:15.118700. Every rejection has Cloud Run's `The request was aborted because there was no available instance.` payload. Affected routes include projects, orb metadata, hosted files, inbox polling, uploads and OIDC discovery. These are ingress refusals, not application or model-provider rate limits.
- CPU minute samples rose from approximately 11% before 14:50 to 77% at 14:58, 97% at 14:59 and 94–100% during 15:00–15:07. At 15:10 CPU was still 83%.
- The instance remained active. Recorded maximum-request-concurrency distribution means were approximately 8–10 during 14:52–14:58 and approximately one in populated samples during 15:00–15:08. These metrics do not show the configured 80-request ceiling being reached.
- Memory reached approximately 75% at 15:08. The bounded system/error query found no instance termination or OOM evidence; its one ERROR was an application 503 on initial checkout.
- Follow-up `run.googleapis.com/scaling/recommended_instances` reads directly show ACT recommending two instances at 15:00–15:01 and 15:08–15:10; CPU utilization recommends two at 14:59–15:11, while ordinary concurrency recommends one. Evidence: `.context/429-investigation/recommended-instances.json`.
- Some requests succeeded throughout the incident. At 15:09:37 the reported orb's metadata, hosted-files and projects reads returned 200 in approximately 6–9 ms. Successful requests do not establish recovery while ingress refusals continue.

Evidence is retained in `.context/429-investigation/`: `rejected-requests.json`, `cpu-utilizations.json`, `max_request_concurrencies.json`, `instance_count.json`, `utilizations.json` (memory), `service-resources.json`, `system-errors.json`, `live-requests.json` and `other-requests.json`. The latter query reached its 2,500-entry limit and does not establish complete non-429 coverage.

## Diagnosis and limits

Confirmed: Cloud Run rejected requests before application handling while the sole instance's CPU was saturated. CPU-driven adaptive concurrency explains refusals below configured concurrency: [Google documents](https://docs.cloud.google.com/run/docs/about-instance-autoscaling#adaptive-concurrency-tuning) that ACT lowers admitted concurrency each second above 90% CPU; background CPU can interfere. Follow-up scaling-driver metrics confirm ACT requesting capacity above the one-instance ceiling during the incident. The exact per-second admission limit was not captured.

Central Pi agents now share the control-plane CPU with browser/runtime/identity HTTP handling. No CPU profile was collected; these observations do not identify the expensive function or prove an agent loop. Merely raising configured concurrency does not address adaptive CPU-based admission.

**Code-mode hypothesis (2026-10-09):** source confirms `apps/control-plane/src/adapters/durable/tools/codemode.ts` constructs the standalone `pi-codemode` sandbox in the control plane. Each execution runs QuickJS/WASM in a fresh Node worker through `bounded-worker.js`; tool callbacks and serialization return to the host thread. Workers share the container's CPU allocation. The adapter sets a 256 MiB VM heap limit, callback/output limits and a default five-minute wall deadline, but no separate worker CPU quota. Thus CPU-heavy script execution or repeated worker initialization can consume API serving capacity without directly blocking the host event loop. Nested shell/filesystem operations still use authorized guest execution. The screenshot's code-mode calls establish use, not CPU attribution; no worker CPU timing/profile was captured. Library source: [pinned host](https://github.com/earendil-works/pi/blob/9b3c19da5cffc4c5e8b6bd74c45abc1ab6bfcd16/packages/codemode/src/runtime/host.ts).

**Configuration research (2026-10-09):** Cloud Run supports `--scaling-cpu-target=disabled` (Terraform `cpu_utilization = 0`), but [Google explicitly states](https://docs.cloud.google.com/run/docs/configuring/scaling-controls#configure-custom-targets) that ACT remains active when CPU-based scaling is disabled. This controls instance-count decisions, not CPU-based concurrency protection; it is not an established remedy for these ingress refusals. No documented ACT-disable setting was identified. No configuration change was selected or applied.

## CPU audit and observability (2026-10-09)

No tight idle loop was found in the inspected lifecycle, admission, owner-renewal, durable-scheduler or code-mode waiting paths:

- Lifecycle polling/reconciliation sleeps between passes; execution readiness sleeps 100 ms; ownership renewal sleeps 20 seconds.
- The durable scheduler coalesces event-triggered work through `queueMicrotask`; its drain stops when no further work marks it dirty. This does not rule out pathological event churn.
- The code-mode worker drains QuickJS jobs initially and on callback messages, then waits for messages. A generated script can still spin or continuously enqueue microtasks; the wall deadline bounds duration, not CPU consumption.
- `http/central-live.ts` polls WebSocket drain every 25 ms per connection. `OutboundWriter.onDrain()` immediately exits when its queue is empty. This is unnecessary idle wakeup work, but no evidence attributes saturation to it.
- `adapters/durable/agent.ts` queues a complete history copy/projection on each commit containing a root-conversation entry. It also constructs a fresh display projector and visits every public record, including known records. This is repeated work proportional to accumulated history per publication, not idle polling; its incident CPU contribution is unknown.

Local experiment after `npm ci`: Node v24.6.0 on macOS, installed pinned `pi-codemode` through the production bounded worker, three fresh executions of `text(await tools.wait({}));`, each callback awaiting a two-second timer. All succeeded. Process-wide CPU during each wait was 36.709, 12.421 and 10.320 ms over approximately 2,001 ms wall time (0.5–1.8% of one core). Full executions used 112.431, 49.920 and 45.469 ms CPU. These include all process threads and initialization/background compilation, not isolated worker CPU; they disprove neither a workload-specific loop nor production behavior. They show this minimal waiting path does not spin locally. Harness and results: `.context/429-investigation/codemode-wait-cpu.mjs` and `codemode-wait-cpu.json`. The preserved first harness failure (`codemode-wait-cpu-first-failure.json`) came from workers inheriting stdin-only `--input-type=module`; running a file removed that harness error.

Cloud Monitoring and Datadog expose container CPU, memory, concurrency, request and scaling metrics. The inspected application/image/live configuration has no CPU profiler or per-worker CPU accounting. Existing code-mode timings measure wall time. `infra/rollout_monitor.py` collects Run memory/instances/startup metrics, but not Run CPU; its error-log filter/counts include 5xx and ERROR, not these ingress 429 warnings.

CPU attribution needs separate main-thread and worker measurements, initialization/execution/callback timings, active worker count and bounded profiles correlated by orb/call identifiers without script or credential contents. Process-wide `process.cpuUsage()` alone cannot attribute overlapping workers. Node offers [worker CPU accounting and profiling](https://nodejs.org/api/worker_threads.html), subject to the deployed Node minor version. Main-thread profiling alone misses worker execution. Google's [Node Cloud Profiler agent](https://docs.cloud.google.com/profiler/docs/profiling-nodejs) supports wall-time and heap profiles; it is not currently installed and does not provide Node CPU-time profiles.

**Profiling feasibility experiment (2026-10-09):** running the same local waiting harness with `node --cpu-prof --cpu-prof-dir=.context/429-investigation/profiles` produced four valid JSON `.cpuprofile` artifacts: main thread plus all three terminated code-mode workers. Each contained sampled stacks, predominantly idle for this workload. Thus the CLI can profile these workers without a sandbox patch locally. Evidence: `.context/429-investigation/profiles/` and `codemode-profile-check.json`. [Node's CLI profiler](https://nodejs.org/api/cli.html#--cpu-prof) writes artifacts before thread/process exit; this experiment does not qualify collection from a long-running production instance or show the incident hotspot.

**Production capture proposal (2026-10-09; not implemented):** one bounded 30-second diagnostic capture during natural central-agent work, recording the main thread through an in-process [inspector Session](https://nodejs.org/api/inspector.html#cpu-profiler) and separately profiling code-mode workers. This needs worker lifecycle hooks in the existing `pi-codemode` host boundary: start profiling on worker startup and stop/collect before termination, including timeout/abort handling. `worker.startCpuProfile()` requires Node 24.8 or later; `worker.cpuUsage()` requires 24.6. The Dockerfile uses floating `node:24-bookworm-slim`; inspection of the exact serving image during the managed-agent evaluation confirmed Node 24.21.0. Persist private artifacts immediately with revision, capture interval, thread/orb/call identifiers and explicit missing/failed capture status, rather than depending on container shutdown/filesystem retention. Pair sampled profiles with process/main/worker CPU counters and phase timings: sampled stacks identify work, counters establish which thread consumes CPU, and timings distinguish initialization, execution, callback serialization and history projection. V8/WASM frames may not identify QuickJS guest source functions. This proposal is diagnostic, not a claim of a configured profiler or a selected production rollout.

**Managed alternative (researched 2026-10-09; not installed in the application):** Google Cloud Profiler provides continuous collection and managed flame graphs through `@google-cloud/profiler`, with the Profiler API enabled and runtime service-account `roles/cloudprofiler.agent` access. Node wall-time samples can identify frequently sampled expensive stacks despite lacking a separate CPU-time profile type; that limitation alone does not justify rejecting the managed agent. The current [agent source](https://github.com/googleapis/google-cloud-node/blob/main/handwritten/cloud-profiler/src/index.ts) recognizes Cloud Run's `K_SERVICE` and `K_REVISION`, although Cloud Run is absent from the documentation's supported-environment list. Native compatibility and worker coverage were tested below; actual Cloud Run collection remains unqualified. A custom collector is an alternative if the managed agent cannot capture the relevant work, not an established prerequisite for production profiling.

**Managed-agent evaluation (2026-10-09):** isolated installation of `@google-cloud/profiler` 8.1.0 / `pprof` 5.0.0 on the exact serving Linux x64 image succeeded. The image runs Node 24.21.0; native sampling, heap collection, gzip/protobuf encoding and synthetic Cloud Run service/revision recognition worked. Experiments used the agent's real `profile()` collection method without starting cloud polling, then decoded its artifacts. Docker Desktop emulated x64 on an ARM Mac, so production overhead is unmeasured.

- A main-thread two-second hot loop appeared in sampled stacks; its three-second collection window used 2,353 ms process / 2,180 ms main-thread CPU, with 31.55% idle samples.
- A timer wait yielded 99.72% idle samples.
- A synchronized two-second code-mode QuickJS hot loop succeeded and used 2,235 ms process / 219 ms main-thread CPU, yet the managed profile was 99.59% idle and contained no QuickJS/WASM frames. Initialization completed before the sampling gate, isolating script execution from startup.
- Loading the native pprof module inside a Node worker failed with `ERR_DLOPEN_FAILED: Module did not self-register`. The [published native binding](https://github.com/google/pprof-nodejs/blob/main/bindings/profiler.cc) uses ordinary `NODE_MODULE` registration and creates its sampler for the current isolate. A main-thread agent does not automatically profile code-mode workers; installing it inside those workers is not viable unchanged in this tested release.

Read-only GCP checks found the Profiler API disabled; an authenticated profiles-list probe returned 403 `SERVICE_DISABLED`. The runtime service account's project bindings lack Profiler Agent. No API/IAM change or upload was attempted. End-to-end managed backend collection and actual Cloud Run execution remain unqualified. The isolated dependency audit also reports 8 moderate / 2 high package entries, including profiler's protobufjs dependency; no repository dependency changes were made.

**Evaluation conclusion (2026-10-09):** reject the unchanged managed agent as a complete diagnostic for this incident because it misses the suspected code-mode CPU path. It remains a candidate for main-thread history/serialization and heap analysis. Separate native worker CPU counters/profiles are required for complete attribution; this finding does not identify the production hotspot. Evidence, harness, first fixture-error correction, exact commands and limits: `.context/profiler-evaluation/README.md`, `results-linux/report.json`, `weighted-samples.jsonl`, `.pb.gz` artifacts, build/audit logs and read-only GCP checks. Mac Node 24.6.0 independently reproduced the worker blind spot/load error.

**Throttle feasibility experiment (2026-10-09; not integrated):** the image's QuickJS interrupt callback can block with `Atomics.wait()` and return normally, preserving a running guest calculation. A shared 12 ms CPU / 20 ms wall budget used `process.threadCpuUsage()` at engine checkpoints, atomically charged all workers, carried overshoot debt and parked exhausted workers until main-thread refill/notification. One unthrottled worker used approximately 100% process CPU; one throttled worker used approximately 64% process / 58% worker CPU; two throttled workers together used approximately 59% process / 56% worker CPU. All completed the same five-million-iteration calculation with checksum `1642668640`. Results establish cooperative pause/resume and shared accounting, not an OS-enforced quota or ingress guarantees. VM initialization was outside the timed gate; compiler/runtime threads and host work are outside worker credit. Engine warmup makes elapsed-time comparisons unsuitable for performance claims. Production cancellation, callback/state semantics, fairness, deterministic scheduling and sustained HTTP/Cloud Run admission remain unqualified. Evidence and preserved harness/refill corrections: `.context/profiler-evaluation/README.md`, `throttle-evaluate.mjs`, `throttle-worker.mjs`, `results-linux/throttle-60-percent-report.json` and `throttle-initial-report.json`.

**Revised budget experiment (user-selected 2026-10-09; not integrated):** the user is independently changing Cloud Run to two vCPUs and selected a shared code-mode allowance of 1 CPU-ms per elapsed wall-ms. The prototype now grants 20 ms CPU per 20 ms wall period, caps unused credit at one period and carries overshoot debt. On a two-vCPU container, two unthrottled workers consumed 1.87 worker cores (1.95 process cores); throttled workers consumed 0.94 worker cores (0.98 process cores). All four one/two-worker unthrottled/throttled cases completed with the same checksum. This updates the proposed interpreter budget, not production integration or initialization/compiler coverage. Evidence: `.context/profiler-evaluation/results-linux/throttle-report.json` and `throttle-one-core-evaluation.log`; the historical 60% report/log are preserved separately.

## Local implementation (2026-10-09; not deployed)

The bounded central worker now receives one process-wide atomic credit pool through sealed public sandbox worker-data hooks. Actual monotonic elapsed time replenishes one CPU microsecond per wall microsecond; idle credit is capped at 20 ms, and overshoot debt survives cancellation/reentry. Cumulative worker-thread CPU charges startup and subsequent QuickJS/callback/output checkpoints. Exhausted workers park without spinning or discarding guest state. Host deadlines/abort/close retain termination authority. Details, exclusions and terminal durable CPU/wait telemetry: `docs/pi-adapter.md`.

The production bounded worker on the serving image's Node 24.21.0, in a two-CPU Linux container, measured 1.00/0.99/1.01 aggregate process cores with 1/2/4 infinite-loop workers. Eight-second measurement windows followed three-second warmup. Concurrent loopback HTTP p99 was 6.2/3.4/3.9 ms; all workers terminated on abort. Evidence: `.context/cpu-budget/production-worker-stress.json`, `stress.mjs`, `stress.log`. Docker Desktop emulates x64 on this Mac; these are local qualification measurements, not production latency guarantees. No native-operation/kernel quota or Cloud Run ingress proof is claimed.

Targeted tests cover bounded idle credit, debt carry, timer lifetime, real concurrent VM callback/job/store preservation, and explicitly synchronized parked-worker abort, timeout and close. One hundred recorded deterministic schedules cover concurrent debit/refill and cancellation/reentry. The first DST fixture failure called a nonexistent `failPoint`; its trace was replayed before correcting the fixture to recorded cancellation entropy. Trace: `test-failures/codemode-cpu-budget-1791584932636-0.json`; first/replay/corrected logs: `.context/cpu-budget/`. Patch seal regressions pass for fresh and already-applied installations. Run CPU is now required rollout evidence; a logged ingress 429 marks the observation as a regression despite healthy application probes.

Initial broad macOS checks exposed unsupported Linux/pidfd process-provider tests, macOS `/var` realpath expectations, inherited user skills and missing real PostgreSQL fixtures. First-failure logs and focused reproduction are preserved in `.context/cpu-budget/full-tests.log` and `unrelated-failure-diagnosis.log`. The Linux container independently returned `ENOSYS` from `os.pidfd_open` and exit 121 from the seccomp guard under x64 emulation; its native lifecycle failures cannot qualify native Linux behavior. Adding the absent `jq` prerequisite cleared the isolated infrastructure checks. Evidence: `.context/cpu-budget/pidfd-probe.log`, `linux-sdk-diagnosis.log`, `linux-infra-with-jq.log`. Native Linux CI and full E2E remain release gates; these initial failures are not treated as noise or cleared by a rerun.

The macOS broad run also exposed a release-child test synchronization defect: before any child creates its readiness log, `grep -c` returns empty output, the shell arithmetic predicate fails, and the fixture sends SIGTERM before readiness. The observed log contained only `parent-exit`. A missing-file probe reproduced the fall-through; precreating the empty log makes the fixture wait for actual ready records. All 29 release-stage tests pass after this one-line fixture correction. Evidence: `.context/cpu-budget/readiness-missing-log-probe.log`, `native-release-readiness-corrected.log`.

Local typecheck/lint, 67 tool tests (including the CPU DST), 18 dependency-patch regressions, 12 rollout-monitor regressions and the Linux infrastructure suite pass. The initial macOS broad run records 36 failures / 4,129 passes; local full E2E has recorded two mobile UI failures and remains unqualified. Neither broader result is waived by limiter-specific checks.
