# 2026-08-05 — unreachable-restart livelock against real VM boot times

Status: closed as of 2026-08-06. Root defects (a), (b) and (c) are fixed, and so is the blindness that made this reconstruction necessary in the first place. The lifecycle rules this incident produced are in `docs/lifecycle.md`. Orb 104600b7 can be restarted once the fix is deployed.

The forensics gap is closed as of 2026-08-06 (rules and event vocabulary in `docs/lifecycle.md`, "the reconciler's event log"; test technique in `docs/testing.md`). The control plane now logs every state transition with its reason, every provider provision/start/stop it decides on with the reason it was issued, the unreachable-restart decision with the grace that expired and whether that grace was the ordinary or the post-restart one, the `stopping` restart cap's refusal, boot-detection outcomes with host-side evidence, and drain progress — under a strict noise rule (a healthy fleet logs nothing; conditions that persist log on their edge, not per tick). A second, quieter defect surfaced while implementing it: the background loops ran under `determined`'s `noSimulation`, whose task logger is hardwired **off**, so even the orphan sweep's pre-existing `task.log` lines could never have reached Cloud Logging. The loops now run on a task that logs. The instrumentation paid for itself immediately — the first flaky DST schedule it met (`sweep-leaves-live-orbs`) was diagnosed from its four log lines alone.

Root defect (c) is closed as of 2026-08-05: the fake world now models host boot latency (65 s by default, everywhere) and hypervisor preemption, and the rule is recorded in `docs/testing.md`. Modeling the boot also showed the livelock is not exotic: with a realistic boot, *any* scheduler-legal lapse of the liveness grace in `running` or `stopping` livelocked, which several unrelated scenarios hit until they temporarily opted out of boot latency.

Root defects (a) and (b) are closed as of 2026-08-06 (decision and rationale in `docs/lifecycle.md`). (b): the inline restart in `running` now CAS-transitions the orb to `starting`, so the patient readiness path — 5 s health polls, the boot sub-deadline, the create/start deadline — drives recovery and no path restarts a host twice from `running`. (a): the `stopping` copy of the restart, which must stay in `stopping` because a pending drain cannot be handed to the readiness path, seeds its liveness baseline with a boot-sized `postRestartGraceMs` (3 minutes) instead of the 30 s unreachable grace, and attempts at most one restart per stopping episode — a second expiry with no pull success in between fails the drain with `drain_runtime_unrecoverable` on evidence rather than waiting out the deadline. The two reproducer scenarios `preemption-while-running` and `runtime-dies-during-stopping-drain`, plus the new `stopping-restart-cap`, are green in `apps/control-plane/src/domain/lifecycle.dst.test.ts`, and every scenario that had opted out of modeled boot latency now runs with it.

**Field finding (2026-08-05, orb 104600b7, `drain_runtime_unrecoverable`): the inline unreachable-runtime restart livelocks against real VM boot times.** Reconstructed from GCE operation audit logs and boot-disk journal forensics (the control plane emits no app-level logs — itself a gap). At 21:16:22Z the VM received a hypervisor ACPI power-off while the orb was `running` (no stop API call and no preemption/hostError event was logged; on a Spot VM the only designed-for source of an unlogged ACPI soft-off is preemption, whose terminal operation was evidently masked by our own stop racing it 32 s later). During the ~30 s ACPI soft-off window the instance still observes as `running`, so the *liveness* path won the race against the *observation* path: at 21:16:54 the 30 s `unreachableGraceMs` expired and the reconciler did its inline `stop`+`start`. From there the loop was self-perpetuating: a COS VM needs ~60–70 s from `instances.start` to a serving runtime container (journal: userspace up ~26 s in, Docker initialized ~33 s in, container started ~35 s in — 2 s before each next stop landed), but the restart path grants only the same 30 s grace before concluding unreachable again. 38 stop/start cycles over 38 minutes, each hard-stopping a booting VM (repeatedly exercising the docs/history-replication.md/Q33 durability gap). The `running`-state loop has no deadline and would have cycled indefinitely; it ended only because idle-stop moved the orb to `stopping`, where the drain deadline expired into `drain_runtime_unrecoverable`. The intended "preemption surfaces as TERMINATED → stopped → normal restart path" never engaged because the inline restarts kept re-starting the instance before it could be observed as stopped. Root defects: (a) the post-restart liveness grace is shorter than a real boot, guaranteeing livelock whenever the inline restart fires against a full VM boot; (b) the inline restart stays in `running` instead of re-entering `starting`, so the patient readiness path (5 s health polls, 15-minute deadline) never takes over; (c) DST did not catch it because `FakeWorld` boots hosts instantaneously — boot latency must become a modeled, schedule-controlled delay.
