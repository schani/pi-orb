This identifies the response-size rejection as the immediate failure, not stopped/idle lifecycle state. No payload byte count or precise limit was measured; no stored history record bodies were retrieved.

`apps/control-plane/src/http/routes.ts` returns the full `readHistorySnapshot` in one JSON reply. `apps/control-plane/src/adapters/pg/store.ts` follows `replication_cursor` through every ancestor and returns each complete JSON record; there is no browser-history paging/limit. The stopped orb needs no runtime to serve history. The `after`/`limit` query in `docs/history-replication.md` is the **runtime replication pull**, not a browser/ops pagination API. The in-orb transcript route also reads the same full snapshot. Cloud Run's empty 500 bypasses the application's typed store-error response, so SQL schema drift is not needed to explain this incident.

The current full-snapshot contract and the earlier large-transcript finding are in `docs/history-replication.md` and `docs/postmortems/2026-09-15-long-transcript-navigation.md`. **Implemented 2026-09-27; deployed 2026-09-28:** both browser and runtime inspection routes stream the unchanged JSON response without `Content-Length`. Registered-route HTTP tests exercise each route above 32 MiB, preserving the JSON schema; a real HTTP test reads a >32 MiB chunked transcript through `HttpOrbInspectionEndpoint` within its unchanged 3-second deadline. Gated-writable, empty-metadata and serialization-failure tests cover backpressure/cancellation and interrupted responses. Size and interruption edges use `logOrbEvent(task, orbId, ...)`, because production disables Fastify's logger. Google's [Cloud Run quotas](https://cloud.google.com/run/quotas) state that the 32 MiB HTTP/1 response limit applies only when the response is neither chunked nor streaming. Streaming does not cure whole-snapshot memory and navigation costs; bounded paging remains separate work in `TODO.md`.
