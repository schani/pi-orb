## Bugs

- **Fence stale control-plane revisions out of autonomous lifecycle authority** (incident: `docs/postmortems/2026-08-11-release-smoke-restart-registry-timeout.md`). Deleting Cloud Run revision `00029` did not terminate its always-allocated reconciler: it continued starting the smoke VM, running boot detection, and eventually failing the orb for 7 minutes 42 seconds after the deletion audit event. The per-host generation fence prevents backward metadata repair — and, under `docs/compute-replacement.md`, backward host-spec replacement — but still permits stale lifecycle actions: a stale revision can start hosts, run boot detection, and make terminal transitions (which there cost a disposable boot disk rather than a stop). A durable active-generation/lease check around every autonomous lifecycle mutation and terminal decision is still required. Compensate late side effects and extend mixed-generation DST through stale start, boot failure, state transition, spec-replacement fencing, and incarnation-bounded compute disposal. Revision deletion remains cleanup only.

Deploy it and pass the mandatory create → running → stop → start smoke before closing this item. `docs/compute-replacement.md` later removes in-place host updates, so retaining an old container becomes transitional; bounded pull retries remain required on every fresh VM.

## Hardening

- **Correlate GCE startup and container diagnostics to one boot attempt** (incident: `docs/postmortems/2026-08-11-release-smoke-restart-registry-timeout.md`). The terminal error joined a current `docker run` failure with the previous boot's `status=running` reporter value. Include a boot-attempt identity in both guest attributes, or clear/stamp container state before each startup, and have `diagnose` reject stale supplementary evidence.
- **Implement immutable compute replacement** (`docs/compute-replacement.md`; incidents: `docs/postmortems/2026-08-06-rollover-repair-war-corrupt-image.md` and the independent Spot-preemption incident matching that failure path `docs/postmortems/2026-08-12-spot-preemption-corrupt-entrypoint-layer.md`). Two stages. Stage 1 failed-compute disposal is code-complete 2026-08-12, including store/provider/lifecycle/token/Tailscale contracts, diagnosis-before-discard, deterministic GCE and lifecycle race coverage, the exact-incarnation E2E launch seam, passing process E2E, and `infra/smoke-compute-replacement.sh`; its remaining release gates are Docker/PostgreSQL E2E and disposable live-GCE smoke on capable infrastructure. Stage 2 remains: immutable spec fingerprint plus forward-only deploy-generation fence and removal of GCE in-place script/image repair, with its DST/provider/E2E/live validation.

- **Close the served-vs-durable persistence gap** (was open question 33; incident: `docs/postmortems/2026-08-03-cursor-not-found.md`). The runtime answers history pulls from in-memory session entries while the SDK persists with `appendFileSync` and no fsync, and the SDK loader silently drops a truncated tail line on reload. A hard host stop can therefore lose a record the control plane already replicated and committed as its cursor, stranding the orb in a `cursor_not_found` integrity failure. Candidate fixes: serve only durably-persisted entries (fsync barrier or persisted-watermark cursor), fsync at drain time, and/or make the loader surface a truncated tail as a load error instead of silence.
- **Abort the GCE startup script when the data-disk mount fails** rather than bind-mounting an empty directory as `/workspace` (from the same incident).
- **Refuse to silently create a fresh session when the control plane already holds replicated history** (from the same incident).
- **Operator replication-reset escape hatch** — recovery from an integrity-`failed` orb today is a new orb (from the same incident).
- **Make the unreachable-runtime decision measure and corroborate actual runtime silence** (incident: `docs/postmortems/2026-08-05-egress-blip-false-unreachable-restart.md`, defects a+b). Today `silent_ms` is "time since last pull success", so time spent waiting on a slow GCE observe — pull attempts are serialized behind a 60 s `observe host for pull` — counts as runtime silence, and a control-plane egress blip reads as a dead runtime; the 2026-08-05 incident hard-stopped a healthy runtime mid-turn without having sent it a single request during the measured silence. A first piece landed 2026-08-10 with the inbox dispatcher: an accepted message delivery is a liveness success, so a runtime answering non-pull requests is no longer restarted for pull silence (`docs/lifecycle.md`). The remaining gap is still visible in DST and is the one flake class left in `lifecycle.dst.test.ts`: under a schedule that cancels every control-plane request by its own deadline for longer than the grace, the reconciler restarts a runtime it never actually reached, and the affected scenarios are budgeted below a modeled host boot, so a restart they cannot absorb reads as a `waitUntil` timeout. Measured 2026-08-10 by running the whole file repeatedly: `preemption-mid-turn-resumes`, `resume-guard-single-shot`, and `idle-stop-across-restart` fail 4 times in 150 runs at ffb416d and 7 times in 200 runs with the inbox fixes — the same rate, none of them inbox-related. Re-measured 2026-08-11 after the crash-window scenarios landed: 1 `resume-guard-single-shot` failure in 31 whole-file runs, same shape (the resumed turn's replication times out behind a restart the runtime never earned), plus 0 in 20 isolated runs of that scenario. The same measurement also costs new scenarios an assertion: `idle-stop-versus-send` cannot assert "no host stop" while it waits out an idle window, only "no *idle* stop", because this false positive can appear in any schedule. Fixing the measurement fixes the scenarios; nothing else in that file flakes. Remaining candidate fixes: base the baseline on pull *attempts that reached the runtime* rather than successes-only, and require corroboration before restarting (e.g. hold off while provider API calls are themselves failing/slow — a failing observe means "my egress is broken", though a successful `RUNNING` observe proves nothing per the livelock postmortem).
